# CI lanes maintenance

`.github/workflows/test.yml` runs the epic suite. No job may run longer than 10 minutes (`timeout-minutes: 10`), with these documented exceptions: the `e2e` lane has 15 job minutes and a 12-minute step, because a shard Chromium boots its own app server and needs about 8.5 minutes under the account's runner cap; the Windows `libs` lane ("other packages") has the same 15/12 budget because that lane finishes under time once the step is not cut at 8 minutes. A core shard passes `--only` to `turbo test`, so it does not run `@orchestra/plugin`'s `tsc`. That compile does not finish inside the 8-minute step on Windows, and a build step ahead of it hashed the task differently from the test step (run 43110315940). The test step stays 8 minutes except for that documented libs step. Core imports the plugin from source. The aim is about 5 minutes of test time per job. The planner `packages/script/src/test-plan.ts` and its data file `packages/script/src/test-timings.json` decide how many shards exist and which test files each one runs.

## Layout

A `plan` job (Node 24, no install) runs `node packages/script/src/test-plan.ts plan` and writes three outputs: `unit` (the matrix of the `unit-rest` job), `e2e` (the shard numbers) and `e2e_shards` (their count). The jobs read them with `fromJSON`, so adding tests changes the shard count without editing the workflow.

- Core (`packages/core`) is sharded on both OSes. Each shard job runs `bun packages/script/src/test-plan.ts shard packages/core <linux|windows> <i> <n>` and hands the file list to `bun turbo test`. Files go to the lightest shard first (longest first). The file list is part of the Turbo task hash, so recomposed shards never replay a stale cache entry. On Windows, `test/filesystem/watcher.test.ts`, `test/tool-write.test.ts`, `test/tool-safety-loopback.test.ts`, `test/tool-safety-sandbox-repairs.test.ts`, and `test/review-toolkit/dependency-shadow.test.ts` are pulled out of that list and each runs in its own `bun test` process, still inside the 8-minute step. The watcher file left a `watcher.node` segfault inside the 85-file process (run 43066731722, twice) and passes alone (test-ci 43109694032). `tool-write.test.ts` is measured at 0.4s and held the shard until the step died (runs 43156203910 and 43217078756). The loopback file prints its Windows proof and then does not return (runs 43232120353 and 43237306628); it exits that process itself, which is why it cannot stay in the shard. `tool-safety-sandbox-repairs.test.ts` does the same after its Windows hold line (run 43242689800). `dependency-shadow.test.ts` started and did not finish before the step died (run 43307894859, windows core 3/9). Run alone, it was still going 5m43s later when the step died, because it started after the shard (run 43319710781). Alone files now start with the shard and the step waits for them, so a slow file gets the same 8 minutes. That was still not enough: the file was running at the 8-minute mark with no failure (run 43333229249). Its caps test writes about 100,000 files and is budgeted at 10 minutes, so it is skipped on Windows. Linux still runs it. The skip is one line, because the file is already over the godfile hard limit and must not grow (run 43350528558). An alone file runs with the omni control scope set to `declared`. Unset is the suite requirement, which failed `tool-write.test.ts` because that file makes no omni spawn (run 43242689800). A file that declares a spawn still has to make one. The shard command passes `--preload ./test/file-start.ts`. That file writes each test path to fd 2 when bun resolves it. `--only-failures` prints no file header until a failure, and a hang before that left the step with no name (run 43258630212, windows core 3/9).
- The other Turbo packages run in fixed lanes (`packageLanes`, same on both OSes unless noted): `app` (the app package alone), `cli` (cli, server, sdk-next, client, tui, session-ui), `atlas` (atlas-boundary alone), `relay` and `libs`. The `@orchestra/relay` package has its own turbo lane on both platforms; the pytest suite stays in the Linux gates lane. The libs lane is the complement of every other filter, so a package added later lands in it. The app lane passes `--only` to `turbo test`: its tests import `@orchestra/ui` from source, and that package's `tsc` does not finish inside the 8-minute step on Windows (run 43225486925). Parts are named `packages-<lane>` on Linux and `windows-<lane>` on Windows.
- Rule: relay and rollback get their own lanes. Linux has a `gates` lane (repo-wide gates plus the Relay suite, no Turbo run at all). On Windows the rollback proof and the process query proof ride in the `atlas` lane, which does not build core, so the proof never waits behind a bulk package. Never put relay, the repo gates or the rollback proof back into `libs` or any lane that runs a bulk package: that is what pushed the lane over the 10 minute job limit.
- Linux has two HttpApi lanes, `httpapi-1` and `httpapi-2`. Each still runs the generated client check. Coverage and auth exerciser modes run in full on each lane; effect mode is partitioned `1/2` and `2/2`. Test isolation is unchanged. A `sandbox` lane runs the `.hosted.ts` proofs. Windows has no separate hosted lane.
- `atlas-boundary` has its own lane because one generator test there takes about 210 s on Linux and 294 s on Windows. The `httpapi-codegen` package is skipped on Windows.
- Maestro stays in Linux `libs`. Windows has `maestro-1` and `maestro-2`: the first runs only `test/v2-reservation-currency.test.ts`, and the second discovers every other Maestro `.test.ts` file. `plannedBins` refuses a missing currency file or an empty complement. These lanes use the existing 10-minute job and 8-minute step, the package's `bun test --timeout 30000` task, unchanged bunfig preloads and the suite-wide omni proof. The workflow passes exact `./` paths through Turbo, so the file list participates in its cache key; it never uses the Core-only `SHARD` branch. Both cold reports map back to `modules/maestro/coordination`, not Core.
- e2e shards come from `packages/app-shell/script/e2e-timings.json` through the same shard-count rule. The previous-pass marker of each shard is keyed `e2e-<os>-<shard>of<N>`, so a relabel replays shards whose inputs did not change.

## Timings file

`packages/script/src/test-timings.json`:

- `target`: seconds of test time per job for `linux`, `windows` and `e2e` (330, 400 and 270). Windows is higher in seconds only because its totals are scaled by `overhead` first; the jobs themselves aim at the same wall time.
- `overhead`: per-OS factor applied to a package's measured total before the shard count. Linux is 2: two real 8-minute failures against a 258s estimate bound the ratio at 1.86, so 2 is the declared overhead, not a fabricated measurement. That factor is paired with two HttpApi effect partitions; coverage and auth stay full and test isolation is unchanged. The lead computes the resulting job count; do not record a hand count here. Windows is 1.8 as declared capacity headroom after run 43514304929 (AppContainer provenance below). The historical 1.6 baseline came from epic run 41317028045, where the Windows core shards ran at 1.0 to 1.6 times (at least 1.57 on the slow ones) their predicted time, and two of four timed out at 8 minutes. A Windows shard also pays 1.5 to 2 minutes of setup, so keep its test time near 6 minutes at most. If a Windows job times out again, raise the factor before adding lanes. The factor scales the shard count (`packageShards`), not the per-file weights, so the file-to-shard packing stays comparable across OSes.
- `margin`: headroom for the imbalance that longest-first packing leaves. Shard count is `ceil(total * overhead * margin / target)`.
- `budget`: `limit` is the account cap on concurrent hosted jobs (20) and `fixed` counts the jobs outside the plan (atlas scope, atlas, two omni jobs).
- `totals`: measured seconds per sharded package and OS. Shard count uses the larger of this total and the sum of current file weights, so new files also increase capacity.
- `reserves`: optional declared scheduling floors per file, keyed like `files`. They are not measurements and never overwrite measured times. The Linux RustSec network proof reserves its 300-second test budget; both packing and shard count use the larger of its measured/estimated time and this floor. Keep workflow timeouts unchanged.
- `files`: seconds per test file, keyed `<package directory>:<os>`. A file with no entry weighs its size at the seconds-per-byte of the measured files, so a new file lands in some shard without any edit.

The shipped `files` and `totals` come from one real run of all 487 core test files on each OS (seconds between a file's header line and the next one in the job log). On that run core took 1078 s on Linux and 1244 s on Windows. Linux overhead 1.7 and Windows overhead 1.6 scale those totals before the shard count. One file dominates Linux: `backend-toolkit-cli.test.ts` (the DataFusion build, about 320 s), so it gets a shard to itself. A bigger shard count cannot help that file. If it gets slower, split the test.

Per-file times are not in a normal lane's log: the core test script passes `--only-failures`. To measure without a cold dispatch, run `bun run test:ci core <every test file as ./path> --os both`, then read the two job logs with `gh run view --job <id> --log`.

Windows AppContainer scheduling provenance: full run `43514304929`, job `132192851187`, checked out merge `46402cb5345aae9d333d2f93c5aabdc81b5d4172`. Setup Bun took 282 seconds and all work before the test step took 302 seconds. `tool-safety-appcontainer-runtimes.test.ts` started at `22:04:00.3938341Z`; the job was cancelled at `22:07:55.7744888Z`, leaving 235.381 seconds of incomplete observation, not a measured successful runtime or a proved cause. Directed Windows run `43518137505`, job `132205265374`, at snapshot `2f1869ac260d02508076f0edfabf5616f1a9d057` added only six phase logs and passed the unchanged assertions in 114.45 seconds; `settled` consumed 110.768 seconds there. The 240-second Windows reserve is a declared scheduling floor rounded above the interrupted observation, so this long file is packed separately; it is not a new measurement or timeout. The measured 69.3-second entry and historical package totals remain intact. The overhead increase provides capacity for the larger observed setup. These observations establish no upper bound for future grant preparation; keep the 10-minute job limit and existing test deadlines unchanged, and qualify the resulting plan in the next epic.

Windows Maestro scheduling provenance: whole-package qualification run `43519292900`, job `132209187710`, snapshot `1fe55daeeba88fbc1b9276bc94c4896f26f8340b`, took 482.75 seconds of tests and failed 11 cases. Currency accounted for 243.93 seconds; the remaining files accounted for about 238.82 seconds. This motivates the fixed partition, not a green qualification or a per-file timing refresh. In the epic workflow, Windows libs job `132192860651` of run `43514304929`, at merge `46402cb5345aae9d333d2f93c5aabdc81b5d4172`, spent 278 seconds before its test step, including 235 seconds in Setup Bun and 2 seconds receiving same-run native binaries. Combining that setup with either partition estimates about 522 or 517 seconds before post-job work. These cross-run estimates do not prove a future runtime bound; qualify both actual lanes without increasing timeouts. Maestro's initial planner weights remain estimates until a cold JUnit refresh and do not decide this fixed split.

## Refreshing the timings

Do this after large test changes, or when a shard job approaches 8 minutes.

1. Dispatch `test.yml` with `cold: true` on a branch (a normal epic run does not write reports). Cold shards run with `--reporter=junit` and upload an artifact `junit-<OS>-<part>`.
2. Download the artifacts into an empty directory with `gh run download <run id> --pattern 'junit-*' --dir <dir>`.
3. Run `bun packages/script/src/test-plan.ts refresh <dir>`. It rewrites each reported package's `files` and `totals`, including the Windows Maestro partition.
4. Run `bun packages/script/src/test-plan.ts plan` to see the new job count, and commit `packages/script/src/test-timings.json`.

Core has a variable shard count. Desktop, Windows App browser, Windows Boundary and Windows Maestro use their explicit partitions in `plannedBins`. If another package grows past its lane's budget, add a lane in `packageLanes` (packages/script/src/test-plan.ts) or shard that package with complete discovery. Measured package times from epic run 41317028045, Linux / Windows seconds: app 283 / 301, cli 223 / 177, server 37 / 65, small clients 38 / 39, atlas-boundary about 210 / 294. The Windows `libs` remainder was not measured on that historical run (at least 175 s); read its current job log and move a package into its own lane if `libs` nears 6 minutes of tests. Turbo with concurrency 1 prints each task's group only when it ends, so the gap between two group-end timestamps in the log is that package's duration.

## Job budget

The account runs at most 20 hosted jobs at once; jobs beyond that were once cancelled as "not acquired by Runner". `unit-rest` uses `max-parallel: 10` and `e2e` uses `max-parallel: 5`, so surplus jobs wait in the queue instead of being cancelled. `plan` prints a `::warning` when unit jobs + e2e shards + `fixed` exceed `budget.limit`; that is expected and costs wall time, not jobs. The 2026-11-12 plan is 38 unit jobs, 8 e2e shards and 4 fixed jobs, 50 execution jobs plus the short-lived plan job, so it always queues; that is accepted because the per-job limit (10 minutes, or the two documented 15-minute exceptions) matters more than the cap. To stay under the cap, raise `target`, merge lanes in `packageLanes`, or drop a hosted lane, but never merge relay or rollback back into a bulk lane.

## Hosted proofs

The `.hosted.ts` core proofs are excluded from Bun's suffix discovery, so they run by exact path:

- Linux `sandbox` lane: `tool-safety-srt-read-alias`, `tool-safety-sandbox-project-config`, `tool-safety-srt-endpoint` (needs Docker for Cassandra, Scylla and Postgres). Bubblewrap, socat and the AppArmor sysctl are set up in the job. They run with the omni control scope set to `declared`.
- `windows-process-query` runs on both OSes: in the Linux `sandbox` lane, and on Windows in the `atlas` lane (with the rollback proof).
- Paths must start with `./`: Bun treats a bare `test/x.hosted.ts` as a name filter and runs nothing.
- test.yml names the omni control's scope variable for these steps, so the ledger in `packages/core/test/test-omni-control.test.ts` lists that file. Do not write the variable's name in this skill: the ledger test scans every tracked file for it.

## Relay

The Relay suite runs under pytest-xdist (`-n auto`, pinned in `modules/relay/requirements-dev.txt`) with `--durations=15`, followed by `tests/test_arm_hook.sh` and `tests/test_concurrent_gate.sh`. A Relay test that shares a fixed temp path or port with another breaks under xdist; give it a per-test directory.

## Caches

`cache-warm.yml` seeds the dependency, ripgrep, Playwright, typecheck Turbo and pip caches on dev. It holds no test entries: test entries are saved by `test.yml`. Dispatch `test.yml` on dev to seed them; a PR epic run can restore dev's entries but never saves into dev's scope.
