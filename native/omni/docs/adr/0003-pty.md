# ADR 0003: Pseudo-terminals (`pty`) on Windows, macOS and Linux

> **Lead status (2026-10-02):** reviewed by Codex (`docs/research/adr-reviews-s1-s2.md`, verdict *reject as a product baseline*). The accepted parts and the replacement design are in **ADR-0005 (supervisor)**; where this ADR and ADR-0005 disagree, ADR-0005 wins.


**Status:** proposed (spike S2, 2026-10-02). Awaiting the lead.
**Evidence:** branch `spike/pty`, crate `spikes/pty` (throwaway), workflow `.github/workflows/spike-pty.yml`.

## Context

PLAN §3 promises `pty: true | {cols, rows}` with `write`, `resize`, `kill`, `wait` and one `output` stream. It also promises: `kill()` kills the whole tree, leaving scope kills the tree, no hangs (K2), no lost output (K5), handles/fds back to baseline (K6) and Windows parity (K8). The brief adds these requirements:
- The child sees the requested size, and resize reaches it.
- Writing `"\x03"` interrupts the foreground program.
- The output is one UTF-8-safe stream, and nothing printed before exit is lost.
- The stream ends when the child exits, with no ConPTY hang.
- `kill()` kills the PTY child's tree using the same Job/process-group model as non-PTY children.

Additions from the coordinator:
- G0 option B: we own the core, and processkit is not a dependency.
- The EOF sequence must be deterministic, with no silence timer.
- The sequence must survive a descendant that keeps writing after the child exits, and a delayed final frame.
- Unix needs a CLOEXEC/fd-inventory check.

Each experiment is one `probe <experiment>` invocation run by `spikes/pty/ci.sh`. It prints `RESULT <Q> ...` lines. The child under test is `spikes/pty/src/bin/helper.rs`.

## Q&A

### Q1: portable-pty or our own (openpty-family + ConPTY via `windows-sys`)?

**Answer: build our own.** portable-pty is rejected.

Maintenance:
- The latest release is portable-pty **0.9.0, published 2025-02-11** (crates.io API, checked 2026-10-02). That is about 20 months without a release.
- wezterm `master` has unreleased PTY changes: `8afe0ad30` "pty: windows: fix kill()" (2026-06-07) and `568f4ffad` "pty: Replace winapi with windows-sys" (2026-08-25).
- 24 open issues in wezterm/wezterm mention portable-pty. Three matter here:
  - #6783 "portable-pty 0.9.0 doesn't work on windows", open since 2025-03. The cause is the DSR request below.
  - #7742 and #7893: when exec fails, the child aborts but spawn returns Ok.
  - #5882: Windows hangs when closing panes.
- #4718, closed by the maintainer, says the EOF ordering is the caller's job: "you can expect to have to take great care with the ownership and order of operations".

Does it expose what we need?

| Need | portable-pty 0.9.0 (source read in `~/.cargo/registry/.../portable-pty-0.9.0/src/win/psuedocon.rs`, `conpty.rs`, `lib.rs`) |
|---|---|
| child pid / handle | yes: `Child::process_id()`; `as_raw_handle()` on Windows |
| child in our Job without a race | **no.** `ProcThreadAttributeList::with_capacity(1)` + `set_pty` only, so there is no JOB_LIST and no `CREATE_SUSPENDED`. Only a post-hoc `AssignProcessToJobObject` is possible. `master` is unchanged (`with_capacity(1)`, line 125). |
| ClosePseudoConsole ordering | **no explicit control.** It runs only in `Drop for PsuedoCon` when the last `Arc<Inner>` (master + slave + writer) drops. |
| headless use (no terminal behind it) | **no.** `CreatePseudoConsole` flags are hard-coded to `INHERIT_CURSOR \| RESIZE_QUIRK \| WIN32_INPUT_MODE`. ConPTY sends `ESC[6n` and holds back the child's output until someone answers. |
| spawn errors | **no (Unix).** `close_random_fds()` in `pre_exec` closes std's exec-error pipe. |

CI evidence:
- `RESULT Q1 lib=portable-pty-0.9.0 os=windows ... got_hello=false dsr_request=true got_hello_after_dsr_reply=true ... eof_with_master_alive=false drop_master_ms=0 eof_after_drop=true raw="\e[6n\e[?9001h..."` on W26100 R1/R2 and W20348 R1/R2. The child's `hello` arrives only after we answer the DSR as a terminal would, and EOF arrives only after the master is dropped.
- `RESULT Q1 execfail os=linux portable_pty_spawn=Ok portable_pty_child_status="exited:Terminated by Aborted after_ms=110" own_spawn=Err(No such file or directory (os error 2))` (ubuntu R2).
- `RESULT Q1 execfail os=macos portable_pty_spawn=Ok portable_pty_child_status="still-running-after-10s" own_spawn=Err(No such file or directory (os error 2))` (macos R1/R2).
- With portable-pty, a missing interpreter becomes a "successful" spawn followed by an abort. That would break our `NOT_FOUND`/`NOT_EXECUTABLE` error codes.
- On Unix, portable-pty's `kill()` sends SIGHUP and then SIGKILL to **one pid**, not to the tree (`lib.rs` 341–370).

Our own implementation passes every experiment below. It is about 180 lines for Unix (`own_unix.rs`) and about 320 lines for Windows (`own_win.rs`), including the experiment switches.

Unix fd hygiene (coordinator request: CLOEXEC/fd inventory):
- **Unix rule:** open the master with `open("/dev/ptmx", O_RDWR|O_NOCTTY|O_CLOEXEC)`, then `grantpt`/`unlockpt`/`ptsname`, then open the slave with `open(slave, O_RDWR|O_NOCTTY|O_CLOEXEC)`. This is atomic on both OS. `openpty()` followed by `fcntl` is not.
- In a 5 s fd race, the probe opens ptys while another thread spawns non-PTY children. Each child lists its tty fds of 3 or more.

| open strategy | macOS R1 | macOS R2 | Linux R1 | Linux R2 |
|---|---|---|---|---|
| `openpty` only (positive control) | 2889/2972 leaked | 1131/1273 | 5698/6231 | 9250/9730 |
| `openpty` + `fcntl(FD_CLOEXEC)` | **118/3116** | **56/1249** | **45/6431** | **76/10117** |
| `/dev/ptmx` + `O_CLOEXEC` | **0/3075** | **0/1329** | **0/6464** | **0/9995** |

- Example line (Linux R2): `RESULT Q1 fd-race os=linux open=OpenptyFcntl ... spawns_that_inherited_a_pty_fd=76 sample="3:tty,8:tty"`.
- The PTY child's own fds are clean (`RESULT Q1 fd-inventory os=linux pty_child="FDS 0:tty,1:tty,2:tty,3:-,142:-,145:-" leaked_tty_fds=[]`). However, it also received **non-tty fds 142 and 145 (Linux) and 131, 140, 143, 146 (macOS) that the probe inherited from the CI runner**. That is an S1 fd-hygiene issue; see Risks.
- On Windows, handles do not leak to the child: `bInheritHandles=FALSE`, and the PSEUDOCONSOLE attribute supplies the console.

### Q2: ConPTY EOF hang. Repro, correct sequence, 200/200, minimum build

**Repro (both hangs reproduced on both Windows builds, R2):**
- `RESULT Q2 naive-no-close os=windows ... hello_within_5s_after_exit_before_close=true ... eof_within_5s_after_exit_without_close=false close_ms=0.0487 eof_within_5s_after_close=true` (W26100; W20348 is the same with `close_ms=2.6921`).
  - The child has exited and all its output, including `hello`, has been read. **The read still never returns** until `ClosePseudoConsole` is called.
- `RESULT Q2 keep-parent-pipe-ends os=windows ... eof_within_5s_after_close=false ... eof_kind=none` (W26100 and W20348).
  - If the host keeps its own copy of the pty-side pipe ends (`out_w`/`in_r`), **EOF never arrives, even after close**. This is the root cause of wezterm #4718.

**Deterministic sequence.** It uses no silence timer. The only clock is the contract's `graceMs` deadline, which starts at a process-exit event. A short code sketch follows each OS list.

Windows (ConPTY):
1. Create two pipes with `CreatePipe`, then call `CreatePseudoConsole(size, in_r, out_w, flags=0, &hpc)`. **Close `in_r` and `out_w` immediately** (conhost keeps its own duplicates). Never pass `PSEUDOCONSOLE_INHERIT_CURSOR` (see Q1 `dsr_request=true`).
2. Call `CreateProcessW` with:
   - `bInheritHandles=FALSE`
   - `EXTENDED_STARTUPINFO_PRESENT`
   - **one** attribute list `{PSEUDOCONSOLE, JOB_LIST}` (see Q5)
   - `STARTF_USESTDHANDLES` with NULL or INVALID std handles (see Q6 stdh)
   - never `CREATE_NEW_PROCESS_GROUP` (see Q3)
3. A dedicated reader thread drains `out_r` from spawn until `ReadFile` returns 0 or `ERROR_BROKEN_PIPE`. **`ClosePseudoConsole` is never called on the reader thread.** (MS docs: before 24H2, `ClosePseudoConsole` "will wait indefinitely" if nobody drains.)
4. When the process handle is signalled (child exit), call `ClosePseudoConsole` from a non-reader thread. This hangs up the console: every remaining client gets `CTRL_CLOSE_EVENT`, and conhost flushes its final frame.
5. Read to EOF. Done.
6. If EOF has not arrived `graceMs` after the exit, a descendant is ignoring the hang-up. Call `TerminateJobObject`, and EOF follows.

```
reader thread: loop { ReadFile(out_r) ... } until 0 / ERROR_BROKEN_PIPE
main:          WaitForSingleObject(proc) -> ClosePseudoConsole(hpc) -> join reader
               [EOF not in graceMs] -> TerminateJobObject(job) -> join reader
```

Unix:
1. Open the pair as in Q1 (O_CLOEXEC). Spawn with stdio set to slave dups. In `pre_exec`, call `setsid()` and then `ioctl(0, TIOCSCTTY, 0)`. **Drop every parent copy of the slave**, including the ones `std::process::Command` owns (drop the `Command`).
2. Read the master until `read` returns 0 (macOS: `eof_kind=read0`) or `EIO` (Linux: `eof_kind=err5`). Both mean EOF.
3. After child exit (`waitpid`), EOF follows at once unless a descendant still holds the slave. Linux keeps the stream open while a descendant that ignores SIGHUP keeps writing. At `graceMs`, kill the tree (Q5 Unix: pgrp plus session sweep), and `EIO` follows.

### Q3: `"\x03"` interrupts the foreground program

| | result | evidence |
|---|---|---|
| Linux | 20/20 (R1, R2), p50 1.1 ms | `RESULT Q3 os=linux ... int_ok=20 ... ready="READY isig=true vintr=0x3 lflag=0x8a3b tcgetpgrp=3553 getpgrp=3553" first_output_after_ctrl_c="^CINT"` |
| macOS | 20/20 (R1, R2), p50 6.8–9 ms | `RESULT Q3 os=macos ... int_ok=20 ... isig=true vintr=0x3 ... first_output_after_ctrl_c="^CINT"` |
| Windows, default | **0/20** on 26100 and 20348 (R1, R2) | `RESULT Q3 os=windows newpg=false child_reset=false host_reset=false iters=20 int_ok=0 noint=20 ... ready="READY inmode=0x1f7"` |
| Windows, child clears flag | 20/20 on both builds (R2) | `RESULT Q3 os=windows newpg=false child_reset=true ... int_ok=20 ... latency_ms_p50=13.4` (W26100); `... latency_ms_p50=18.3` (W20348) |
| Windows, **host clears flag before spawn** | **20/20** on both builds (R2) | `RESULT Q3 os=windows newpg=false child_reset=false host_reset=true iters=20 int_ok=20 ... latency_ms_p50=13.4 max=16.2` (W26100); `... p50=18.9 max=21.4` (W20348) |
| Windows, `CREATE_NEW_PROCESS_GROUP` | 0/5 | `RESULT Q3 os=windows newpg=true ... int_ok=0` |

ConPTY does translate `0x03` into `CTRL_C_EVENT`. The child's console input mode `0x1f7` has `ENABLE_PROCESSED_INPUT` set. The child ignored it because it **inherited the per-process "ignore CTRL+C" flag** from the CI process chain. `SetConsoleCtrlHandler(NULL, TRUE)` and `CREATE_NEW_PROCESS_GROUP` set that flag, and it passes to children.

**Decision:**
- Unix: write `0x03` to the master. ISIG is on by default and the child is the foreground pgrp after `setsid`+`TIOCSCTTY`.
- Windows:
  - never create PTY children with `CREATE_NEW_PROCESS_GROUP`;
  - clear the inherited flag for the PTY child with `SetConsoleCtrlHandler(NULL, FALSE)` in the host before `CreateProcessW` (proven 20/20). This is process-global; see Risks.
- Unix echoes `^C` into the output (ECHOCTL). ConPTY does not.

### Q5: ConPTY child inside a Job with no race

One attribute list holds both `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` (value = `HPCON`) and `PROC_THREAD_ATTRIBUTE_JOB_LIST` (value = `HANDLE[1]`). The helper spawns a grandchild as its very first instruction:
- `RESULT Q5 win-job os=windows mode=joblist iters=100 child_in_job=100 grandchild_in_job=100 grandchild_dead_after_TerminateJobObject=100 eof_after_kill_and_close=100 close_ms_max=0.2` (W26100 R2)
- Same result on W20348 R2 (`close_ms_max=1.8`) and in R1.

Control modes:
- `suspended` (CREATE_SUSPENDED → Assign → Resume, processkit's order) also got 100/100.
- `racy` (CreateProcess, then Assign) **also got 100/100 on all 4 Windows jobs**. The startup race is real by construction but too narrow to observe: the child takes milliseconds to start, and the assign takes microseconds.
- So the evidence for JOB_LIST is not a measured escape. It rests on two points:
  1. The kernel creates the process inside the job, so there is no instant at which a crash of the host leaves a child (a suspended one, in the SUSPENDED order) outside the Job.
  2. It is one call with no thread-resume bookkeeping.
- JOB_LIST needs Windows 10 / Server 2016 (UpdateProcThreadAttribute docs), which is below ConPTY's 1809 minimum.

Unix analogue: the grandchild is in the child's pgrp and session 100/100, and `killpg` kills it 100/100 (`RESULT Q5 unix-pgrp os=linux iters=100 gc_same_pgid=100 gc_same_sid=100 gc_dead_after_killpg=100 eof_after_kill=100`; same on macOS).

**However, `killpg` is not enough for a PTY:**
- An interactive job-control shell moves each job into its own pgrp.
- `RESULT Q5 unix-jobctl os=linux ... session_members(pid,pgid)=[(3940, 3940), (3943, 3943), (3944, 3944)] survivors_after_killpg=[3943] bg_alive_after_killpg=true eof_after_killpg=false survivors_after_session_sweep=[] eof_after_sweep=true` (ubuntu R2; on macOS the background job also survives `killpg`, but EOF still arrives because the tty is revoked: `eof_after_killpg=true`).
- A background job survives `killpg(child)` and keeps the stream open on Linux. A session sweep (SIGKILL every pid whose `getsid == child pid`) kills it.

### Q6: Output noise, raw samples and the matcher

Raw bytes of `helper hello` (`print!("hello\n")`, Rust std) through the correct sequence. Escaping: `\e`=ESC, `\r`, `\n`, `\xNN`.

| OS | raw (from `RESULT Q6 os=... mode=hello ... raw="..."`) |
|---|---|
| Linux (ubuntu-24.04) | `hello\r\n` |
| macOS (macos-26-arm64) | `hello\r\n` |
| Windows 26100 | `\e[?9001h\e[?1004h\e[?25l\e[2J\e[m\e[Hhello\r\n\e]0;D:\\a\\hugr-omni\\hugr-omni\\spikes\\pty\\target\\release\\helper.exe\x07\e[?25h\e[?9001l\e[?1004l` |
| Windows 20348 | `\e[2J\e[m\e[Hhello\r\n\e]0;D:\\a\\hugr-omni\\hugr-omni\\spikes\\pty\\target\\release\\helper.exe\x07\e[?25h` |
| Windows, portable-pty (INHERIT_CURSOR) 26100 | `\e[6n\e[?9001h\e[?1004h\e[m\e]0;D:\\...\\helper.exe\x07\e[?25hhello\r\n\e[?9001l\e[?1004l` |

What the noise is:
- ONLCR turns `\n` into `\r\n` everywhere.
- ConPTY adds:
  - win32-input-mode and focus-event DECSET/DECRST (`?9001`, `?1004`; 24H2 only)
  - cursor hide/show (`?25`)
  - ED 2 (`2J`), SGR 0 (`m`), CUP home (`H`)
  - OSC 0 window title = the child's image path
- The UTF-8 sample `h\xc3\xa9llo \xe2\x9c\x93 \xe6\x97\xa5\xe6\x9c\xac\r\n` passes through unchanged on all OS (`mode=utf8 ... match=true`).

**Normative matcher** (`spikes/pty/src/stream.rs`, `visible()` + `normalize()`):
1. Feed the raw bytes to a `vte` 0.15 `Parser`.
2. `print(c)` → append `c`. Execute `LF` → `\n`. `TAB` is kept. `CR` and every other C0 is dropped.
3. CSI `H`/`f` (CUP) to a row greater than the current row → that many `\n` (ConPTY may position instead of sending LF). CSI `C` (CUF n) → n spaces. Every other CSI/OSC/ESC/DCS is dropped.
4. Then trim trailing whitespace per line, drop leading and trailing empty lines, and end with a single `\n`.

Under this matcher, all captures equal `"hello\n"`: `RESULT Q6 ... match=true norm="hello\n"` on all 4 jobs × 2 runs, and the UTF-8 sample also matches on all. An equivalent byte regex is enough for the samples above: delete `\x1b\[[0-?]*[ -/]*[@-~]`, `\x1b\][^\x07\x1b]*(\x07|\x1b\\)`, `\x1b[@-Z\\-_]` and `\r`. It is **not** normative, because it cannot map CUP/CUF to text.

Std-handle variants (this is a correctness rule, not noise) while the host's stdout is a pipe:
- `RESULT Q6 stdh variant=Unset hello_in_pty=false` (the Microsoft sample, with no `STARTF_USESTDHANDLES`). The child's `hello` went **to the host's redirected stdout**: it shows up as a bare `hello` line in the job log right before that RESULT line.
- `variant=Invalid hello_in_pty=true` and `variant=Null hello_in_pty=true` on both builds and both runs.

## Decision

1. **Build our own PTY layer.** Do not depend on portable-pty or processkit.
   - Unix: atomic `/dev/ptmx` with `O_CLOEXEC`, then `grantpt`/`unlockpt`/`ptsname`, then the slave opened with `O_CLOEXEC`, then `TIOCSWINSZ`. Spawn with `pre_exec{setsid; TIOCSCTTY}` and drop all parent slave copies.
   - Windows: ConPTY via `windows-sys`, with the rules in Q2 step 1–2 (flags=0, close the pty-side pipe ends, `STARTF_USESTDHANDLES`+NULL, one attribute list `{PSEUDOCONSOLE, JOB_LIST}`, `bInheritHandles=FALSE`, no `CREATE_NEW_PROCESS_GROUP`, clear the inherited ignore-CTRL+C flag).
2. **EOF is event-driven:**
   - a reader that drains from spawn (Windows: its own thread, never the closer);
   - on child exit, Windows calls `ClosePseudoConsole` (a hang-up) and Unix does nothing;
   - read to EOF/EIO;
   - if there is no EOF within `graceMs` of the exit, kill the tree, and EOF follows.
   - There is no silence heuristic anywhere.
3. **Tree kill for PTY children:**
   - Windows uses the same Job as non-PTY children (JOB_LIST).
   - Unix needs **pgrp + session sweep**, because the PTY child is a session leader and job-control shells create new pgrps.
4. **Interrupt** is `write("\x03")` on all OS. The Windows part depends on decision 1's flag clearing.
5. **Output comparison** across OS uses the vte normalizer in Q6. Bytes are never compared.

## Rejected alternatives

- **portable-pty 0.9.0 / master.** There is no JOB_LIST and no suspended spawn. It hard-codes `INHERIT_CURSOR`, so a headless host never gets output until it answers the DSR. ClosePseudoConsole runs only via `Drop`. Unix exec failure returns Ok and the child aborts. Unix `kill()` is pid-only. It has not had a release in 20 months.
- **processkit** (G0 option B; it also has the defects the coordinator listed, three of which these experiments confirm independently):
  - non-CLOEXEC pty: openpty+fcntl leaks;
  - silence-timer EOF: `delayed`/`descendant`;
  - SUSPENDED order.
- **Silence-timer EOF.** It cuts the delayed final frame and never terminates while a descendant writes.
- **Naive "wait for exit, then read to EOF" without `ClosePseudoConsole`.** It hangs forever on 20348 and 26100.
- **Keeping the host's copies of `in_r`/`out_w`.** EOF never comes, even after close.
- **`ClosePseudoConsole` on the reader thread.** Documented deadlock before 24H2. Not reproduced, because the design never does it.
- **`CREATE_SUSPENDED` → `AssignProcessToJobObject` → `ResumeThread`.** It works 100/100, but leaves a crash window with a suspended child outside the Job and needs extra steps. **Post-hoc assign** is racy by construction (escapes were not observable, 0/100).
- **`openpty()` + `fcntl(FD_CLOEXEC)`.** It leaks pty fds to concurrent spawns (45–118 per 5 s).
- **STARTUPINFO without `STARTF_USESTDHANDLES`.** The child writes to the host's stdout instead of the PTY.
- **`killpg` alone on Unix.** Job-control background jobs survive.
- **Closing all fds in `pre_exec`** (portable-pty `close_random_fds`). It breaks exec-error reporting. Mark them CLOEXEC instead.
- **Sideloading `conpty.dll` + `OpenConsole.exe`** (Microsoft.Windows.Console.ConPTY, as wezterm does). Deferred: it is a packaging cost. It is the likely fix for the 20348 handle leak if K6 must hold there.

## Consequences for the contract

These are the rows the frozen `pty` seam and GUARANTEES must carry:

- **Seam (`pty/` module, shared by W12 and W12w):** `open(size) -> Pty`, `spawn(argv, env, cwd, pty, job_or_pgid_slot) -> PtyChild {pid, write(bytes), resize(cols, rows), output: one byte stream, wait, hangup(), kill_tree()}`.
  - A PTY has **no separate stderr**: `RunResult.stderr` is empty in PTY mode.
  - The Windows child must be created inside the caller's Job through the same attribute list. The seam takes the Job handle as a spawn input; it does not assign afterwards.
- **GUARANTEES: output.** "In PTY mode, `output` is the terminal's byte stream. On Unix that is the child's bytes after ONLCR plus the echo of written input (e.g. `^C`). On Windows it is ConPTY's re-rendered VT stream (DECSET 9001/1004/25, ED, CUP, OSC title). Text is equal across OS only after the documented VT normalization. Byte equality is not promised." Contract tests for `pty` compare normalized text.
- **GUARANTEES: end of stream / K5.** "The PTY stream ends after the child exits. If no descendant holds the terminal, it ends at once. Otherwise descendants are hung up (Windows `CTRL_CLOSE`, Unix SIGHUP at session-leader exit) and those still alive at `graceMs` are killed. Every byte the child wrote before exiting is delivered." Do **not** promise descendant output after the root exits: macOS revokes the tty immediately, Linux keeps it, and Windows gives about 5 s.
- **GUARANTEES: kill / INV-04.** "`kill()` on a PTY child: Windows uses the same Job as non-PTY children. Unix uses the child's process group plus every process in its session." The brief's "same process-group model" holds only on Windows. The PTY graceful step is a **hang-up** (`ClosePseudoConsole` / SIGHUP to the session), not CTRL_BREAK/SIGTERM, before the force step at `graceMs`.
- **GUARANTEES: interrupt and resize.**
  - "`write("\x03")` interrupts the foreground program on Linux, macOS and Windows (Windows: hugr-omni clears the inherited ignore-CTRL+C flag for PTY children)."
  - "`resize` is observed by the child. Latency is not guaranteed (measured ≤ 24 ms on CI)."
- **Platform floor:** Windows 10 1809 / Server 2019 is the documented floor, and the GUARANTEES must list tested builds (20348, 26100). Builds before 26100 leak one handle per PTY session (K6). The lead must choose: declare the leak and scope K6 on Windows to 26100+, or ship `conpty.dll`.
- **W12w should stay its own WP.**
  - Its failure modes are Windows-only and only show up in Windows CI: EOF/close ordering, DSR, std handles, the Ctrl-C flag, VT noise, the 20348 handle leak, and close blocking before 24H2.
  - Its write-set (`pty/windows.rs`) is disjoint from W12's (`pty/unix.rs` plus integration).
  - It depends on W06 (Job) and on the frozen seam above.
  - Its acceptance checklist is the Windows rules in Decision 1–2 plus the Q2/Q3/Q5/Q6 experiments as contract items.

## Open risks

- **20348 handle leak (1 per pseudoconsole).** The leaked handle type was not identified, and 17763, 19045 and 22631 were not tested. K6/K8 on Windows Server 2022 and on Windows 10/11 before 24H2 are at risk.
- **Ctrl-C flag clearing is process-global** (`SetConsoleCtrlHandler(NULL, FALSE)` in the host). It changes the host's own Ctrl+C behaviour if the host has a console. Restoring the flag after spawn needs the undocumented `RTL_USER_PROCESS_PARAMETERS.ConsoleFlags` read. W12w must decide between toggle-under-spawn-lock and leaving it cleared, and must test it.
- **Escaped Unix descendants.** A process that calls `setsid()` and keeps the slave open escapes both pgrp and session sweep, so EOF never comes. The reader must be poll-based with a wake fd, so the master can be dropped at `graceMs`. Untested. Overlaps S1 (cgroup/subreaper).
- **Host-inherited non-CLOEXEC fds reach PTY children** (macOS CI 131, 140, 143, 146; Linux 142, 145). S1 must define child fd hygiene: in `pre_exec`, mark fds ≥ 3 CLOEXEC (`close_range(3, ~0, CLOSE_RANGE_CLOEXEC)` on Linux ≥ 5.11, an `fcntl` loop otherwise). Do not close them.
- **ConPTY is a renderer, not a pipe.** 2000-line bursts at 80×24 lost nothing on either build. Not tested: lines wider than `cols` (wrap), full-screen apps, resize during output (reflow), and children that write raw non-UTF-8 bytes under a non-65001 code page.
- **Windows stubborn descendants:** without our kill, Windows terminates them about 5 s after `CTRL_CLOSE`. A `graceMs` above 5 s therefore makes no difference.
- **24H2 emits `?9001h`** (it asks the terminal for win32-input-mode). Plain VT input (`0x03`, text) works today. A future ConPTY could change input handling.
- **conhost/OpenConsole is the host's child and is not in the Job.** What happens to it when the host crashes was not tested.
- **Linux `stubborn-kill`:** in R1 `gc_dead_at_eof_check` was 49/50. EOF was 50/50 and the descendant was gone within 2 s in R2 (50/50). This is probably a reaping lag on the runner and was not investigated.
