# Compare on a common decision basis

Read for alternative selection, claim validation against a baseline, feasibility comparison or material differences. Do not rank a field before criteria exist; explore it first. A one-clause truth check can use [simple fact](simple-fact.md).

## Inputs and discriminating questions

Use the question/claim, current solution, candidate versions, concrete requirements, scenario and permitted sources/observations. Ask: which requirements eliminate a candidate, which trade-off could change the choice, and what evidence would make the candidates comparable? Ask Maestro for a missing decisive preference only after identifying the actual trade-off.

## Procedure

1. Include the current baseline and the option of no change where relevant. Fix common criteria from the decision: correctness/compatibility, resources, operational burden, integration, licensing or supported environment only when material. Do not invent a generic weighted score.
2. For claim validation, extract the claim's precise scope and predicted consequence, then locate applicable support and a material counterexample. A validated narrow claim is not universal endorsement.
3. Capture each candidate's actual version and evidence under comparable conditions. Distinguish documented feature, source implementation, observation and vendor assertion. A strongest headline from different benchmarks/settings does not form one ranking.
4. Build only material cells: applicable finding, conditions and citation. Mark “not examined”, “not addressed”, “unavailable”, “contradicted” and “supported” distinctly. An empty cell is not missing functionality.
5. Explain decisive differences and transfer costs. For empirical comparisons, read [study reading](../references/study-reading.md) and include setup/indexing/retries where evidence supplies them. If conditions cannot be aligned, state incomparability instead of interpolating results.
6. Recommend conditionally, retain the baseline, or specify the smallest discriminating proof. A winner is unnecessary when evidence/preferences do not decide it.

## Capabilities and failure

Use permitted primary-source acquisition, verified Own, native findings/relations/documents and supplied observation receipts. Do not install candidates, run arbitrary benchmarks, change product/config or delegate. A proposed test goes to Maestro's qualified executor with exact conditions and contrary outcomes.

Return acquisition failure or access/verification hold verbatim, preserving which criterion remains unknown. Do not drop a candidate because its source is unavailable or call unknown evidence a negative. Use shared [corpus](../../jimmy-discovery/references/corpus.md) when the matrix must remain revisable.

## Writing and closure

Use profile `evaluate` for a concrete decision/claim; omit modality there. Research comparison uses profile `research`, modality `comparative`. Genre is `comparison`; follow [comparison writing](../writing/comparison.md).

Lead with the conditional decision and decisive qualifier, then explain criteria and actual baseline. The matrix supports an argument; it is not the entire answer. Stop when decisive requirements/trade-offs are supported, essential comparison evidence is unavailable or effort ends. Close with conditions, unknowns and precise next work, not an unsupported score or architecture approval.
