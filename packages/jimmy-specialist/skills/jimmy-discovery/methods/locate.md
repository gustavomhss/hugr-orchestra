# Locate the effective entry

Read when selecting profile `locate`: finding implementation, registration/selection, origin or consumers. Do not use location alone to explain an entire journey, prove production activation or diagnose cause; switch to [understand](understand.md) or [investigate](investigate.md) for those questions.

## Inputs and discriminators

Use the requested behavior/symbol/error/route, bound repository revision, scenario and available config/build facts. A partial name is a valid starting point. Ask: does the recipient need a declaration, the selected body, the upstream origin or all examined consumers? Which import condition, provider or runtime could change selection?

## Procedure

1. Find candidates with exact text/path search. If the territory is unknown, inspect nearby module responsibilities and signatures, then open only relevant bodies. Keep excluded candidates recoverable.
2. **Implementation:** resolve the caller's symbol through imports, aliases, exports, wrappers and overloads to a body. Use configured LSP/compiler services with readiness/coverage; use explicit static derivation when semantic resolution is unavailable. Read [identity](../references/identity.md) for ambiguous selection.
3. **Registration/selection:** follow the registration key and selector to the bootstrap/config branch. Distinguish installed, registered, selectable and selected. A no-op provider or alternative export may be legitimate; inspect the actual selection condition rather than choosing the most plausible filename.
4. **Origin:** trace wrappers/generated output to authoritative implementation, schema/generator input or upstream revision. Read [version/config/build](../references/version-config-build.md) when the effective bytes depend on generation or packaging. Do not treat generated declarations as behavior.
5. **Consumers:** follow resolved references and witnessed dynamic boundaries, not only matching spellings. Inspect event names, queue contracts, serialization and configuration when they connect otherwise separate files. A candidate list needs reasons explaining relevance.
6. Capture the decisive entry and selector/origin witnesses through admitted acquisition. Record an independently addressable finding only when linkage/revision/reuse warrants it; [evidence](../references/evidence.md) applies even to a short answer.

## Capability and failure boundaries

Use read/grep/glob, exposed LSP/compiler operations, verified Own and specialized read-only history where relevant. No engine installation, arbitrary commands, product edits or delegation. If selection depends on unavailable runtime/build facts, return the located static candidate and exact missing discriminator. If a permission or verification hold denies access, preserve it verbatim without another route around it.

Before claiming “no consumers”, retrieve a known positive reference with the same operation and declare scope, exclusions and failures. A successful control does not turn partial semantic support into complete coverage.

## Output and closure

Use [answer](../../jimmy-research/writing/answer.md) for one entry; [map](../../jimmy-research/writing/map.md) for several connected origins/consumers. Explain where to start, why this entry is applicable, which boundary must be preserved and whether selection is static or observed. Give exact admitted evidence rather than a large unqualified file list.

Stop when the recipient can begin at the correct entry under stated conditions. If runtime selection or a dynamic consumer remains essential and unavailable, close partial/blocked with the smallest next observation and qualified executor using [closure](../references/closure.md).
