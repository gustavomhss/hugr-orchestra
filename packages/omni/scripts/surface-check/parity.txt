# The parity map (C-PAR-01): which public item of each language belongs to which concept of the glossary
# (docs/api-contract.md §2). `parity.mjs` reads the glossary, `bindings/node/index.d.ts` and the core crate's public
# API, and fails when any of them and this file disagree, in either direction.
#
# [parity] rows:  <concept> | <TypeScript items> | <Rust items>
#   - the concept is spelled exactly as in the glossary; every glossary concept has exactly one row;
#   - every public item of each language appears in exactly one row; a name that does not exist is an error;
#   - TypeScript items: `run`, `Type`, `Type.member`, `Type.member.nested`;
#   - Rust items: `Type`, `Type.field`, `Type::method`;
#   - a line that starts with a space continues the row above.
# Adding a capability to one language means adding it here, which means placing it in a concept, which means
# adding it to the other language too (INV-02): the check refuses a row with nothing on one side.
# Python joins in v0.2 as a third column.
# Declared limit: the rows place capabilities (functions, options, fields, types). The values inside a type, Rust enum
# variants and TypeScript string-literal unions (error codes, `reason`, `stream`, `stdin`), are not compared across
# languages: full C-PAR-01 is v0.2.
#
# [excluded]: words that name a capability the project decided against. No public item of any language, and no
# glossary concept, may carry one of these words in its name (`<word> | where it was decided`).

[excluded]
shell | INV-03 (PLAN §4.3): no shell, ever
kill | PLAN §3: `stop()` ends the tree, there is no `kill()`
sandbox | PLAN phases 2-3: arrives with SANDBOX_UNAVAILABLE, not in v0.1 (docs/api-contract.md §11)
label | PLAN Apêndice E, `processes()` decision: no agent or session label
