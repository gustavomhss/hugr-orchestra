## Options

- **A — Build the TS package on processkit.** Fastest start, but we would replace its I/O, timers, exit reasons, host-exit handling and (under Node/Bun) its wait mechanism, keep an 86k-line, fast-churning dependency, and need upstream fixes for the ConPTY path.
- **B — Own lean core, TypeScript first (lead's recommendation).** Rust core written to our contract and module rules, reusing the techniques processkit proved (suspended child → Job → resume on Windows; cgroup v2 when delegated; process group otherwise; per-child blocking `waitpid` or pidfd for exits). Python and Rust packages follow on the same core when the Owner decides. Everything we promise is ours to fix.
- **C — Stop.** Point TS users at execa + node-pty and contribute to processkit.

## Recommendation

**Go with B.** The measured value left in processkit after our adapter is the Windows Job/ConPTY setup and Linux cgroup setup, which is a small part of a lean core. Depending on it costs us control over the exact promises we sell (no lost output, no hangs, safe Windows arguments) and adds a known hang inside Node/Bun.

Before any Phase 1 dispatch:
1. **Owner:** unlock GitHub Actions billing for HuGR-Labs (or move the repo). Nothing on Windows can be proven otherwise.
2. **Lead:** resume S1/S2 on Windows CI (they answer exactly the Windows questions B needs), then freeze the contract (W00) after your API approval (D5).
