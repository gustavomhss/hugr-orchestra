## Purpose and responsibility

The component separates durable Session input admission from process-local execution coordination. Admission records work and its identity; execution coordination decides whether this process starts, joins, or coalesces work. Those responsibilities have different scopes: the owner contract assigns `SessionExecution` process-global, Session-ID-based coordination, while runner, model, tools, permissions, and filesystem are Location-scoped. Placement is discovered at drain start through the Session and its Location. These are owner constraints, not proof that the supplied implementation excerpts enforce the full routing contract. ## Contract and state model

**Intended contract.** A prompt is admitted before execution is requested. `resume: false` means admission without a wake; otherwise the facade requests a wake. The specification distinguishes explicit `run`, which starts or joins and can force a drain past the no-eligible-input guard, from advisory `wake`, which coalesces and calls the provider only when eligible input can be promoted. A wake is therefore not an execution receipt. [L1:authority#Evidence register @ 82d5d832e8ded04256460acf8296edc21b19121a3cda5047b58416ffe82210db; `docs/specs/v2/session.md:3-50 @ c9b8e54cbf2c6c2c4bb59bbda2dc878430a54085`; `docs/specs/v2/session.md:155-185 @ c9b8e54cbf2c6c2c4bb59bbda2dc878430a54085`]

The intended delivery boundary is also distinct from execution: admitted input is outside model-visible history until `Prompted` projection promotes it. `steer` promotes at a safe provider-turn boundary; `queue` remains FIFO while continuation is required and promotes one item when otherwise idle. [L1:authority#Evidence register @ 82d5d832e8ded04256460acf8296edc21b19121a3cda5047b58416ffe82210db; `docs/specs/v2/session.md:3-50 @ c9b8e54cbf2c6c2c4bb59bbda2dc878430a54085`; `docs/specs/v2/session.md:155-185 @ c9b8e54cbf2c6c2c4bb59bbda2dc878430a54085`]

**Observed implementation.** The facade defaults delivery to `steer`, invokes admission, checks the returned admission against the expected identity/content, and calls `execution.wake(admitted.sessionID)` unless `resume === false`. In the supplied coordinator excerpt, `run` joins an existing entry (waiting and retrying if it is stopping) or starts an explicit-run drain. `wake` marks an active entry for a follow-up and returns, or creates an entry and starts a wake drain. The excerpt passes `true` for explicit run and `false` for wake; the drain’s interpretation of that argument is not supplied. ## Conditions and failure boundaries

The coordinator’s `active` map is runtime state. The execution interface describes `active()` as a snapshot of work owned by this process; the owner contract likewise excludes background subagents and tasks. An active observation can describe this process’s registered foreground execution, not durable ownership, work on another process, or complete system activity. After restart, the intended contract says the registry is empty; it does not resolve whether an interrupted provider attempt completed or what usage it incurred. The interface describes interruption as process-local, waiting for cleanup, and a no-op when idle. The specification says interruption preserves inbox rows and clears coalesced wake state. These are contract statements; the supplied coordinator excerpt does not include stop/cleanup internals or prove those effects at runtime. Post-crash recovery is explicitly deferred: neither wake nor an active observation establishes safe replay. ## Change impact and verification

A change to Session-ID routing or coordinator keying affects which process-local coordination responsibility handles a Session; a change to runner selection affects Location-scoped execution. A change to `run` or `wake` branches can alter whether a caller joins, starts, or coalesces work. A change to drain eligibility, promotion, or pending-wake consumption can affect whether admitted inputs become visible and when execution is requested. These consequences follow from the declared contract and observed branch points; the excerpts do not establish full end-to-end behavior. The supplied test definitions assert admission before transcript promotion, exact-retry and conflict behavior, selected concurrent retry/steer-promotion and cutoff cases, legacy projection/global ID behavior, and fixture-level wake selection. In particular, the wake fixture asserts default and `resume: true` request wake without direct execution calls, while `resume: false` records without wake.
