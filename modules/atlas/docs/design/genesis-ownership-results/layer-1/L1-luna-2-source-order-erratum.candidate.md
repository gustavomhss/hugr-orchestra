## Reuse and conflicts

Observed selector behavior is conditional: the drain selects steer ahead of queue; a requested queue promotion promotes at most one eligible queue row, then eligible steers through the captured cutoff. Steer promotion selects all matching unpromoted steers through that cutoff in admission order. These are implementation facts, not an owner-stated delivery guarantee. The location check and `governance.beforeTurn` occur before promotion, so interruption or refusal at those checks can leave pending input unpromoted. (`packages/core/src/session/input.ts:348-391` and `packages/core/src/session/runner/llm.ts:185-213,616-642 @ c9b8e54cbf2c6c2c4bb59bbda2dc878430a54085`.)

The observed allowance-related behavior in the supplied ranges is the `currentStep` counter: it is reset to 1 if promotion count is positive, and `isLastStep` compares it with the agent step setting or `DEFAULT_MAX_STEPS`. At the last step, the default provider-model path appends `MAX_STEPS_PROMPT` to the `toLLMMessages(context, model)` array before passing that array to `compaction.transform`, and sets `toolChoice: "none"` on the request; non-last steps prepare/materialize tools. This does not establish a broader product-intended allowance policy or runtime guarantee. (`llm.ts:205-215,244-259,267-270 @ c9b8e54cbf2c6c2c4bb59bbda2dc878430a54085`.)

For the default LLM request path, history entries after the system baseline are mapped to messages, converted with `toLLMMessages`, and passed through `compaction.transform`; request construction uses the resulting messages. `llm.stream(request)` is selected when a request exists. This establishes source-level transformation, not that a particular admitted prompt was included in a particular request or that the request completed. The supplied ranges do not establish every compaction/recovery outcome. Hosted-engine execution is outside this account. (`llm.ts:229-239,251-272,427-429 @ c9b8e54cbf2c6c2c4bb59bbda2dc878430a54085`.)
