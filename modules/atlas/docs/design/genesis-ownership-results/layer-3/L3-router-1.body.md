## Integrated responsibility
The supported product job is to make a caller-supplied prompt durably acknowledged, later visible, and only then potentially part of a provider request, without conflating those three states. Admission owns identity, receipt, and retry reconciliation and advises execution; it does not execute a provider call (E-AD lines 13-17). Persistence/projection owns the `session_input` row, `admittedSeq`/`promotedSeq` carriers, and the `PromptAdmitted`/`Prompted` projection writes that move a row from pending to promoted; it does not own drain or provider execution (E-PJ lines 10-14, 23-27). Delivery owns eligibility of pending steers and queues at a provider-turn boundary; eligibility does not prove a provider request occurs or succeeds (E-DL lines 12-14). Execution coordination owns only process-local start/join/coalesce decisions for a Session; it does not own durable admission, promotion, or cross-process ownership (E-EC lines 10-18). *Interpretation:* the maintainer-critical separation is durable receipt → promoted/visible state → process-local execution advisory → provider-turn request, in that order, with each later stage conditional on the earlier one.

## Integrated model
Three receipt paths converge on the same receipt vocabulary but preserve different provenance, so a receipt need not entail a new `PromptAdmitted` event. Fresh admission normalizes identity (`input.id ?? generated`, delivery default `steer`), admits, re-checks `equivalent`, and only then wakes unless `resume:false` (E-AD lines 20-24; E-PJ lines 16-19). Exact retry looks up by ID and returns the stored record only if `equivalent` — delivery plus session/prompt, *not* context/time/sequence — holds; changed prompt/delivery or global ID reuse conflicts (E-AD lines 26, 39-40; E-PJ lines 32-36). Historical reconciliation, when no row exists, requires a durable `Prompted` event, rechecks in an immediate transaction, and derives delivery from original event provenance (projections omit it), synthesizing an already-promoted row with historical sequence for both carriers; it does not publish a new admission (E-AD lines 28, 41-42; E-PJ lines 38-40). Pending means `admitted_seq` set and `promoted_seq` null; promoted means `Prompted` writes `promotedSeq` and calls `run`; admitted input is outside model-visible history until promotion (E-PJ lines 23-26; E-AD lines 30-32). Projection matching is stricter than retry equivalence — it adds prompt-context and epoch-millis time equality, plus promoted-sequence equality on the existing-row path — and the `projectPrompted` update predicate alone is not the safety gate (E-AD lines 30, 36; E-PJ lines 34, 40).

Caller and execution semantics compose conditionally. `resume:false` admits only: it suppresses *this call's* wake, not eligibility to an already-active drain and not other scheduling (E-AD line 43; E-EC line 14). Default/`resume:true` calls `execution.wake(sessionID)`: if an entry is active, `wake` sets `pendingWake` and returns (coalesced follow-up, no new work started); if idle, it creates an entry and starts `drain(key,false)`; explicit `run` instead joins or starts `drain(key,true)` and awaits `done` (E-AD line 34; E-EC lines 18-20). Neither wake branch proves provider completion (E-AD lines 34, 42). In the drain, steers and queues have *different* predicates: eligible steers are unpromoted rows with `admitted_seq <= cutoff` (latest event sequence captured for the turn), ordered by admission; queue selection chooses the earliest unpromoted queue row without the steer cutoff, promotes at most one queue row, then eligible steers (E-DL lines 20-22). Pre-promotion checks (session-location mismatch, `governance.beforeTurn`) can leave a row pending on that attempt (E-DL line 26). At the request boundary, intended policy says promoting new user input resets the selected agent's provider-turn allowance (a steer batch once), while observed code resets `currentStep` to 1 only if at least one row was promoted and compares against configured/`DEFAULT_MAX_STEPS`; at the last step the default provider-model path appends `MAX_STEPS_PROMPT` *before* `compaction.transform` (E-DL lines 26-28). Intended reset and observed counter behavior are separate claims; last-step insertion precedes transformation as separate observed ordering.

## Consequences and boundaries
An acknowledged-but-not-yet-visible input is a normal intermediate state, not provider failure: pending is not evidence of provider failure, and promotion publication suppresses `LifecycleConflict` only when the stored row already has `promotedSeq`, otherwise it dies (E-DL lines 18, 30). A durable receipt, visibility, and an execution/provider result are three distinct claims; a receipt alone guarantees none of new execution, promotion, model-visible history, wake-drain completion, or provider completion (E-AD line 42; E-EC lines 14, 36). Changing `equivalent` widens/narrows retry acceptance opposite to changing `matchesProjection`; changing the `steer` default, ID generation, or `resume !== false` condition changes which rows become eligible for wake and promotion; changing cutoff, selector ordering, or the one-row queue limit changes which pending rows can promote in a turn (E-AD lines 47-51; E-PJ lines 45-49; E-DL line 34). Non-guarantees remain explicit: provider-level exactly-once, crash-safety/cross-process serialization, post-crash recovery, hosted/distributed execution, and concurrent projection outcomes are not established; `active()` is a process-local snapshot, empty after restart, and does not resolve whether an interrupted provider attempt completed or what usage it incurred (E-PJ line 42; E-EC lines 24-28; E-AD line 55). Supported scope is the default LLM runner only.

## Verification and evidence limits
Supplied test definitions assert: admission before transcript promotion, exact-retry/conflict behavior, concurrent exact retry and concurrent steer promotion with cutoff exclusion of a later steer, legacy projection/global-ID cases, and wake selection (default/`resume:true` wake without direct execution calls in the fixture vs. `resume:false` no wake) (E-AD lines 47-52; E-PJ line 47; E-DL line 36; E-EC line 34). These are definitions, not execution receipts: no execution receipt is supplied for any row, and concurrent queue behavior, provider-request inclusion of a specific input, crash/interleaving behavior, and end-to-end completion are unproven (E-AD line 52; E-DL line 36; E-EC lines 34-36). A hypothetical behavior change is not proof that a specific test fails; cite only its actual supplied assertions — e.g., narrowing `equivalent` to add context/time would change retry semantics, but no supplied assertion establishes that such a narrowed predicate fails a named test (E-AD line 48). Missing evidence from one original L1 seat is not globally missing when supplied in the accepted L2 closure; remaining genuinely unavailable premises are drain/`start`/`stop`/`makeEntry` bodies, `run(db,event)` internals, `execution.wake` routing implementation, atomicity/sequence-allocation proof, and any runtime/execution receipt (E-AD line 55; E-PJ lines 51, 61; E-EC lines 42-47).
