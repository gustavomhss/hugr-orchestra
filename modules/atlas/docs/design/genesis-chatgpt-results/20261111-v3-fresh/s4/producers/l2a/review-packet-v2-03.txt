## How current inputs are observed

**Observed:** the host observer accepts only `file:<relative-path>` and `members:<relative-directory>`. It refuses empty paths, backslashes, absolute/drive paths, empty path segments, `.`/`..`, and `.git`/`.atlas` segments. It resolves the repository root, checks containment, and refuses symlink/non-directory ancestors and unsuitable targets. Root resolution itself does not establish a valid Git checkout or its HEAD. [I:31-46,71-110,143-155; R:34-39]

| Observation or situation | What it establishes | What a maintainer must preserve |
| --- | --- | --- |
| `present(version)` | A version from the actual bytes or effective membership read. | Compare with the receipt's recorded version; retain the key and both versions when diagnosing change. [I:141,182; T:50-56] |
| `absent` | A negative lookup corroborated by successful enumeration of an ancestor checked to be a directory; its inode must match before/after enumeration. | It is evidence of missing input, not unchanged content. A removal can affect dependents. [I:50-68,99-109,143-150; C:55] |
| `unavailable` | Invalid/refused key or path, I/O/Git failure, unsuitable target, oversized file, malformed/truncated membership, or failed consistency checks. | Keep the uncertainty. Do not infer deletion, an empty affected set, or permission to omit the source. [I:40-46,99-182; P:140-144] |
| Recorded version differs from a present version | **Inferred:** the input changed relative to that receipt; this is a freshness issue, not an observer state named `stale`. | Reevaluate affected knowledge using the real runtime; the read contract includes `ownership-input-changed`. A prior accepted version or rollback does not make it current. [T:80-102; C:53-55] |
| `ownershipInput(...)` returns `undefined` | The legacy projection collapses both absent and unavailable; it also catches thrown failures. | Never invert `undefined` into proof of absence. The pilot's `bind` labels undefined as input unavailable and stops. [I:21-29,185-190; H:35-39] |

### File bytes

**Observed:** the default file path opens with read-only and, where available, `O_NOFOLLOW`/`O_NONBLOCK`; verifies the opened target is a file; reads chunks; closes the descriptor; and rejects more than 256,000 bytes. It compares path inode and size before/after the read, then returns `id({kind:"ownership-source",version:1,bytes:[...]})`. A read failure or post-read disappearance is unavailable, not corroborated absent. The 256,000-byte guard also applies after injected reads. [I:143-182]

**Unknown:** these inspected checks do not by themselves prove a repository-wide atomic snapshot or rule out every concurrent same-inode, same-size edit. The version names bytes actually returned by this observation; a statement that an entire checkout was coherently observed requires additional evidence. [I:154-182; R:34-39]

### Directory membership

**Observed:** membership invokes strict Git `ls-files --cached --others --exclude-standard -z -- :(literal)<dir>`. It rejects thrown failure, truncation, nonempty stderr, malformed NUL termination, newline/carriage-return names, and empty candidate names. Candidates are deduplicated/sorted, must remain contained files without symlinks, and a missing candidate is dropped only after corroborated absence. The requested directory is checked again before success. The resulting version is `id({kind:"ownership-membership",version:2,bytes:UTF8(sortedPaths.join("\0"))})`. [I:99-141]

**Inferred impact:** membership can detect effective path additions/removals, including nonignored untracked files. It does not incorporate each member's contents. A consumer needing edits as well as membership must declare relevant `file:` keys too. A valid present empty membership is different from an absent directory and different from failed Git observation. This file delegates Git execution to `runGitStrict`; its internal process/error implementation was not inspected in this unit. [I:6-7,112-141]

## Binding separado e publicação governada

Depois da preparação, o mesmo par local independente recebe o candidato e a
transformação exatos. O registro `genesis-native-binding-approval/v1` deve nomear
os dois IDs reais e distintos desta execução, com propósito
`runtime-import-binding`. Cada decisão cobre o candidate ID, o contrato, todos
os critérios e todos os pares de result/input dos artefatos. O adapter não
deduz PASS lendo prosa e não converte aceitação semântica antiga em binding novo.

Pedidos e respostas originais ficam preservados por referência e corpo CAS.
Quando o host não expõe um message ID, `decision_id_kind:response-sha256`
identifica os bytes da resposta; o valor deve coincidir com seu digest. Esse
identificador não é telemetria de mensagem. O provenance gerado diz que é um
registro do adapter, não a fala original do juiz. IDs e transcrição fiel da
decisão são fornecidos pelo operador; esta porta não autentica identidades.

`OwnershipManifest` nos tipos existentes. Cada artefato passa por `readOwnership`,
inclusive os alcançados somente por navegação: blocked não é promovido a supported.
O carrier usa a derivação de grounding existente e percorre
`composeRuntime.check` e `atlas-emit`. Não há publicação direta de projeção.

Política, ator, provenance do store e ratificação continuam portas independentes.

nomeia quem assume a ratificação, não constitui segredo ou autenticação. Uma
execução isolada explicitamente autorizada pode configurar sua política normal
e nomear seu principal real, preservando a origem da autorização. Não pode
imitar um ator histórico, copiar autoridade de fixture ou alegar autorização de
produção. O adapter não cria política nem modifica essas variáveis. Binding PASS
não remove uma recusa do gate.

## Delta R1 e controles de recuperação

R1 mantém toda a validação de v1 e troca três casts duplos por um cast do valor
original já validado para seu tipo nomeado. Não adiciona um mecanismo de runtime.
O novo `genesis-native-recovery.test.ts` apenas dirige portas existentes com
fixtures explicitamente sintéticas:

- **NR1-01:** uma interrupção na fronteira real de sidecar, depois do CAS durável
  e antes da ativação, deixa HOLD ou o manifesto antigo ainda válido. A retomada
  desserializa o candidato preservado, usa seus mesmos resultados e não repete
  o callback de autoria sintética. Essa contagem não é telemetria de modelo.
- **NR1-02:** após drift da fonte e falha de ativação, a leitura atual fica HOLD;
  a histórica permanece explicitamente rotulada. A retomada aceita a nova
  seleção, e tentativas de rollback incompatível são recusadas tanto no adapter
  como no emit governado. Estado antigo e scope independente permanecem preservados.
- **NR1-03:** transporte v0, rebinding de scope, approval antigo para candidato novo
  e relocalização pelo emit não substituem o scope aceito. Isso não inventa um
  bloqueio cronológico universal por versão de produtor: republicação compatível
  de um candidato antigo é uma decisão separada de rollback.
- **NR1-04:** um Worker usa o runtime compilado da mesma revisão e lê a porta real
  continuamente enquanto outra thread ativa o sidecar pelo emit governado.
  Barreira e intervalos monotônicos exigem leitura sobreposta à serialização,
  link e commit depois de liberar a barreira, e não apenas reopen posterior.
  Cada resposta ready deve corresponder integralmente a um dos manifestos aceitos;
  o scope independente continua legível.

As semânticas de CAS-before-projection, geração imutável, fallback de predecessor
legível e recusa de store totalmente corrompido já pertencem ao sidecar/G3.
R1 não duplica os testes existentes de cache, rebuild ou update-input e não
transforma o antigo G3-02 sequencial em prova de sobreposição real.
