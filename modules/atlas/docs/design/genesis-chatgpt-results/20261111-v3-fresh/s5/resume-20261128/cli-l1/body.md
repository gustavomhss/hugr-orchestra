# CLI L1: executable composition and distribution boundary

Status: new, unevaluated candidate. This document is a source-based ownership map at Git commit `1cde2ff7a71bcf7aecb5d030917b577165135d38`, tree `a522a53e5f046f1758151b0f558531bbded04592`. It is not a recovered historical CLI body, an independent judgment, or a claim that a binary was built, installed, tested, released, or run. The adjacent inventory accounts for all 162 CLI paths assigned by the fixed S5 partition. A path's inclusion or grouping does not establish that its contents were semantically examined. The source receipt identifies the specific code excerpts observed for the statements below. In particular, test filenames identify intended test areas, not results.

## Role and first entrypoints

`@orchestra/cli` is the executable composition package: its package metadata maps the `orchestra` bin to `bin/orchestra.cjs`, publishes that bin directory, and declares a development entry at `src/index.ts` and a build script. At this revision its package version is `1.18.27`; that is metadata at the pinned tree, not the installed version in any environment. Its declared dependencies include Core, Client, Server, TUI, Maestro, and an engine adapter; this application composition must not be mistaken for permission to introduce those dependencies into the Client or protocol layers. The package README describes a command for users and scripts, a desktop server executable, and a thin npm shim. The source tree, rather than the README alone, provides the entrypoint binding and actual behavior. [R01, R02]

There are two materially different starts. A source/development invocation loads `src/index.ts`. A compiled build uses `src/omni-entry.ts` as its configured entry, which evaluates an Omni preflight and then imports `src/index.ts`. The npm executable is `bin/orchestra.cjs`, which chooses or accepts an explicit native binary and launches that binary. Therefore package installation, selection of a compatible native executable, compiled preflight, CLI parsing, server connection and execution are separate steps with different possible failures; a valid npm wrapper does not prove the required native companion exists or works. [R02, R03, R04, R05]

`src/index.ts` constructs handler loaders against the `Commands` specification, then supplies the daemon layer, Node services, a scope and the Node main runner. It supplies a version formatter that returns the exact version string rather than the usual decorated CLI version. Its mapping identifies the default handler and named handlers for API/debug, session, model and provider management, upgrade/uninstall, database, import/export, service, serve/run/attach/web, ACP, plugin, toolkit, stats, agent and MCP. An entry in this mapping establishes a source-level command binding; exact options and visibility are determined by the command specification, and individual command outcomes require the selected handler and its dependencies. [R02, R06]

The framework collects loader functions by walking the spec tree and associates a loader with a command spec. A selected handler is imported through an effect when invoked; nested specs become subcommands. The framework's handler requirements include the daemon and a child-process spawner. Its comment explicitly distinguishes the database: generic handler requirements do not open it, and database handlers provide it for their own execution. A command's existence in the map is not evidence that merely requesting version or help runs that handler or opens a database. [R07]

The default handler obtains the daemon transport and starts the TUI against the returned URL and headers. It is a client of the daemon connection rather than proof that a new daemon is always spawned: the transport logic can reuse an existing compatible service. `run` selects its transport according to its inputs and passes a directory into its client calls; it sets a nonzero process exit code if the result is not successful. These descriptions deliberately stop at the CLI-to-server boundary. They do not assert a provider response, session persistence or successful model execution. [R08, R09, R10]

## Configuration, service identity and process boundary

The daemon service declares operations for client, transport, start, start-on-port, status, stop, password and scoped registration. It uses Core's global state directory for `server.json` and `password`. The password operation reads an existing value, otherwise generates or accepts a value, writes a temporary file with mode `0600`, and renames it into place. The registration schema contains URL and PID, with optional ID and version. Health checks use authenticated client requests and a bounded timeout; version compatibility compares the registered version with the installation version. The source distinguishes unavailable registration/password, unreachable or unhealthy service, and version mismatch. These are implementation paths, not observations of any particular running service or filesystem permissions on a deployed machine. [R11]

The start path can launch the same executable as a detached child with `serve --register`, wait for readiness, and report when the child exits before registration. The daemon file directly imports `node:child_process` for this detached server lifetime. The bootstrap launcher also directly imports child process for launching the native program and host probes. Those observed boundaries should be evaluated against the source-revision allowlist rather than generalized to ordinary Orchestra process creation. The CLI's `services/process.ts` instead receives `ChildProcessSpawner` and collects stdout, stderr and exit status through that service. A source-level spawn call describes intended invocation, not observed process isolation, process termination, resource use or a successful operational run. [R11, R12, R13]

The stop path checks the healthy registration and requires it to match the identity it is stopping before signalling the recorded process. The `startOn` path checks whether the requested local port is already answering, and otherwise launches `serve` bound to loopback at that port. The registration path is scoped, with identity checks and finalization logic; source-level safeguards are distinct from a concurrency or security proof on a live host. The `service` command family delegates to these operations through its own handlers. The client and server credential implementations remain owned outside this CLI slice. [R11, R14]

`serve` resolves a web UI root from an environment-specified directory, a binary-adjacent web directory or a development build location when present. It selects a password from `ORCHESTRA_SERVER_PASSWORD` or the daemon password, removes server password and username from the environment, starts its host and HTTP listener, and conditionally registers the server. Its listener uses an explicitly requested port or tries a sequence beginning at the source-defined default; shutdown observes process signals and uses scoped finalization with a grace deadline. The command-spec defaults, implementation and deployment binding each have different authority: consult them for the actual hostname, port, CORS and authentication of a specific invocation rather than inferring exposure from a command name. The scoped source excerpt does not prove graceful shutdown happened in a particular process. [R15, R06]

## Command and input surfaces

The command specification is the canonical source for flags, defaults, nested commands and hidden help surfaces. For example it defines `run` message arguments, session continuation, model/agent options and output formats; other handlers implement server, database, service, management and integration operations. `src/index.ts` is the corresponding loader graph, not a second independent source of flag semantics. For a change to a flag, first inspect the spec and its actual selected handler together; an option present in one but unused or interpreted differently in the other cannot be assumed correct. A hidden help entry can still be bound and invocable, so help visibility is not authorization or a security boundary. [R06, R02]

## Native executable and companion selection

The source-controlled target list is a closed build matrix assembled from OS, architecture, an x64 baseline variant and optional musl ABI. Its rows are build inputs, not a set of observed installations. `build.ts` resolves each target's Omni companion before building, resolves tree-sitter inputs, and configures the compiled CLI entry as `src/omni-entry.ts`. The build also has a ripgrep bundling switch and target-specific resolution. A declared row, or source that can create a payload, does not prove its build succeeded, that the artifact corresponds to this commit, or that runtime qualification occurred. [R03, R18, R19]

The compiled preflight calls `needsOmni` on arguments. Help/version flags, a `help` word and `db path` skip the early load. Other invocations load Omni when the build enables it and `ORCHESTRA_EXPERIMENTAL_OMNI_SPAWNER` is unset, `1`, or `strict`; on load failure the program reports a preflight failure and exits. The loader comment names override variables and binary-relative locations. The early skip only describes the guard: it is not proof that an arbitrary command will never need a process later, or that the bypass validates the companion. [R04, R05]

A material pinned-source conflict must remain visible. The CLI README says Omni is disabled on Linux musl and Windows ARM64; `packages/script/src/omni.ts` maps both musl variants and Windows ARM64 to enabled companion IDs, and enables every one of the twelve listed target names. `build.ts` calls that resolver. For interpreting the build configuration, the executable target map is the more direct source at this revision; the contradictory README remains stale documentation, not proof that a build or those platforms ran successfully. No correction is made by this candidate. [R16, R19, R03]

The npm launcher honors `ORCHESTRA_BIN_PATH`, otherwise derives platform and architecture and detects host characteristics to choose a package. On Linux its libc checks distinguish musl from glibc; when detection is unknown it refuses automatic selection and tells the user to choose a compatible binary explicitly. It forwards arguments to the child with inherited stdio, forwards selected signals, and propagates the exit or signal result. It also has platform-specific capability probes. The existence of this fallback and its error handling does not validate a user-provided binary or establish host compatibility. It is a bootstrap implementation outside the regular daemon/spawner path, not a replacement for the native build's preflight. [R13]

## Distribution, tests and release evidence boundaries

The distribution README describes a prepared directory containing package metadata, the native `bin` tree, a descriptor and checksum file; a POSIX installer consumes an exact version, target, archive and trusted archive digest, while npm packaging creates a wrapper and target packages. The README describes locking, immutable versions, checks and atomic selection as intended implementation behavior; consult `distribution/install.sh`, `script/distribution-payload.ts`, and `script/distribution-npm.ts` for code and input-specific behavior. Their presence or a documented command is not an install, registry publish or rollback receipt. [R20, R17]

Distribution and runtime evidence have separate scopes. A source test can specify a real process, an installed binary or a negative control, but its contents are not a run. A built artifact requires its exact source commit, target, build inputs and output digest. Installed proof additionally requires the actual environment, artifact and execution result. An external registry publish, signing, notarization and release require their own actual receipts and authority. A successful service health check says something about the answering service and credential path, not every CLI command or its transitive provider. Likewise a companion peer check, where available, must not be promoted into proof that a public CLI performed a governed tool-spawn turn. The distribution guide itself distinguishes the installed companion peer probe, musl qualification, provider execution and publication. [R20]

## Change and incident navigation

For CLI command changes, locate the spec, loader and selected handler; verify how the flags become client/server input, then choose tests that exercise the public behavior and relevant error paths. For startup issues distinguish shim selection, compiled preflight, handler import and daemon transport. For service issues inspect registration identity, version, credentials, process lifetime and listener settings without treating an old PID or unverified registration as authority. For distribution issues bind target, OS/architecture/libc, companion and tree-sitter inputs to the built artifact; compare the source README conflict with the target resolver before drawing conclusions. For runtime or release claims request actual hosted run, job, artifact, digest, platform and result; this document deliberately supplies none.

These are navigation boundaries, not a procedure that has been performed. Ownership outside `apps/cli` remains with the respective package: Core owns Omni loading and global paths, Server owns server internals and authentication, the script package owns companion resolution, and distribution or release workflows own their respective automation. The 162-path inventory is exhaustive at the pinned revision only; it is not an ownership assertion for added paths or later commits. The partition groups the whole S5 population as CLI 162, Omni 426 and Platform 339; the present analysis does not claim to cover the other 765 members. [R17, R19, R21]
