## 1. Startup, readiness and shutdown

The desktop is an Electron host around the shared application. Main chooses application state, migration and logging, creates windows, registers integrations and starts the backend service. Its normal branch creates `join(app.getPath("userData"), "global")` recursively and passes that exact directory as `cwd` to `startOwnedServe`, after resolving the bundled CLI and launch environment together. The maintenance skill separately prescribes `userData/global` and warns against home or another large folder; its reported startup cost is historical, not a measurement from this work. The returned URL and Basic credentials are published through `serverReady` **after** `owned.health.wait` succeeds. Failure flows through `forwardInitializationFailure`; this ordering is stronger evidence than the renderer comment claiming credentials are available before health. (`M/index.ts:320–338,431–475`; `.orchestra/skills/desktop-startup-maintenance/SKILL.md:18–21`; `R/index.tsx:367–388`.)

`startOwnedServe` reserves a loopback port and random password, spawns `serve --hostname … --port …`, redacts the password from output, and retains the last 15 output lines for startup errors. Readiness races authenticated `/api/health`, the first child's exit and a 120-second ceiling. Its local health predicate accepts an HTTP success response; it is not the stricter WSL response/body and wrong-password check described later. `sidecarMode` selects shared mode only for the exact string `shared`. (`M/owned-serve.ts:15–68,94–102,130–141`; `M/owned-serve.test.ts:4–12`.)

**Static discrepancy:** on a child exit after `STABLE_AFTER`, the implementation sets `state.failures` to zero and reads `BACKOFF[state.failures - 1]`. That becomes index `-1`, giving `undefined` and the “not restarting” branch, although the nearby comment describes resetting backoff after stable operation. This is a direct control-flow inference, not a reproduced crash. The inspected owned-serve test only covers mode selection, so it supplies no restart regression evidence. (`M/owned-serve.ts:22–25,70–86`; `M/owned-serve.test.ts:1–13`.)

Stopping is a lifecycle operation: the owned child receives termination, main waits for `close` rather than just `exit`, and a watchdog escalates. Main's quit sequence marks quitting, flushes renderer state, stops sidecars and runtime resources, then continues quit. Windows are restored while initialization is in flight. The shared-daemon branch instead discovers candidate state homes, issues `service start` and retrieves its password; it is not evidence that the application owns that daemon's lifetime. (`M/owned-serve.ts:104–126`; `M/index.ts:277–294,414–429,477–495`; `M/background-cli.ts:21–53`.)

The launch environment sets desktop identity and a desktop state root, resolves staged executables/resources and removes inappropriate inherited settings. Shell discovery is bounded: `env -0` is parsed without splitting values on subsequent `=`, an interactive login probe times out after five seconds, and Nushell is skipped. Reported historical startup timings in the maintenance skill and guide were not measured here. (`M/server.ts:25–73`; `M/shell-env.ts:5–7,25–83`; `.orchestra/skills/desktop-startup-maintenance/SKILL.md`; `docs/guides/desktop-startup.md`.)

There is also a main-process fallback before a usable window can present recovery. The observer attached to `Effect.runFork(main)` returns on success, otherwise formats the cause, logs “desktop startup failed,” shows a native error box and exits with status 1. The comment motivates pre-window failure handling; the observer itself does not check whether windows already exist. Its title is the literal “HuGR Orchestra could not start,” and its body combines the first cause line with a literal “Logs:” label and path. **Instruction/source conflict:** desktop AGENTS requires i18n keys for displayed errors/dialogs and `nativeT(...)` in main; this path hardcodes visible English instead. That is an observed localization gap, not an inferred runtime display result or an authorized copy change. (`M/index.ts:498–508`; `apps/desktop/AGENTS.md:5–9`.)

## 2. Windows, persistence and IPC authority

Main windows have stable IDs and independently persisted state. The registry retains the last window during quit/restore but can forget a closed window when other windows remain. BrowserWindow construction enables `contextIsolation` and sandboxing and disables Node integration. Navigation is constrained to the renderer host or opened externally. A per-window flusher sends a random acknowledgment ID, coalesces concurrent requests and permits shutdown after three seconds; destroyed/crashed pages do not block indefinitely. The preload waits for all unload callbacks to settle before acknowledging. (`M/windows.ts:186–234,324–388`; `M/window-registry.ts:1–52`; `M/window-flush.ts:1–54`; `P/index.ts:15–21`.)

Origin policy trusts `oc://renderer` or the configured development origin, with packaged builds ignoring the development URL. The enforced CSP contains only `object-src 'none'; base-uri 'self'`; the fuller policy remains report-only. The inspected origin test explicitly expects that distinction, while fake-window tests exercise coalescing, separate acknowledgments and timeout behavior. These assertions do not prove the effective packaged renderer policy or real OS recovery. (`M/renderer-origin.ts:11–45`; `M/renderer-origin.test.ts:4–26`; `M/window-flush.test.ts:30–113`.)

The general `ipc.ts` registration wrapper checks `senderFrame.url` through `isRendererOrigin`. `window.api` exposes named operations rather than the entire Electron API. Picked attachments receive opaque random tokens tied to a sender and selected paths, consume each path once, and share a 20 MiB budget. **Admission is not uniform across all channels:** Dock, response transfer, live and WSL register separately. Dock requires the owning BrowserWindow's main frame; live and WSL directly call `ipcMain.handle` without the general origin wrapper in those modules. This is an audit gap, not an exploitability claim: Electron exposure, separate preloads and navigation controls also affect reachability. (`M/ipc.ts:69–94`; `P/index.ts:24–180`; `M/attachment-picker.ts:5–30`; `M/ipc-app-dock.ts:74–87`; `M/live-ipc.ts:1–58`; `M/wsl/ipc.ts:27–67`.)

Persistent state uses multiple mechanisms. `store.ts` lazily caches electron-store instances so construction follows userData selection; filenames have no extra extension and dot-notation access is disabled. Cleanup targets narrowly named draft/workspace files, checks small empty JSON, age/count criteria and mtimes again before deleting. Migration reads old per-channel Tauri files, avoids overwriting existing target values and records migration completion. (`M/store.ts:1–35`; `M/store-cleanup.ts:1–102`; `M/migrate.ts:1–91`.)

Drafts use SQLite WAL through Drizzle, a latest-value pending map, 500 ms batched transactions and SHA-256-addressed blobs. Startup removes blobs unreferenced by persisted draft documents; close flushes pending writes. The Node test file contains a meaningful negative control: copying only the main SQLite file while WAL holds commits loses the newer data, whereas an explicit backup after flushing is expected to restore exact document/blob bytes. None of those databases or tests was run. (`M/draft-store.ts:1–82`; `M/draft-store.node.test.ts:11–76`.)

## 3. Host adapters, recovery and native integration

The renderer constructs a desktop `Platform`: storage calls IPC, native menu actions delegate to main except renderer-controlled zoom, and server selection joins the local sidecar with ready WSL connections. If local startup fails, it probes stored HTTP servers and suppresses the local error only when a healthy remote is available. Shared `@orchestra/app` owns the application interface and most product behavior. The small boot entry paints the splash before importing the larger app, with a timer fallback when animation frames do not run. (`R/index.tsx:120–175,353–455`; `R/initialization.ts:1–71`; `R/boot.tsx:1–14`.)

Native menu commands implement window creation/close/minimize/maximize, reload, devtools, zoom, fullscreen and edit operations. Other adapter leaves handle app resolution, deep/external links, open-path behavior and platform declarations at family depth. Onboarding remains pending until the renderer confirms its first opened project; old-layout eligibility derives from existing app state. Janitor state bounds report bytes and snooze duration and remembers dismissals. Keep-awake is application-wide, uses `prevent-app-suspension`, broadcasts state and is not persisted. (`M/desktop-menu-actions.ts:11–84`; `M/onboarding.ts:7–33`; `M/install-state.ts:1–8`; `M/janitor.ts:27–70`; `M/caffeinate.ts:1–18`; `docs/guides/keep-awake.md`.)

Logging writes run-scoped files, admits console messages only from the owning renderer main frame, starts Crashpad without uploading, and provides bounded net logging and support ZIP export. Window recovery captures renderer failure/unresponsiveness and can offer recovery/log actions. Log-redaction and OS sampling leaves are recorded as family-supported, not an exhaustive privacy or platform audit. The log-hygiene skill is maintenance guidance; log data is not instruction authority. (`M/logging.ts:23–79,99–135`; `M/windows.ts:445–458,542–564`; `.orchestra/skills/app-log-hygiene/SKILL.md`.)

## 4. Dock browser ownership and page tools

Dock has a browser state plane and separate agent-operation transport. Browser views are sandboxed with no privileged preload. Tabs carry `{tabID, generation}`; active attachment and generation checks keep delayed resize/hide/select work from moving a replacement view. Inactive tabs have a bounded LRU. Recovery replaces the view with a new generation, while profile deletion retires the storage key, closes matching tabs and clears browser storage/cache. URL normalization accepts HTTPS and can convert plain search input to a search URL. (`M/app-dock.ts:237–315,535–605`; `M/app-dock-utils.ts:18–55`.)

Profiles own persistent session partitions and a registry with active/deleting/deleted states. Manifest replacement uses expected-revision comparison; writing is temporary-file/fsync/rename based. Session permissions are denied except fullscreen. Download ownership follows the sender/tab lifecycle, with bounded active and terminal records. Popup tests use fake Electron views: only the visible tab may create a new selected Dock tab; background or hidden views are denied. These tests describe policy, not a fresh browser-security proof. (`M/app-dock-profile-registry.ts:8–38,247–303`; `M/app-dock-session.ts:7–17,117–179`; `M/app-dock-popups.test.ts:78–110`.)

The page layer builds JavaScript for semantic DOM reads, input, storage, network/evaluation, waits and screenshots. Numeric browser references live in bounded namespaces; navigation invalidates them. `app-dock-browser.ts` is a handwritten script builder, not a generated corpus. Snapshot budgets, text caps, traversal limits and JSON/tree/CSV modes constrain responses. Navigation serializes by tab/generation, times out and rechecks identity; page reads coalesce and can retry after namespace changes. AppDockRPC distinguishes browser numeric references from native `n:` references and routes selector-compatible operations accordingly. (`M/app-dock-browser.ts:1–155`; `M/app-dock-navigation.ts:1–102`; `M/app-dock-page.ts`, `read`/`execute`/`wait`/`screenshot`; `M/app-dock-rpc.ts:464–488,660–682`.)

## 5. Native Dock identity and uncertain outcomes

Native operations carry more than a tab identifier: sender/window, tab generation, profile, runtime ID/epoch, accessibility session, binding ID/epoch, application launch identity, ownership revision and process identities participate. Process identity includes PID birth ticks, boot ID and PID/mount namespaces. Protocol frames and pending work are bounded; startup, request and cancellation grace have separate deadlines. JSON validation and helper hello checks bind the backend/version/capability surface. (`M/app-dock-native-protocol.ts:1–132`; `M/app-dock-native.ts:1–160,362–372`.)

The host reserves capacity before awaiting resource acquisition, tracks retiring clients/cleanup and keeps occupied capacity when reaping is uncertain. Native client admission is serialized with bounded queued work and immutable argument snapshots; cancellation after dispatch reports `unknown`, while work rejected before dispatch can report `not-dispatched`. Control acknowledgments do not by themselves release the original operation's slot. Channel shutdown and dedicated helper termination seek actual disappearance instead of treating elapsed time as success. (`M/app-dock-native.ts:1–160,290–375`; `M/app-dock-native-client.ts:1–115,300–390`; `M/app-dock-native-channel.ts:1–150`; `M/app-dock-native-runtime.ts:1–90`.)

Workspace preparation checks the visible placement against fresh runtime/process evidence, acquires a helper, and returns ownership immediately so later cancellation cannot orphan it. Confirmation repeats the census and confirms actual helper-proposed AT-SPI roots; it does not infer roots from titles or X11 window IDs. Rebind tests expect old unbind/reap to precede replacement discovery and stale refs to fail. The admission test explicitly retains a slot after abort and cancel ACK until the original terminal response. These are strong test designs, still unexecuted. (`M/app-dock-native-workspace.ts:7–37`; `M/app-dock-rpc-workspace-rebind.test.ts:8–70`; `M/app-dock-native-client-admission.test.ts:35–59,102–140`.)

The eight Python helper modules separate protocol dispatch, bindings, request context, D-Bus, snapshots, references, actions and keyboard input. Discovery matches exporter PIDs against current birth identities and proposes bounded concrete windows; host confirmation is required. Reference fingerprints suppress protected text, detect changed ancestry and bound event-invalidated caches. Snapshots explicitly report non-atomic coverage, bounded live traversal and no logical dataset identity. Actions recheck advertised actions and return dispatch acknowledgment with postcondition still unverified. A successful provider ACK is therefore not proof of a saved file, changed setting or intended UI result. (`H/bindings.py:1–84`; `H/context.py:21–39,63–83`; `H/refs.py:27–89`; `H/snapshot.py:32–83`; `H/actions.py:12–56`.)

## 6. Linux runtime, access RPC and WSL

The production Linux desktop uses a local Docker engine, a durable owner/endpoint/container identity and an Xpra viewer. Only Unix sockets or Windows named pipes are admitted as backend endpoints. Docker commands neutralize inherited routing overrides and use the saved local endpoint and immutable container ID after ownership checks. Runtime mutations serialize; native observation failure can degrade native readiness without poisoning ordinary workspace readiness. The visible Linux view additionally tracks sender/profile/generation and minimizes/hides display activity when not visible. (`M/app-dock-runtime-backend.ts:1–140`; `M/app-dock-runtime-docker.ts:1–125`; `M/app-dock-runtime.ts:1–170,300–445`; `M/app-dock-linux.ts:1–140`.)

The guest build pins Xpra/HTML5 versions and copies workspace scripts. `workspace.py` publishes a private session record, refuses symlinks, verifies current process birth identity, preserves the distribution D-Bus policy and clears stale display sockets only after probing. Its comment about measured Electron accessibility behavior remains a historical statement. The runtime README documents a Moby-derived seccomp baseline plus selected changes; the seccomp file, signing key and future live apt closure were not independently authenticated. (`apps/desktop/resources/linux-runtime/Dockerfile:1–26`; `apps/desktop/resources/linux-runtime/README.md:1–55`; `apps/desktop/resources/linux-runtime/workspace.py:319–370,553–608`.)

`linux.rpc` is distinct from browser/native Dock operations. It handles exec, file read/write/list and session-owned terminal operations, cancellation and session close. Runtime identity is checked around access. File reads cap chunks at 65,536 bytes, writes bound encoded input, and paths must be absolute guest paths; this is not a host-path restriction. Guest cancellation uses process start evidence, and transport retirement waits for actual termination with uncertainty preserved on failure. (`M/linux-workspace-rpc.ts:1–158`; `M/linux-workspace-access.ts:1–160`; `M/linux-workspace-files.ts:5–70`; `apps/desktop/resources/linux-runtime/workspace-access.py:1–100`.)

WSL is a separate Windows server-management path. Its controller separates stored configs from runtime state and uses per-distro/job generations to reject stale completions. Artifacts are restricted to supported Linux architectures, checked as regular executable files, hashed and version-checked before replacement or launch, with required companions staged alongside. Every WSL command has a timeout and output decoding; sidecar startup races health, exit and a finite deadline. WSL readiness requires authenticated `healthy: true` and a wrong-password 401. The renderer includes only ready servers and falls back when a selected WSL server is unavailable. (`M/wsl/servers.ts:1–140,235–365`; `M/wsl/artifact.ts:1–120`; `M/wsl/runtime.ts:34–110`; `M/wsl/sidecar.ts:1–100`; `M/wsl/startup.ts:1–36`; `R/wsl/connections.ts:1–28`.)

## 7. Live capture and overlay

Live orchestration permits one meeting and one outstanding answer. Startup requires a transcription key and usable requested sources; denied requested microphone access fails, while unavailable system audio can degrade to microphone-only. Readiness reports system audio availability separately from permission, and deliberately leaves answer-provider reachability unknown instead of probing it. The key is encrypted with Electron safeStorage when stored, with an environment fallback. Settings filter typed fields and test shortcut registration before persistence. (`M/live-loop.ts:1–130,210–340`; `M/live-readiness.ts:1–59`; `M/live-key.ts:1–27`; `M/live-settings.ts:1–173`.)

Audio capture uses a hidden, sandboxed isolated window and its narrow preload. Two 16 kHz PCM tracks are conditioned with echo gating; a bounded recent-audio ring supports reconnect. Deepgram transcription uses final watermarks to suppress duplicates, with capped reconnect backoff. Meeting segments retain stable IDs for retry; stop drains capture/transcription, flushes segments and reports unsent data. The session client follows backend events and filters by session. These are client contracts; the backend implementation and real provider semantics were not checked here. (`M/live-capture.ts:1–125`; `P/live-capture.ts:1–10`; `M/live-audio.ts:1–77`; `M/live-transcriber.ts:1–130`; `M/live-senses.ts:1–168`; `M/live-meeting-client.ts:1–108`; `M/live-session-client.ts:1–100`.)

Main owns overlay state and passes it through a separate `window.live` bridge. Overlay actions check the exact overlay webContents/main frame; content protection and always-on-top are reasserted, though actual screen-sharing exclusion needs platform evidence. The renderer has its own English/Brazilian Portuguese copy selected from system language, outside the general locale dictionaries. Direct live IPC and separate content-protection handlers merit their own admission review. No screen, microphone or external service was accessed. (`M/live-overlay.ts:1–95,205–265`; `M/live-overlay-state.ts:1–125`; `P/live.ts:1–24`; `R/live/index.tsx:14–16`; `M/live-ipc.ts:1–58`.)

## 8. Response files, executable resources and updates

Response download grants an opaque handle after native selection, binds it to the originating main frame and writes an exclusively created temporary file. Sequence checks and one in-flight write preserve ordering/backpressure. The renderer consumes bounded copies rather than buffering the full response. Completion renames into the chosen destination; cancellation must not reinterpret a committed rename or delete a temporary file it never acquired. Tests cover foreign senders, sequence gaps, partial writes and an unowned temporary-name collision. (`M/response-download.ts:1–180`; `R/response-download.ts:1–115`; `P/index.ts:165–179`; `M/response-download.test.ts:7–100`.)

CLI resource resolution verifies manifest target/hash and executable version. Packaged installation uses a version/target/hash-named cache with required Omni pair, tree-sitter and optional bundled ripgrep. An existing copy is rechecked; installation stages companions before publishing the manifest. Optional Omni process adapters preserve explicit environment semantics, strip `HUGR_OMNI_*` from children, distinguish exit from drained close and route termination to owned process trees. Core loader/native internals remain outside this inspection. (`M/background-cli.ts:56–76`; `M/cli-artifacts.ts:8–58,66–117`; `M/cli-install.ts:22–87`; `M/omni-process.ts:18–39,54–124`; `M/omni-host.ts:20–36`.)

Packaging separately builds main, preload and renderer entries. Staging validates target sets and copied artifacts; electron-builder verifies resources before/after packing/signing and avoids rewriting already-hashed staged executables. Extra resources include native icons, Python helper, Linux runtime, playbooks, CLI, executable notices and Omni files outside ASAR. Fuses disable RunAsNode, Node options and inspection switches; ASAR-integrity enablement is explicitly absent in the inspected config. None of these declared build checks ran. (`apps/desktop/electron.vite.config.ts:1–99`; `apps/desktop/scripts/cli-staging.ts:1–150`; `apps/desktop/electron-builder.config.ts:1–175,177–210`.)

The updater owns one authoritative state machine: check, download, ready, install. A stored ready version is revalidated through the updater backend/cache, not accepted alone. Installation first stops resources; failure returns to ready. Builds unable to replace themselves expose a release-page URL. Prerelease/downgrade and automatic installation are disabled in the wrapper. Mock tests assert these states but provide no release-feed, signing or installer proof. (`M/updater-controller.ts:1–106`; `M/updater.ts:1–110`; `M/updater-controller.test.ts:47–103`.)

## Open evidence and maintenance consequences

The principal unresolved behavioral question is the stable-child restart indexing. The principal cross-cutting audit boundary is nonuniform IPC admission, alongside the intentionally partial enforced CSP. The native startup error dialog also conflicts with the package's localization instruction. These observations are not converted into unsupported runtime failure or exploit claims. Actual OS permissions, Docker/WSL identity/reaping, AT-SPI effects, media capture, package signatures, installed update behavior and renderer appearance require authorized runtime evidence elsewhere. Most fixture, locale, asset and helper leaves have explicitly bounded family coverage; five metadata-only entries have no semantic assurance. Source bytes and path accounting are verified here, while product correctness and later-layer reconstruction remain open.
