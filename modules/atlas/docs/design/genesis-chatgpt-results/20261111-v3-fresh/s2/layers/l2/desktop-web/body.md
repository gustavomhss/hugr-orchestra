# Genesis S2 — desktop/web behavior and maintenance

## Orientation and ownership

This explanation is `s2.l2.desktop-web`, built from accepted `s2.l1.desktop-web` at repository revision `1cde2ff7a71bcf7aecb5d030917b577165135d38`. It interprets the desktop/web unit's 532 entries across 30 families. L1's representative coverage remains representative; this layer adds no whole-file or runtime assurance. “Implementation” denotes observed code, “instruction” attributes repository guidance, and “maintenance interpretation” identifies the consequence drawn here.

Electron main owns host resources, preload exposes selected operations, and the desktop renderer hosts `@orchestra/app`. The web entry supplies a browser `Platform` to that same shared application. **Maintenance interpretation:** place host lifetime and OS-capability changes in their host owner; investigate shared session/UI behavior through the shared application boundary. Navigation destinations `s2.l2.app-session` and `s2.l2.design-tui` are consultation pointers, not build evidence for this body. (Evidence: `s2.l1.desktop-web`, “Scope and evidentiary status,” §3 “Host adapters, recovery and native integration,” and §9 “Web, languages, media and historical evidence”; `apps/web/AGENTS.md`; `apps/desktop/src/main/README.md:3–14`.)

## Startup publishes readiness before the renderer proceeds

The normal desktop branch resolves the CLI and launch environment together, starts an authenticated loopback child in `userData/global`, waits for health, then publishes its URL and credentials. The renderer's comment claiming earlier credential availability disagrees with this main-process ordering. The separate `shared` mode discovers/starts a background daemon; discovery does not establish ownership of its lifetime. (Implementation: `apps/desktop/src/main/index.ts:431–475`; `apps/desktop/src/renderer/index.tsx:367–388`; accepted `s2.l1.desktop-web`, §1 “Startup, readiness and shutdown.”)

**Instruction and historical rationale:** the startup skill prescribes the small `userData/global` working directory because requests without a directory create a Location there; it reports earlier costs from watching home and scanning unsigned binaries. Those timings were not measured here. **Maintenance interpretation:** preserve the readiness race between health, first-child exit and the 120-second ceiling; distinguish cold executable validation from warm startup work before changing deadlines or adding awaited initialization. The local health check accepts an HTTP success response; it does not perform WSL's stronger body/authentication checks. (`.orchestra/skills/desktop-startup-maintenance/SKILL.md:10–26`; `apps/desktop/src/main/owned-serve.ts:94–102,135–142`.)

**Static discrepancy retained:** after more than `STABLE_AFTER`, child exit resets failures to zero, reads `BACKOFF[-1]`, and takes “not restarting.” This contradicts the reset-backoff comment; the accepted mode-selection test supplies no restart regression evidence. Shutdown separately flushes windows, stops resources, and waits for child `close`, with escalation bounded by a watchdog. **Maintenance interpretation:** a startup success or exit notification does not settle restart or drained-shutdown behavior. (`apps/desktop/src/main/owned-serve.ts:23–25,70–86,104–126`; `s2.l1.desktop-web`, §1.)

## Persistence and recovery have several owners

Window IDs and stored placement survive independently. Per-window flush requests coalesce, use separate acknowledgment IDs, and allow shutdown after three seconds; preload waits for unload callbacks to settle. **Maintenance interpretation:** preserve that bounded handoff when changing close/reload behavior; a timeout permits lifecycle progress and is not proof that every renderer write became durable. (Implementation and inference: `s2.l1.desktop-web`, §2 “Windows, persistence and IPC authority.”)

Settings stores are created lazily after userData selection. Legacy migration avoids overwriting existing targets, while cleanup targets small, empty, scoped files and rechecks mtimes. Drafts instead combine SQLite WAL, a latest-value pending map, 500 ms transaction batches and content-addressed blobs; close flushes pending changes. The inspected draft test contrasts a main-file-only copy that loses WAL commits with a flushed backup expected to restore document/blob bytes. **Maintenance interpretation:** copying a settings file and backing up drafts are different operations; the unexecuted negative control explains why WAL-aware handling matters. (Evidence: `s2.l1.desktop-web`, §2.)

Recovery also has separate paths: renderer initialization may use a healthy stored remote server after local startup failure; window recovery offers renderer-failure actions; main's failure observer logs, shows a native error and exits. Run-scoped logs, bounded network logging and support export aid diagnosis, while redaction/OS sampler coverage remains partial. The log-hygiene skill instructs maintainers to treat logs as data and fix repeated noise at its source. No real recovery or export was exercised. (Evidence: `s2.l1.desktop-web`, §1 and §3 “Host adapters, recovery and native integration”; `.orchestra/skills/app-log-hygiene/SKILL.md:8–16`.)

## Privilege is checked at each request boundary

Main windows enable isolation/sandboxing and disable Node integration; packaged origin selection ignores the development URL. The enforced CSP contains only `object-src 'none'; base-uri 'self'`; the wider policy remains report-only. Its source comment attributes this to unverified packaged compatibility. **Maintenance interpretation:** review origin, navigation, preload exposure and handler admission together; the existence of a policy string does not establish that the whole policy is enforced. (`apps/desktop/src/main/renderer-origin.ts:7–45`; `s2.l1.desktop-web`, §2 “Windows, persistence and IPC authority.”)

The general IPC wrapper checks renderer origin, but registration is not uniform. Dock checks the owning window's main frame; Live and WSL register directly without that wrapper in the inspected modules. Separate preloads and navigation controls still affect reachability. **Maintenance interpretation:** changing or adding a channel requires its own admission analysis; this source difference alone proves neither exploitability nor safety. (Evidence: `s2.l1.desktop-web`, §2.)

File capabilities illustrate why sender and lifetime checks matter. Picked attachments use opaque, sender-bound, one-use path tokens with a 20 MiB shared budget. Response downloads bind a save handle to the originating main frame, sequence bounded writes, exclusively acquire a temporary file and rename on completion. Cancellation must preserve a committed rename and must not delete a temporary file it never owned. The inspected foreign-sender, partial-write and collision tests are expectations, not results. **Maintenance interpretation:** keep native selection, transfer authorization and final commit distinct when changing file flows. (Evidence: `s2.l1.desktop-web`, §2 and §8 “Response files, executable resources and updates.”)

## Browser Dock operates on current tab observations

Dock browser views receive no privileged preload. Persistent profiles own session partitions; deletion retires the profile, closes tabs and clears storage. Expected-revision replacement and temporary-file/fsync/rename protect the profile manifest. Tabs pair an ID with a generation, so delayed attachment, resize, hide or recovery work can reject an obsolete view. Inactive views have bounded LRU capacity, and popup policy admits only the visible tab. Permissions are denied except fullscreen. (Implementation: `s2.l1.desktop-web`, §4 “Dock browser ownership and page tools.”)

Page operations use bounded handwritten script builders for semantic reads, input, navigation, evaluation, storage/network operations and screenshots. Navigation invalidates numeric reference namespaces, serializes work and rechecks generation; reads can coalesce or retry after namespace changes. Browser numeric references and native `n:` references have separate routing. **Maintenance interpretation:** a previously observed element or tab is not continuing authority after replacement/navigation. Preserve identity checks after awaits and response budgets when extending tools; fake-view popup tests and script inspection do not establish real browser behavior. (Evidence: `s2.l1.desktop-web`, §4.)

## Native Dock preserves identity and uncertain outcomes

Native authority includes window/sender, tab generation, profile, runtime epoch, accessibility session, binding epoch, launch identity, ownership revision and process birth/namespaces. Capacity is reserved before acquisition. Admission serializes bounded work; retirement retains capacity if reaping is uncertain. **Maintenance interpretation:** replacing these checks with a PID or visible title would discard identity distinctions the implementation uses to reject stale work. (Evidence: `s2.l1.desktop-web`, §5 “Native Dock identity and uncertain outcomes.”)

Cancellation before dispatch may report `not-dispatched`; after dispatch it reports `unknown`. A cancel acknowledgment does not release the original operation slot by itself. Workspace confirmation repeats fresh process evidence and confirms helper-proposed AT-SPI roots; it does not derive roots from window titles or X11 IDs. The helper bounds traversal/references, suppresses protected text, and reports non-atomic snapshots without logical dataset identity. Action dispatch acknowledgment leaves the postcondition unverified. **Maintenance interpretation:** preserve uncertainty through cleanup and user-facing results, and obtain a new observation before asserting that an action saved a file or changed a setting. The admission/rebind tests encode useful adversarial expectations but were not executed. (Evidence: `s2.l1.desktop-web`, §5.)

## Linux workspaces and WSL have different lifetimes

The Linux desktop uses a local Docker endpoint, durable owner/container identity and Xpra display. Only Unix sockets or Windows named pipes are admitted; commands neutralize inherited routing overrides and use the saved endpoint plus immutable container ID after ownership checks. Runtime mutations serialize, while a native-observation failure can degrade native readiness without invalidating ordinary workspace readiness. Guest session publication checks current process birth identity, refuses symlinks and preserves distribution D-Bus policy. (Implementation: `s2.l1.desktop-web`, §6 “Linux runtime, access RPC and WSL.”)

`linux.rpc` separately owns guest exec, files, session terminals, cancellation and close. Reads cap chunks at 65,536 bytes; absolute guest paths are not host-path restrictions. Termination uncertainty is preserved. **Instruction:** the main-domain README says Dock RPC and Linux workspace RPC have different authorities and must not be unified. **Maintenance interpretation:** the visible Linux tab is not sufficient authority for every guest-access operation. (Evidence: `s2.l1.desktop-web`, §6; `apps/desktop/src/main/README.md:29–34`.)

WSL instead manages per-distro servers on Windows, separating stored configurations from runtime generations. Executables/companions are architecture, file, hash and version checked; commands and startup have deadlines. Readiness requires authenticated `healthy: true` and a wrong-password 401, and the renderer admits only ready WSL servers. **Maintenance interpretation:** preserve those generation and authentication checks when reconnecting; do not substitute the owned-server HTTP-success predicate. Docker/Xpra, WSL, actual reaping, seccomp/signing-key provenance and future apt closure remain unverified. (Evidence: `s2.l1.desktop-web`, §6.)

## Live separates readiness, capture and delivery

Live allows one meeting and one outstanding answer. Startup needs a transcription key and usable requested sources: denied requested microphone access fails, while unavailable system audio can degrade to microphone-only. Permission and system-audio availability are separate fields; answer-provider reachability is deliberately `unknown`. Stored keys use Electron safeStorage, with an environment fallback; settings validate typed fields and test shortcut registration before persistence. **Maintenance interpretation:** a readiness display must preserve these distinctions rather than equate configuration with provider connectivity. (`apps/desktop/src/main/live-readiness.ts:28–45`; `s2.l1.desktop-web`, §7 “Live capture and overlay.”)

Capture uses a hidden isolated window and narrow preload. Audio conditioning, a bounded reconnect ring and transcription final-watermark suppression support continuity; stable meeting segment IDs support retries. Stop drains capture/transcription, flushes segments and reports unsent data. These are client contracts, without independent backend/provider verification. Main owns overlay state; overlay actions check its exact webContents/main frame. Content protection is reasserted, but actual exclusion from screen sharing requires platform evidence. The overlay's English/Brazilian Portuguese copy follows its own system-language path, outside general dictionaries. **Maintenance interpretation:** preserve delivery evidence separately from audio capture or overlay visibility; no microphone, screen or external service was accessed here. (Evidence: `s2.l1.desktop-web`, §7.)

## Executable staging and update state are separate evidence

CLI resolution verifies manifest target/hash and executable version. Installation stages required companions into a version/target/hash cache before publishing its manifest and rechecks existing copies. Omni adapters preserve explicit environment semantics, strip `HUGR_OMNI_*`, distinguish exit from drained close and target owned process trees; core native internals remain outside this inspection. **Maintenance interpretation:** retain companion and lifecycle checks when changing executable discovery or shutdown, and keep the startup skill's warm-path hashing constraint visible. (Evidence: `s2.l1.desktop-web`, §8 “Response files, executable resources and updates”; `.orchestra/skills/desktop-startup-maintenance/SKILL.md:19`.)

Build configuration separates main/preload/renderer entries, places required executable/native/Linux/playbook resources outside ASAR and declares staging/packing/signing checks. Fuses disable RunAsNode, Node options and inspection switches; inspected configuration does not enable ASAR integrity. The updater revalidates stored readiness against its backend/cache, stops resources before installation and returns to ready on failure; nonreplaceable builds expose a release URL. **Maintenance interpretation:** installed behavior requires evidence beyond declared build checks or a remembered ready version. No build, signing, feed, installer or mock updater test ran. (Evidence: `s2.l1.desktop-web`, §8.)

## Host adapters own platform differences and copy

The browser host supplies drafts, notifications, restricted external navigation and default-server preference. A saved default and current-origin token authentication are separate paths; `auth_token` is removed from browser history. Vite shares assets and supports fixtures/optional Sentry upload; CLI serving is a README boundary claim, not inspected CLI implementation. **Maintenance interpretation:** trace server preference and authentication independently when investigating connection behavior. (`apps/web/src/entry.tsx:77–124,145–172`; `apps/web/README.md:3–19`; `s2.l1.desktop-web`, §9 “Web, languages, media and historical evidence.”)

Desktop adapters own native menus, app/path/deep-link integration, onboarding confirmation, bounded janitor state and application-wide, unpersisted keep-awake. General translation imports 62 dictionaries with English fallback; representative English/Arabic reads establish neither linguistic quality nor key completeness. Desktop instructions require typed native translations. **Static conflict retained:** main's startup failure observer hardcodes visible English, and, despite its pre-window motivation comment, does not test window existence. (Evidence: `s2.l1.desktop-web`, §3 and §9; `apps/desktop/AGENTS.md:5–9`; `apps/desktop/src/main/index.ts:498–508`.)

The splash supports reduced motion, skipping and mount-aware dismissal, without visual inspection here. Specific icon documentation describes generation provenance; it does not establish tray/splash authorship or binary correctness. **Maintenance interpretation:** shared appearance and localization work belongs with shared UI owners, while host copy/assets retain their own provenance and platform checks. (Evidence: `s2.l1.desktop-web`, §9; `apps/web/AGENTS.md`; `packages/app-shell/AGENTS.md`.)

## Maintenance evidence retains its original limits

Generated Dock documents emit stored “measured”/“ready” labels; generation does not execute their referenced tests. Historical plans and closure claims remain history. Native proof fixtures distinguish launch receipts from semantic readiness; packaged Omni matrices distinguish production cases from diagnostics. Standalone runtime/WSL proof drivers have family-level coverage, and live package repositories prevent a promised byte-identical future rebuild. Five tooling/ignore/declaration entries remain metadata-only. (Evidence: `s2.l1.desktop-web`, “Scope and evidentiary status,” §9 “Web, languages, media and historical evidence,” and “Open evidence and maintenance consequences.”)

**Maintenance interpretation:** use these artifacts to locate an appropriate future check, while retaining the present gaps in IPC admission, partial CSP, stable-child restart, startup localization, OS/native effects, provider behavior and installed-package behavior. Root guidance assigns product tests to CI; this task changed no product code and ran no product test or CI. Mechanical source/body hashing establishes byte identity only. This L2 is an ownership explanation, not a runtime, security, accessibility, translation or release verdict. (Instruction: `AGENTS.md`, “Testing” and “CI Cadence”; accepted `s2.l1.desktop-web`, “Open evidence and maintenance consequences.”)
