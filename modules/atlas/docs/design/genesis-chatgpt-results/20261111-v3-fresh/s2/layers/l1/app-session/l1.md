## Transport, stream health and canonical recovery

The generated Client has its own runtime dependency rule: root AGENTS permits Client dependencies on Schema and Protocol and forbids dependencies on Core or Server at runtime. This Client prohibition is distinct from the explicitly permitted `platform:browserSafe` Core-helper exception for the UI layer described above; that UI exception does not authorize a Client runtime dependency. After a public Protocol or Server `HttpApi` change, root AGENTS requires `bun run generate` from `packages/client`; raw `packages/client/src/generated` and `packages/client/src/generated-effect` files must never be hand-edited. These are prescribed change requirements; no Client generation or product change was performed here. (`AGENTS.md:1–2`.)

The app adapter wraps the generated client and maps wire results into app view contracts. `scopedFetch` composes context lifetime, Request and call-specific abort signals. SDK readiness is a retryable thenable: success is retained, rejected attempts can retry with backoff. Startup readiness accepts either a numeric PID or `healthy: true`; the independent health probe checks `healthy === true`. These are distinct predicates. Health polling uses a short credential/fetcher-sensitive cache, requires two consecutive failures before declaring down, and lets recent stream activity override probe failure. (`packages/client/src/index.ts:1–3`; `A/src/utils/server.ts:28–150`; `A/src/utils/scoped-fetch.ts:1–27`; `A/src/context/server-sdk.tsx:167–225`; `A/src/utils/server-ready.ts:1–133`; `A/src/utils/server-health.ts:28–200`.)

The stream taps raw bytes, so comment heartbeats count as liveness even when no application event decodes. It batches work, combines only adjacent matching delta identities/directories, and preserves intervening-event order. Its silence threshold is 45 seconds; failures reconnect with bounded exponential delay, while lifecycle cleanup aborts transport and clears queued work. The server subscribes to a bounded 4,096-event stream before emitting `server.connected`, sends a comment heartbeat every 15 seconds, and emits SSE frames without a replay ID. The source supports a reconnect-and-reconcile design; it does not establish durable replay or lossless delivery under every overload. (`A/src/context/server-sdk.tsx:86–140,227–429`; `A/src/utils/server-stream-liveness.ts:1–89`; `packages/server/src/handlers/event.ts:13–43,51–59`; `packages/server/src/handlers/health.ts:1–10`.)

Server sync owns shared canonical session state and directory projections. Fetch reconciliation preserves live-touched values; tombstones and generation checks prevent late fetch resurrection. Pins protect active sessions/ancestors, and message paging fetches newest history until the necessary user-turn boundary is available. `session-recovery.resolve` coalesces concurrent reads, rejects superseded generations and repeats a GET if policy changes while it is pending. Its locally incremented read receipt is not a backend event revision; compatibility snapshots have no canonical V2 policy provenance. Normalization preserves unknown cost and separately compares read receipts, durable sequence and timestamps. (`A/src/context/server-session.ts:146–284,460–541`; `A/src/context/server-sync.tsx:230–280,455–570,600–707`; `A/src/context/session-recovery.ts:32–97`; `A/src/utils/session.ts:1–112,117–244`.)

Native event adaptation and transcript projection are separate steps. Admission records enter pending input state; promotion materializes a user transcript entry, and missing promotion context asks for recovery. Stable text/reasoning part IDs are adapted to renderer ordinals rather than treated as sortable content order. Reconnection refreshes relevant state; the inspected source does not prove exhaustive event/reducer coverage. ## Prompt admission and draft ownership

The reusable editor supplies a pure interaction machine and caller-owned store. It handles normal/shell mode, completion popovers, history and IME-aware Enter; app-shell owns persistence, permission policy, session creation and network submission. Attachment construction translates text, file/agent mentions, selected-line URLs and image data into the wire prompt. Undo restoration reconstructs prompt parts from prior messages; its selected spans include source-range repair, not every restoration branch. (`S/src/v2/components/prompt-input/machine.ts:1–267`; `S/src/v2/components/prompt-input/store.ts:1–130`; `A/src/components/prompt-input-v2.tsx:150–215`; `A/src/components/prompt-input/build-request-parts.ts:1–115`; `A/src/utils/prompt.ts:1–115,160–207`.)

The inspected first-send flow has five consequential steps:

1. Capture server credentials/scope, directory, tab/draft, prompt snapshot and generation-based owner. A WeakMap admission record survives composer remounts and prevents a second concurrent submit for the same source.
2. Resolve or create the target session and retain it for the attempt. Worktree waiting coalesces per server/directory and preserves terminal ready/failed results.
3. Acknowledge subagent policy through serialized writes and a canonical read. A failed predecessor remains a failure barrier; policy revision and owner are checked again around asynchronous attachment work and immediately at dispatch.
4. Send a stable request ID and payload. A transport failure after dispatch is ambiguous: it must retain the session/request for retry. Cleanup deletes only a never-dispatched session that the server confirms empty.
5. Only after admission succeeds, promote the draft tab to its session. Policy edits made in flight are acknowledged first; later composer edits move to the session unsent, and captured-state restoration must not overwrite newer input.

These steps are source observations, not an executed transaction proof. (`A/src/components/prompt-input/submission-admission.ts:1–45`; `A/src/components/prompt-input/submit.ts:280–476,530–583,600–708`; `A/src/components/prompt-input/submission-policy.ts:75–151,186–392`; `A/src/components/prompt-input/submission-state.ts:1–94`; `A/src/utils/worktree.ts:1–76`.)

The boundary makes admission precise. Schema `SessionInput.Admitted` contains admission sequence, message/session IDs, prompt/context, delivery, creation time and optional promotion sequence. Protocol prompt/command endpoints return this shape; their description says durable admission schedules execution unless `resume` is false. Server handlers invoke admission and map known missing/conflict/blocked errors. Core returns the previous admission when an existing ID has an equivalent session, encoded prompt and delivery; non-equivalent reuse rejects with `LifecycleConflict`. When it creates a new admission, Core publishes the admission event, requires a durable aggregate sequence and finds the projected record before returning. Retry equivalence compares **session, encoded prompt and delivery**; prompt context additionally participates in projection equivalence, so those two comparisons must not be conflated. Admission is therefore distinct from a rendered user message or completed assistant execution. (`packages/schema/src/session-input.ts:15–25`; `packages/schema/src/session-delivery.ts:1–6`; `packages/protocol/src/groups/session.ts:333–375`; `packages/server/src/handlers/session.ts:48–100,243–287`; `packages/core/src/session/input.ts:48–94,291–316,348–390`.)

Persistence likewise has multiple owners. Prompt scopes distinguish draft from session; tabs keep draft memory across component mounts. `Persist` namespaces global/workspace/draft/window data, migrates legacy canonical-local keys, separates remote scopes and protects edits during asynchronous hydration. Its draft backend may use IndexedDB documents and SHA-256-addressed image blobs, with version guards and object-URL/orphan cleanup. This is observed storage logic, not measured quota/crash consistency. (`A/src/context/prompt.tsx:40–168`; `A/src/context/prompt-state.ts:1–90`; `A/src/context/tabs.tsx:1–90`; `A/src/components/prompt-input/draft-session.ts:1–96`; `A/src/utils/persist.ts:87–164,349–387,477–704`; `A/src/utils/draft-store.ts:1–166`.)

## Skills catalog, editing and ownership

The catalog boundary is `readSkills(value: unknown)`, called on the list response's `.data`, before visibility filtering, sorting or cache writes. It accepts an array, including an empty array, whose entries have the following declared shape; a response envelope or JSON string is not that array. Required strings have no local nonempty, uniqueness or path-safety refinement. The decoder uses `Schema.decodeUnknownOption` over the entire array and `Option.getOrThrowWith`: malformed input fails the load with `Error("Skills response is malformed")`, rather than becoming an empty catalog or silently retaining only valid entries. (`A/src/orchestra/chapters/skills-data.ts:3–28`; `A/src/orchestra/chapters/skills.tsx:77–87`.)

| Entry field | Admissible declared value |
|---|---|
| `name` | Required string. |
| `location` | Required string; the file path is used for access, editing and saved-file matching. |
| `content` | Required string containing the instructions shown in the dialog. |
| `description` | Optional string or null. |
| `mtime` | Optional number or null. |
| `internal` | Optional boolean or null; only the value `true` excludes an entry as internal. |

Visibility and editability are separate decisions. `listedSkills` normalizes backslashes, collects every input location ending in `/SKILL.md` as a folder prefix, then excludes internal entries and any other location below one of those folders. The folder set is built before internal filtering, so an internal parent's folder still participates in hiding descendants. This implements a catalog view of skill trees; it does not delete entries or prove that a hidden node cannot be loaded through its parent. Search trims and lowercases the query and matches name, description or location. Sorting places project, global and builtin sources in that order, using `name.localeCompare` within a source. Neither the decoder nor these helpers establishes unique names. (`A/src/orchestra/chapters/skills-data.ts:30–49,58–72,83–89`.)

Ownership is derived from `location` and the current directory, not the display name. A literal `/builtin/` prefix gives source/access `builtin`. Otherwise, normalized locations beginning with the normalized directory plus its trailing slash are `project`; the rest are `global` and read-only. For project files, access is `governed` first when the relative path begins `.orchestra/skills/own/`. Remaining project files are editable only when they end in lowercase `.md` and lie under `.orchestra/skills/`, `.orchestra/skill/`, `.claude/skills/` or `.agents/skills/`; all others are `fixed`. These are lexical UI rules: slash normalization does not resolve symlinks, dot segments or filesystem authority, and the helper's comment about mirroring the server is not independent proof of filesystem enforcement. (`A/src/orchestra/chapters/skills-data.ts:51–81,98–99`.)

The page's cache identity is server scope plus a NUL separator plus `pathKey(directory)`; a warm list paints immediately while a new list is requested with `location: { directory }`. Only successful decode/filter/sort writes the cache. Refresh treats an error's object `cause.status` of 404, 405 or 501 as `unavailable`; other failures, including the decoder error, become `error`. Both states expose Retry and differ from a successful empty list. The load carries the page's abort signal and ignores results after cleanup. Catalog rows retain `skill.location`, and the dialog receives the computed access class; source names and project labels are presentation. (`A/src/orchestra/chapters/skills.tsx:29–55,69–97,136–137,175–187,208–210`.)

The client edit shape is `SkillSaveInput { name: string; description: string; content: string; path?: string; mtime?: number }`. Adding supplies no existing path/mtime. Editing supplies `skill.location` as path and `skill.mtime ?? undefined`; name/description are browser-required fields, while instructions are submitted as content. The normal dialog enables editing only for add or access `edit`, exposes removal only for an editable existing entry, blocks repeated submissions while busy and discards late UI results after disposal. The page calls `sdk().orchestra.skills.save({ location: { directory }, ...input })` or `remove({ location: { directory }, path: skill.location })`. On success it closes only the same dialog instance and reloads; save retains the returned location as pending and shows a notice if the refreshed list does not contain it. Write calls here receive no page abort signal, so cleanup suppressing later UI updates does not prove cancellation of an already sent write. (`A/src/orchestra/chapters/skills-dialog.tsx:5–26,34–57,134–175`; `A/src/orchestra/chapters/skills.tsx:48–55,100–125,219–238`.)

The pinned API declares `GET /api/skill` for listing, `PUT /api/skill` with `Skill.SaveInput`, and `DELETE /api/skill` with location query plus path. Its save description reserves new files for project `.orchestra/skills`, permits rewriting a registered project file, treats global/builtin/Atlas-governed files as read-only and says frontmatter is reserialized as YAML. The inspected handler delegates to `SkillV2` with the server Location directory, mapping input path to service location and forwarding mtime; conflict write errors become `ConflictError`, other write errors become `InvalidRequestError`. This confirms the API/service boundary, not the uninspected filesystem implementation or a successful write. The page turns unsupported-write statuses into its unavailable message, avoids displaying an undeclared `ClientError` message, and otherwise uses a string `message` or its fallback. No product, decoder or write test was executed in this correction. (`packages/protocol/src/groups/skill.ts:8–56`; `packages/server/src/handlers/skill.ts:10–46`; `A/src/orchestra/chapters/skills-data.ts:92–96`; `A/src/orchestra/chapters/skills.tsx:128–132`.)
