- **Alive after 35 seconds:** readiness is still pending, not yet a timeout. The owned child’s authenticated `/api/health` probe races its first exit and a **120-second ceiling**. The historical report that a first macOS launch can spend about 30 seconds scanning an unsigned executable is context, not a measurement or diagnosis of this launch. Local readiness accepts HTTP success; it is distinct from the stricter WSL health contract. **Cites:** result `0e87752e06abf7f3666af2d7a2cbb4ef8dfa2c833a2dc24d37b5d1164e7cb58c`, key `s2.l2.desktop-web`, “Startup publishes readiness before the renderer proceeds”; result `75c3347283b89766e28058b6618ea5cec5588e0a9d1b011e2b2b3b8bade9ab58`, key `s2.l1.desktop-web`, §1.

- **Immediate exit:** the first child exiting before health fails startup immediately; it does not wait for the 120-second ceiling. Inspect the exit and retained output: startup errors retain the last 15 output lines, with the password redacted. The normal path resolves CLI and environment together, starts the authenticated loopback child in `userData/global`, and publishes URL and credentials only after health succeeds. **Cites:** results `0e87752e06abf7f3666af2d7a2cbb4ef8dfa2c833a2dc24d37b5d1164e7cb58c` and `75c3347283b89766e28058b6618ea5cec5588e0a9d1b011e2b2b3b8bade9ab58`, same keys and sections above.

- **Recovery:** after local startup failure, renderer recovery may select a **configured HTTP(S) connection that passes its health probe**, trying the preferred URL first and then remaining entries in stored order. A configured remote’s mere presence is insufficient, and arbitrary servers are not discovered. Selecting a healthy remote recovers server selection; it does not show that the local child recovered. Shared-daemon mode also has different lifetime ownership. **Cites:** result `0e87752e06abf7f3666af2d7a2cbb4ef8dfa2c833a2dc24d37b5d1164e7cb58c`, key `s2.l2.desktop-web`, “Startup publishes readiness before the renderer proceeds”; result `ad072b7556935a92b5711269629f5aee15b98e2dbfa2aa3b2134328fe89901f1`, key `s2.l3.desktop-web`, “Launch, choose a server and identify the health decision.”

- **Inspect without restart:** use existing process state and run-scoped main, server and renderer diagnostics; compare launch-stage timestamps and cold/warm behavior. Record source/build/channel, OS, owned versus shared mode, selected server key and credential-context generation. ### Clarification

The documented **early main-process fallback** observes `Effect.runFork(main)`: on failure it formats the cause, logs “desktop startup failed,” shows a native error box titled “HuGR Orchestra could not start” with the first cause line and a literal “Logs:” label plus path, then exits with status 1. Although its comment motivates handling before a usable window exists, the observer itself does **not** check whether windows already exist. This is a source observation, not proof that the dialog appeared in either launch. **Cite:** result `75c3347283b89766e28058b6618ea5cec5588e0a9d1b011e2b2b3b8bade9ab58`, key `s2.l1.desktop-web`, §1 “Startup, readiness and shutdown.”

Before starting the owned child, main creates `userData/global` recursively and resolves the bundled CLI and launch environment together; it then passes that directory as the child’s `cwd`. The reads do **not** establish a more precise sequence between directory creation and the concurrent CLI/environment resolution, nor an ordering between those two resolutions. After spawn, health, first-child exit and the 120-second ceiling race; publication follows successful health. **Cites:** result `75c3347283b89766e28058b6618ea5cec5588e0a9d1b011e2b2b3b8bade9ab58`, key `s2.l1.desktop-web`, §1; result `0e87752e06abf7f3666af2d7a2cbb4ef8dfa2c833a2dc24d37b5d1164e7cb58c`, key `s2.l2.desktop-web`, “Startup publishes readiness before the renderer proceeds.”
