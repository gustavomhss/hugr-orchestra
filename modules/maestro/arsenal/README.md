# Maestro Arsenal

The tool catalog Maestro uses to plan and govern work: decomposition, conflict maps, contract freezing, wave scheduling,
repository onboarding, and governance checks (acceptance, usage and cost, repository hygiene, completion contracts).
Each tool is a bounded, schema-validated operation with declared effects (`read`, `write`, `process`). Results are
advice: the host owns permissions, process execution and completion evaluation.

## Who uses it

- `packages/core/src/tool/maestro-arsenal.ts` exposes it to the native Maestro seat as `maestro_arsenal_catalog`,
  `maestro_arsenal_describe` and `maestro_arsenal_execute`, loading the package lazily
  (`maestro-arsenal-omni.ts`). It binds the context, authorization and process runner.
- `modules/maestro/coordination` supplies the host observations and native bindings (`modules/maestro/coordination/src/arsenal-native.ts` and
  `arsenal-observations.ts`). How Maestro uses the tools is in [the Maestro guide](../../../docs/guides/maestro.md).
- `./server` is a standalone stdio MCP adapter, with no global configuration and no implicit permission grants.

## Entry points

- `src/index.ts` (the `Arsenal` namespace): `list`, `describe`, `execute`, `validateHostSnapshot`, `extractSymbols`,
  `readPreferencesSnapshot`, `setProcessRunner` and `processRunner`, `trustedAsset`, and the shared types
  (`ArsenalContext`, `Descriptor`, `Effect`, `Tool`).
- `src/registry.ts` holds the static descriptors; handlers in `src/tools/<name>.ts` load only when that tool runs.
  Engine descriptors live in `src/engine` and governance descriptors in `src/governance`.
- `src/onboard` extracts symbols and derives a project profile; it uses tree-sitter and a parser worker.
- `src/server.ts` is the MCP server. As a script it takes `--directory`, `--state-directory`, `--project-id` and
  repeated `--allow read|write|process`.

## Boundaries

- The caller supplies the project directory, the state directory and the project ID. State stays outside the source
  repository, under `<stateDirectory>/<projectID>`.
- The module does not own Session execution, Core data roots, model permissions or the completion evaluator.
- Tree-sitter grammars and the parser worker are runtime assets; source and compiled-binary placement differ.
  Desktop packaging carries the prebuilds.
- Integration semantics and persistence limits are in [HOST-BINDINGS.md](src/governance/HOST-BINDINGS.md); the port
  contract is [arsenal-port.md](../../../docs/specs/hugr-maestro/arsenal-port.md). Source attribution is in `LICENSE`,
  `NOTICE` and the adaptation headers.

## Commands

`bun typecheck` from this directory. Tests run on CI from the repository root:

```sh
bun run test:ci maestro-arsenal test/registry.test.ts test/resource-authority.test.ts
```

These cover registry identity, lazy handlers, native authority and source-relative fixtures. Native grammar builds and
compiled CLI or desktop qualification use their own repository lanes.
