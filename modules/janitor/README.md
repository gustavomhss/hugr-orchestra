# @orchestra/janitor

Janitor scans the data directory for growth, keeps the latest report and hands each report to a host-supplied sink.

## Purpose and ownership

- The scan (`src/scan.ts`) reads only: it runs an allowlist of read-only commands (`ps`, `df`, `du`, `lsof`, `docker`, `git`, and a few platform ones) and never deletes or kills anything.
- `src/scheduler.ts` and `src/thresholds.ts` decide when to scan and how severe a finding is; `src/report-state.ts` keeps the latest report; `src/bootstrap.ts` starts the loop.
- The desktop shows and dismisses reports from `apps/desktop/src/main/janitor.ts` and `apps/desktop/src/main/janitor-ipc.ts`.

## Public entry points and consumers

- Export keys `./bootstrap` (`startJanitorLoop(scope, sink, env)`, `enabled`, `configFromEnv`) and `./report-state` (`getLatestReport`).
- The sink is a parameter; the module never imports a bus.
- No package under `apps`, `packages` or `modules` imports it yet; only its own tests do.

## Dependencies and boundaries

Layer `product`: it may import foundation, native, library, contract, extension-api, module, platform and product packages, never composition or app packages.

## Assets, schemas and generated files

- No generated files. `src/scan.ts` defines the `Report` and `Finding` schemas.

## Persistence, identity and lifetime

- Nothing is written to disk. The latest report is held in process memory and cleared when the last loop user leaves its scope.
- One loop runs per process, shared by every `startJanitorLoop` caller. `ORCHESTRA_JANITOR=0` disables it and `ORCHESTRA_JANITOR_INTERVAL_MIN` sets the interval.

## Commands

- `bun run test:ci janitor` from the repository root.
- `bun typecheck` in this directory.
