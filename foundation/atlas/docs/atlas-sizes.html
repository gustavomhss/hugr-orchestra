O sweet spot de tamanho

O tamanho é a linha que separa overhead do que funciona. E não é um número só.

A arma anti-overhead: um teto global de injeçãoo que anda em TODO contexto tem um orçamento — a soma respeita o teto

O que é injetado compete com o contexto da tarefa a cada turno. Então não basta capar cada tipo: a soma de tudo que é auto-injetado tem um teto — uns ~3–5% da janela. Ultrapassou o teto = overhead. Abaixo, com o que é load-bearing = funciona.

Os dois drivers que fixam o tamanho 1. Injetado × frequência. Anda em todo turno → os menores (os três slabs do header: awareness ~400 + orientação ~250 derivados, + a memória de projeto ~500 escrita). Injetado às vezes (pack ao entrar num território) → pequeno-médio. Consultável (pago só no acesso) → pode ser rico.
2. Volatilidade × vida. Volátil e curto (manutenção/staleness) → pequeno, decai rápido. Estável e longevo (arquitetura) → o tamanho se amortiza, pode ser denso.

Como o sweet spot se ajustanão é chute fixo — é medido

Os números acima são ponto de partida. O sweet spot real é calibrado pelo ledger: cada tipo mede hits (quantas vezes evitou um erro / foi consultado). Se um tipo não move métrica, ele encolhe (ou decai do set ativo → arquivo). Se sistematicamente estoura seu cap com conteúdo load-bearing, sobe — com evidência, não por conforto. O overhead nunca é presumido; é medido e cortado.

A regra em uma linha Injetado: menor possível que ainda carregue o load-bearing. Consultável: rico o suficiente pra valer o acesso, capado pra não virar dump. O teto global é sagrado.
