Memória de Projeto

O caderninho de "sempre / nunca" de cada membro — sussurrado no ouvido dele a cada turno.

A memória de projeto é INJETADA, não consultada. Ela está sempre lá, em todo turno — o membro não pede.

INJETADA · memória de projeto

Entra sozinha em todo contexto do membro. Ele nunca pede — ela já está no prompt. Por isso tem que ser minúscula e só o essencial: se inchar, envenena cada turno.

CONSULTÁVEL · task · pr · logbook

Fica guardada; o membro pede quando precisa. Custa só no acesso, então pode ser rica. A de projeto é o oposto: pequena, porque o custo é pago sempre.

O que é injetado tem três slabs: Awareness · Orientação · Regras

No começo do turno o membro recebe três coisas — e elas não se misturam. As duas primeiras são compartilhadas + derivadas (não são memória escrita, então não podem apodrecer); só a terceira é uma memória escrita, privada dele.

AWARENESS · self-model do projeto · derivado do root

O que o projeto É: mission · constitution · terrain · ontology · taste. Um rollup dos nós de topo do Atlas (grounded, node@sha), byte-idêntico pra todo membro. Não é memória escrita — é montado do root, então nunca fica stale.

ORIENTAÇÃO · compartilhada · derivada do log

Onde o projeto está AGORA: goal + last/current + state. Vem do walt (goal) + fold sobre o event log (estado). Byte-idêntica pra todo membro, sempre atual, nunca envelhece.

REGRAS · privadas do membro · a ÚNICA escrita

As "sempre / nunca" que ELE aprendeu (o resto deste doc). A única memória de projeto escrita. Não compartilhada — a do charlie não polui o lucy.

awareness (rollup do root · byte-idêntica) ~400 tok 
# derivada do Atlas root — grounded node@sha, não escrita à mão

mission       sistema de billing idempotente ponta-a-ponta
constitution nenhum efeito de pagamento sem Idempotency-Key (T0)
terrain       gateway · worker · reconcile · ledger — T0: gateway, ledger
ontology      seat · território · pack · poke · tier · kit
taste         expand/contract · sem prosa livre · gate verde ou FAILED
orientação (montada · derivada do log) ~250 tok 
# injetada em TODOS, a cada turno — situational awareness barata

goal     migrar o billing pra idempotência ponta-a-ponta   (walt · Definição)
last     WP-12 · Idempotency-Key no gateway — selado
current  WP-13 · retries idempotentes no worker — em andamento
state    3/5 territórios de billing cobertos · falta worker + reconcile
Por que vale muito Awareness (o que o projeto É) + Orientação (onde está) são derivadas e byte-idênticas — situational awareness barata que mata o drift, sem nenhuma memória escrita pra apodrecer. Os três slabs cabem fácil sob o teto de injeção. O resto deste doc é a terceira slab, a única escrita: as regras.

Como é na prática

A memória de projeto do charlie (classe build). Cada linha é uma regra imperativa — "sempre" ou "nunca" — com o escopo onde vale e um contador de uso.

atlas/members/charlie/memory/project.md ≤ ~500 tok 
# regras que entram em todo turno do charlie

- nunca logar o header Authorization          scope: src/http/**   hits: 12
- sempre rodar `pnpm typecheck` antes de selar   scope: *             hits: 40
- migrations aqui são expand/contract só        scope: db/**         hits:  7

É isso. Três linhas que valem ouro, não três parágrafos. Específica e acionável — "nunca logar o Authorization", não "cuidado com segurança".

A estrutura pré-definida

Toda regra escreve contra este template fixo — nunca prosa livre. Quatro campos:

rule
uma linha imperativa. "sempre X" / "nunca Y". Sem narrativa.
scope
onde vale — um glob de path, uma fase, uma tool. É o que a torna relevante só onde importa.
grounding (opcional)
um ponteiro (arquivo@sha / PR / commit) que justifica a regra — de onde ela veio.
hits
quantas vezes evitou um erro. Ordena as regras e comanda o decaimento — a que não é usada, some.

Entra por promoção + barra de admissão. O set injetado é slot fixo: top-12 por hits. Sai por evicção — hits==0 em max(20 waves, 30 dias) → arquivo — nunca é deletada.

As regras que impedem virar lixo

1
Cap duro. ~500 tokens no total por membro (o orquestrador ~800). 1–2 linhas por regra. Estourou → não entra.
2
Imperativa e específica. "nunca logar o Authorization" entra; "cuidado com auth" é vago → recusado.
3
Slot fixo: top-12 por hits. o set injetado são as 12 regras de maior hits (orq pode mais, sob ~800). Não é só cap de token — é contagem de slot que ranqueia pra evicção.
4
Evicta, não morre. regra com hits==0 em max(20 waves, 30 dias) sai pro arquivo — versionada, re-spawnável. Nada se perde.
5
Por membro. a do charlie é do charlie; não polui o lucy nem o knowledge compartilhado. É memory, não knowledge.
6
Vem do trabalho. nasce de uma lição de task/pr que se provou geral — promovida de propósito, não inventada.
Injetada = o menor conjunto de regras que ainda carrega o essencial. Nada além disso anda em todo turno.
