1

O conceitoa verdade-fundamento do sistema — o que todo mundo lê antes de agir

O Atlas é a camada de conhecimento + memória do time: um substrato aterrado, content-addressed, que vive na pasta atlas/, viaja com o repo, e tem uma propriedade que nenhum wiki/KB de mercado tem — não pode mentir: todo fato re-checa contra o código, e apodrece sozinho quando o código muda.

É a fusão de três ideias normalmente construídas separadas — knowledge base + wiki à la Karpathy (cresce do trabalho) + open knowledge (exportável, sem lock-in). É a camada 0: DEFINE, DESIGN, o Conductor e os seats todos leem daqui em vez de inventar.

Por que é a fundação O motivo do v1 alucinar era não ter chão: cada fase re-derivava a realidade e inventava as lacunas. O Atlas é onde se lê em vez de adivinhar — e, como ler é mais barato e mais verdadeiro que re-derivar, é ao mesmo tempo a jogada anti-alucinação e a jogada de custo.
2

Knowledge ≠ Memory — dois tipos, um Atlasdistintos, nunca conflatados — mas não dois sistemas

KNOWLEDGE — compartilhado
  • Sobre o código. Aterrado a source@sha.
  • Leitura universal, mas owned (um dono escreve/cura).
  • Evolui por edição/supersede, não append.
MEMORY — por membro (+ orquestrador)
  • Sobre a experiência de trabalhar, não o código.
  • Escopada: task · pr · project · logbook (só orquestrador).
  • Privada do membro; o logbook é memory, nunca knowledge.
A fronteira que não pode borrar Misturar dá lixo dos dois lados: um grafo compartilhado cheio de palpite privado vira inoperável; craft privado tratado como verdade vira crença falsa. Mesmo substrato, dois kinds, nunca a mesma coluna.
3

Grounding — a lei que impede o apodrecimentoum fato nunca se declara verdadeiro

A única prova de verdade é uma citação que re-checa agora. E ela ancora numa unidade estrutural (símbolo/bloco), pelo hash BLAKE3 do subtree (sobre o trecho de código cru da unidade) — não em número de linha (frágil: um import acima drifta um fato que não mudou). Reformatar a própria unidade citada drifta o fato: o hash é sobre bytes crus, sem normalização — alarme falso aceito de propósito.

ancora estrutural · subtree-hash, não linha BLAKE3 · árvore de merkle nativa código muda → DRIFTED → BROKEN → bloqueia o merge começa vazio e honesto · T0 só humano

A barra de admissão — nada de knowledge inútil

Um fato pode ser verdadeiro e inútil (verdadeiro-mas-óbvio = ruído). Por isso entra só quem passa nas duas portas:

porta 1 · verdade
É verdade?

Cita source@sha que re-checa. Sem grounding → NA.

porta 2 · utilidade
Vale lembrar?

Muda uma decisão e não é derivável de só olhar. "retorna string" = lixo; "valida Idempotency-Key ou cobra 2×" = ouro.

Verdadeiro + inútil = ruído. As duas portas, ou não entra.
4

Sem embeddings, sem RAG — um índice hasheadoretrieval determinístico, não similaridade

Regra dura: zero embeddings, zero RAG. Um CAS content-addressed (estilo bazel) + a árvore merkle do BLAKE3 organiza tudo no nosso formato. Relevância se resolve por estrutura, em três modos determinísticos:

1. Por escopo (path) — resolve o path → nó(s), com rollup pela hierarquia. 2. Por dependência — segue arestas depends-on (blast-radius). 3. Por trigger/tag — protocolos cross-cut casam por match. O índice é o oráculo de drift (chaveia por subtree-hash).

As pastas — uma por membroum esqueleto, parametrizado por manifest · knowledge co-locado com o dono 

atlas/                     # no root do repo · versionado · anexado a commits/PRs
├─ index/                 # o índice hasheado — ponteiros p/ tudo
├─ archive/               # nada morre — decaído/fechado, deduped, re-spawnável
├─ log.jsonl              # event log append-only (a fonte do fold)
└─ members/
   ├─ charlie/            # ← UMA PASTA POR MEMBRO (esqueleto pré-definido)
   │  ├─ manifest.json    # classe · kit · escopo · caps/templates ← ONDE DIFERE
   │  ├─ knowledge/       # o que ELE possui (owner-write, shared-read)
   │  └─ memory/ { project.md (injetado) · task/ · pr/ }
   ├─ lucy/ bobby/ …       # mesmo esqueleto, manifest diferente
   └─ orchestrator/
      └─ memory/ { … · logbook.md ← só o orquestrador (memory) }
Co-locação A pasta guarda o knowledge que o membro possui + a memória dele. Escrita é do dono; leitura é universal. Efêmeros (jimmy-1..n) escrevem na pasta do membro — a pasta é a identidade do assento.

Memória — quatro tiposa lei: injetada = budget sagrado · consultável = pode ser rica

Tipo Acesso O que guarda
task consultável (sob demanda) o que tentou, o que falhou, onde parou (o fold), a lição de retry
pr consultável decisões do PR, resultado da review, o knowledge-delta
project INJETADA (todo turno) regras objetivas "always/never" — capada, template rígido
logbook (só orq) consultável o diário em prosa — ritual/PR · seções fixas · append-only
O cabeçalho injetado Além da project (regras do membro), o membro recebe a Orientação — goal · last · current · state — compartilhada e derivada do log (nunca escrita, nunca stale). Injetadas juntas, sob o teto.
Regra universal Toda entrada (memory e knowledge) escreve contra um template fixo — campos + cap + regras, nunca prosa livre. O logbook é a única forma narrativa, e mesmo ele é seções fixas + caps (prosa estruturada).

Calibrado, não chutado Os números são ponto de partida. O ledger mede hits; tipo que não move métrica encolhe (ou decai → arquivo). Overhead é medido e cortado, nunca presumido.
9

Versionado & vivo — nada morregit-native · anexado a commits e PRs · re-spawnável

O Atlas é parte viva do versionamento, não um sidecar. Vive dentro do host que o user usa (GitHub/GitLab/…): anexado aos commits (git notes + trailers) e aos PRs (via adapter de host). O que anexa não é o blob — é o índice hasheado (ponteiros), com o conteúdo no CAS.

nada morre · decay = sai do set ativo → arquivo per-agent · model, tokens, tools, tempo, retries, verdict re-spawnável · de um clone, outra máquina/fork fonte = git-native · o PR é uma vitrine
A reconciliação honesta Se vivesse só no GitHub, um clone noutra máquina não teria. Então a fonte de verdade é git-native (viaja em qualquer clone) e o PR é uma projeção renderizada no host. Aberto (teu): o corpo do transcript in-tree vs num CAS sidecar — commitar MB com segredo é irreversível.
10

Como chega até vocêaparece sozinho, "pokeando" — e como tool

O grafo se projeta numa superfície de MCP tools, proativa e escopada por lugar. Quando um LLM navega e cruza um escopo (file/pasta/módulo/crate), um hook injeta o pack daquele escopo (push) e expõe os nós como tools (pull). Só o escopo atual vira tools — retrai ao sair, senão os schemas estouram o contexto.

A tríade do SDK casa: Skill ensina a chamar · Hook injeta sozinho · Subagent isola o trabalho. Tudo determinístico (é o índice estrutural, sem RAG) — só empurrado na hora certa em vez de esperado.
