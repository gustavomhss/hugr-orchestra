O índice hasheado

O que anexa num commit ou PR são ponteiros, não blobs. Igual o git.

O conteúdo (knowledge + memory) mora num CAS — chaveado por hash. O que viaja anexado ao commit/PR é o índice: um mapa de ponteiros pra esse conteúdo.

CAS — onde o conteúdo mora

Todo objeto (nó estrutural, fato de knowledge, entrada de memory) é chaveado pelo seu hash BLAKE3. O store é hash → objeto. Content-addressed: mesmo conteúdo = mesmo hash (dedup + integridade grátis).

Índice — o que anexa

Um mapa de ponteiros (hashes) organizados na árvore merkle (repo→crate→…→bloco). Pequeno. É ele que gruda no commit/PR — não os blobs. Igual um commit git aponta pra uma tree de hashes.

Não é uma árvore — são eixoso que vem DENTRO de cada eixo · dual Merkle rollup · e TUDO é hasheado

É o subsistema mais duro do atlas. Não é UM caminho — são 3 eixos, cada um uma hierarquia própria sobre o mesmo objeto (guardado 1× no CAS, cruzado nos 3). Cada eixo responde uma pergunta diferente sobre o mesmo hash:

1 · spatiala árvore estrutural — o eixo da granularidade
Níveisrepo→crate→módulo→file→item→bloco. item=decl de topo (fn/struct/trait/class); bloco=unidade sub-item com subtreeHash próprio (corpo de método, match-arm, closure) — a âncora mais fina de um StructRef.
Deriva defile tree + parse AST; o subtreeHash é o hash do trecho de código cru da unidade (comentário e whitespace não são removidos — não existe normalizador). $0-LLM, determinístico.
Pendura
Knowledgefatos aterrados por StructRef nesse nó — a superfície primária de grounding ("essa fn TEM que valer X").
Memorytask/pr do membro, cruzada pelas unidades que ele tocou ("o que aprendi da última vez em cas.ts").
Respondescope (modo 1) — "tô nesse path, o que se sabe aqui e acima". O poke dispara ao entrar num escopo spatial.
2 · territórioposse + criticidade — NÃO é a file tree
Níveisprojeto→território (owner·tier)→região. território=unidade atômica de governança {owner:seat, tier:T0|T1|T2, members:StructRef[]}, pode cruzar files/crates; região=sub-zona nomeada dentro dele. Cada unidade pertence a exatamente 1 território (posse é partição).
Deriva demanifesto territories (globs→owner·tier) reconciliado com a árvore real — path sem território = flag; T0 default nega. Dado, não LLM.
Pendura
Knowledgeregras por tier, sem símbolo ("T0: nada de alloc sem bound"); o tier de ratificação (T0=só humano).
Memoryquem é owner → de quem é a memória que escopa aqui; Rules de projeto com scope=território surgem ao entrar; logbook cruzado por território tocado.
Respondegovernança/trigger — roteia review pro owner, aperta gate por tier, prioriza injeção (T0 injeta primeiro no teto), "me dá tudo que é T0".
3 · dependênciablast radius — um DAG, não uma árvore
Estruturanós=unidades; arestas=depends-on (import/call/type-ref). Fecho forward (o que preciso) + fecho reverso (quem precisa de mim = blast radius). Rollup aqui é alcançabilidade, não cadeia de pai.
Deriva deo grafo de import/call (tree-sitter / language-server). $0-LLM, determinístico.
Pendura
Knowledgefatos de contrato/interface que propagam pela aresta — mudou a assinatura, a premissa de todo dependente fica suspeita.
Memorymemória de "da última vez que essa API mudou, N callers quebraram" surge quando o fecho reverso é grande.
Respondedependência (modo 2) — editar X mostra fatos/memória ancorados em todo o fecho reverso de X; limita re-check ao fecho, nunca a N. É o eixo que pega drift transitivo: se um dep meu driftou, meu rState vira mesmo sem eu mudar 1 byte.

Dual rollup: cada nó carrega rId (estrutura) + rState (status+freshness). Um Delta diz se mudou a forma ou o estado, e onde — re-check só nos buckets afetados, nunca no store inteiro. O mesmo objeto é cruzado nos 3 eixos, nunca duplicado.

tudo é hasheado — inclusive os docs

Todo objeto vira CAS por BLAKE3: código · fatos · memória · proveniência · transcript · e os próprios docs. Os docs são objetos do atlas — aterrados, drift-checked (rosie). O atlas indexa a própria documentação. Dogfood literal.

O índice é anexado (git-native); o conteúdo mora no CAS. A fonte é git-native — o PR é uma projeção.

Onde grudanos objetos nativos do host

No commit

git notes (refs/notes/orchestra) + trailers — carregam o índice + proveniência (WP/model/verdict/transcript-SHA). Git puro, viaja com o objeto, vem em qualquer clone.

No PR

Via host adapter (GitHub/GitLab/…): o índice do knowledge-delta do PR gruda no PR de verdade. É uma projeção — a fonte de verdade fica git-native (re-spawnável de um clone).

Três propriedades que caem de graça

content-addresseddedup + integridade. O hash É o endereço; adulterou, o hash muda. Zero formato proprietário (estilo bazel).
git-nativeviaja e re-spawna. Índice + proveniência vivem no git (notes/trailers) → em qualquer clone, máquina, fork. Nada preso em nuvem de terceiro.
é o oráculo de driftum índice, dois trabalhos. Chaveia por subtree-hash → uma entrada stale aparece na hora da query. Mesmo índice serve retrieval e drift. Sem RAG.
Anexa o mapa (ponteiros), guarda o conteúdo no CAS. É o git aplicado a knowledge + memory.
