Test review as a dedicated domain: how should an expert reviewer judge the tests that come with a change, and the tests a change should have but lacks? Use primary sources (papers on test smells, test adequacy, the oracle problem, flaky tests; Google testing blog and "Software Engineering at Google" testing chapters; mutation testing literature).
Subquestions: (1) test adequacy: does the test fail without the change (fail-before/pass-after), coverage of changed lines and branches, mutation score on the diff, requirement-to-test traceability, missing negative and error-path tests; (2) test quality and smells: weak or absent assertions, assertion roulette, over-mocking and testing the mock, duplicated logic in tests, tests coupled to implementation, snapshot abuse, sleeps and timing, shared state, order dependence; (3) the oracle problem: how to judge whether an assertion checks the right thing, metamorphic relations, property-based oracles, golden files and their drift; (4) flaky tests: root-cause taxonomy (async waits, concurrency, order, time, network, resource leaks), detection by rerun and by static signals, quarantine policy; (5) test levels and strategy review: unit vs integration vs e2e balance, test pyramid vs trophy evidence, cost and runtime budgets, and this repository's own testing rules (AGENTS.md Testing section, test:ci, omni positive control, test-guard, no mocks/globalThis rule) that a reviewer must enforce.
