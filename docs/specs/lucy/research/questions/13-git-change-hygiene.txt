Git and change hygiene as a review domain: what should a best-in-class reviewer check about how a change is made, not only what it does? Use primary sources (git documentation, Linux kernel and Git project contribution rules, Google/Meta stacked-diff practice, papers on commit quality and tangled changes).
Subquestions: (1) commit and PR structure: atomic commits, tangled changes and how to detect and split them, commit message quality and conventional commits, PR size limits, stacked diffs (Phabricator, Graphite, ghstack, git-branchless, Sapling, jj); (2) history and archaeology as review evidence: git blame, log -S/-G, bisect, prior reverts and hot files, code ownership (CODEOWNERS) and churn as risk signals; (3) merge mechanics risks: rebase vs merge, semantic merge conflicts that compile but break, conflict-resolution review, merge-queue semantics and the "rerun at old head" trap, cherry-picks and backports; (4) integrity and provenance: signed commits and tags (GPG, SSH, Sigstore gitsign), author identity, force-push protection, branch rulesets, secrets accidentally committed and history rewriting; (5) scope discipline checks: unrelated edits, generated files edited by hand, lockfile drift, vendored code, whitespace/format-only noise, and which of these this repository already guards (check script/, .github/workflows, guardrail rules, AGENTS.md).
