# R03 — native backend-agent plugin seams

**Verdict:** standalone backend profile, packaged skills, tools, and ordinary delegation fit existing V1 plugin mechanisms. Full Maestro-native placement plus native shared Atlas Knowledge+Memory needs host seams. Fork V2 supports profile/skill transforms, but does not supply equivalent plugin, MCP, or delegation capabilities. Keep Orchestra as model executor; Atlas remains shared data authority.

Research-only; source inspection, not runtime certification. Tests below are proposed, not executed.

## 2. Already supported extension paths

### V1: practical initial target

- **Package/local plugin:** async function returning `Hooks`, or module with `server`; options accepted. Initialization supplies SDK client, project, directory, worktree, server URL, Bun shell, and experimental workspace-adapter registration. Workspace adapters describe targets; they do not register agents or confer delegated authority. Loader runs plugins/hooks sequentially and invokes mutable `config` hooks. Bootstrap explicitly awaits plugin initialization before other services ([public API](packages/plugin/src/index.ts#L26-L80), [loader](packages/orchestra/src/plugin/index.ts#L115-L125), [config hooks](packages/orchestra/src/plugin/index.ts#L245-L254), [bootstrap](packages/orchestra/src/project/bootstrap.ts#L32-L45)).
- **Independent agent:** populate `config.agent[stableID]` with prompt, description, `mode: "all"`, model preferences, and permissions. Generic configured agents already preserve distinct `id`/display `name`; `all` supports primary selection and Task discovery. Direct operation needs no Maestro workflow. Ordinary Task creates native Orchestra child Session and calls existing prompt executor; it does not need another model loop ([agent merge/default](packages/orchestra/src/agent/agent.ts#L310-L395), [Task catalog](packages/orchestra/src/tool/registry.ts#L303-L329), [child creation](packages/orchestra/src/tool/task.ts#L383-L400), [execution](packages/orchestra/src/tool/task.ts#L529-L542)).
- **Tools:** return `Hooks.tool` using exported `tool()`/Zod; tool result supports text, metadata, attachments, cancellation, and permission requests. Local `{tool,tools}/*.{js,ts}` discovery also works. Registry wraps tools into existing execution/truncation path ([definition](packages/plugin/src/tool.ts#L1-L54), [registration](packages/orchestra/src/tool/registry.ts#L139-L222)). Tools may invoke installed Python/Go/JVM/.NET/Rust/etc. executables; JS/TS plugin entrypoint does not restrict backend language.
- **Packaged skills:** npm installation alone does not advertise package assets. Add absolute package-relative skill directory to `config.skills.paths` during config hook, or install assets into discovered skill directories. Resolve assets from package module URL, not process CWD. V1 scans `SKILL.md`, indexes frontmatter `name`, advertises described/permitted skills, and loads body on demand ([discovery](packages/orchestra/src/skill/index.ts#L179-L277), [indexing](packages/orchestra/src/skill/index.ts#L124-L145), [availability](packages/orchestra/src/skill/index.ts#L356-L391), [loading](packages/orchestra/src/tool/skill.ts#L54-L97)).
- **Commands/MCP:** `config.command` provides slash-command templates; MCP prompts and discovered skills also become commands. MCP local config supports command argv, CWD, environment; remote connections also exist. Server/tool names are normalized into effective tool IDs. Use native MCP or thin native tools over Atlas operations ([commands](packages/orchestra/src/command/index.ts#L90-L152), [MCP launch](packages/orchestra/src/mcp/index.ts#L340-L381), [tool mapping](packages/orchestra/src/mcp/catalog.ts#L42-L82), [names](packages/orchestra/src/mcp/catalog.ts#L117-L119)).
- **CLI distinction:** slash commands and TUI command/keymap registration are not new `orchestra <subcommand>` registrations. V1 CLI uses explicit yargs command list; fork V2 CLI also uses explicit handlers. Package can ship its own binary, invoked through existing shell/tools. No top-level CLI extension is needed for this backend profile ([V1 CLI](packages/orchestra/src/index.ts#L64-L257), [TUI API](packages/plugin/src/tui.ts#L86-L120), [V2 CLI](packages/cli/src/index.ts#L10-L25)).

### Fork V2: separate, partial contract

- Default export `{ id, effect }` or `{ id, setup }`; configured through `plugins` strings/objects. Local discovery scans direct `{plugin,plugins}/*.{ts,js}`. Loader forks activation and ignores external load failures; current docs' package-directory discovery/reload/management promises cannot be imported wholesale ([loader](packages/core/src/config/plugin/external.ts#L15-L89)).
- Public Effect and Promise contexts expose **options, agent, aisdk, catalog, command, integration, plugin, reference, skill**. Agent transforms update profiles; skill transforms register directory, URL, or embedded sources; registrations are scoped to plugin lifetime ([Effect context](packages/plugin/src/v2/effect/context.ts#L12-L22), [Promise context](packages/plugin/src/v2/promise/context.ts#L12-L22), [host implementation](packages/core/src/plugin/host.ts#L20-L42), [skill host](packages/core/src/plugin/host.ts#L208-L217), [skill sources](packages/schema/src/skill.ts#L8-L54), [lifecycle](packages/core/src/plugin.ts#L43-L96)).
- **Not public V2 plugin capabilities here:** tool registration, MCP registration, session hooks/client, storage, System Context registration, or placement metadata. Core canonical tool registration exists, including embedding API `orchestra.tools.register`, but that is a host-composition API, not plugin context ([registry](packages/core/src/tool/registry.ts#L16-L31), [SDK-next](packages/sdk-next/src/orchestra.ts#L10-L42)). Core tool instructions explicitly record plugin/MCP integration gaps ([architecture](packages/core/src/tool/AGENTS.md#L55-L59)).
- V2 command transforms populate template catalog; this is not current docs' executable command API. Session interface has no command operation; user-invoked `shell`/`skill` methods return `OperationUnavailableError`, while model-called skill tool is implemented. Built-in V2 tools still list Task as remaining work; Maestro roster is V1-side ([command schema](packages/schema/src/command.ts#L8-L15), [Session API](packages/core/src/session.ts#L113-L180), [unavailable methods](packages/core/src/session.ts#L387-L392), [built-ins](packages/core/src/tool/builtins.ts#L18-L47)). **Agent registration alone does not provide V2 Maestro delegation.**

## 3. Identity, display names, and placement

**Concrete mismatch:** V1 public `ToolContext.agent` is populated with **display name**. Internal context also carries stable `agentID`, but public plugin type does not declare it. Conversely `chat.params`/`chat.headers` receive stable ID when available. System-transform hook gets only optional Session ID and model; agent-generation also calls it without Session ID. Per-session startup cache cannot reliably identify selected agent for every later turn ([tool type](packages/plugin/src/tool.ts#L3-L19), [actual values](packages/orchestra/src/session/tools.ts#L64-L72), [request hooks](packages/orchestra/src/session/llm/request.ts#L68-L73), [stable request ID](packages/orchestra/src/session/llm/request.ts#L114-L142), [agent generation](packages/orchestra/src/agent/agent.ts#L431-L432)).

V2 Session schema already contains `agent`, `parentID`, `projectID`, and `location`; Location carries directory plus optional workspace identity. Runner checks placement before selecting agent. Public plugin context exposes neither instance Location nor invocation identity. Core `SystemContextRegistry.load()` takes no Session/agent input: Location scope alone cannot select owner-specific Memory ([Session](packages/schema/src/session.ts#L19-L44), [Location](packages/schema/src/location.ts#L8-L21), [runner](packages/core/src/session/runner/llm.ts#L168-L203), [registry](packages/core/src/system-context/registry.ts#L7-L15)).

**Maestro integration is stronger than ordinary delegation.** Roster freezes canonical `backend` seat, display name, prompt, profile, and return contract. Agent config for native seats accepts only model/variant/temperature before returning; name, prompt, mode, disable, and permissions are ignored. Native execution profile allows read/glob/grep/bash/edit, therefore denies skill and MCP/custom Atlas tools unless deliberately admitted. Invocation permission checks reapply native profile. Authorized Task additionally requires native Maestro and exact routed-seat/task binding; injects verified context skills and revalidates before model execution ([roster](packages/orchestra/src/maestro/roster.ts#L10-L63), [native profile creation/lock](packages/orchestra/src/agent/agent.ts#L291-L317), [permission enforcement](packages/orchestra/src/session/tools.ts#L60-L103), [authorization](packages/orchestra/src/tool/task.ts#L182-L208), [context handoff](packages/orchestra/src/tool/task.ts#L480-L542)).

Generic V1 names already support env-driven config through `{env:VAR}` or plugin initialization; missing substitution becomes empty string. Native seat names remain hardcoded, and V2 agent/config schemas have no separate display-name field. Current backend specialist prompt also hardcodes persona. Keep canonical IDs/Atlas owners/receipt bindings stable when labels change; explicitly keep Maestro label fixed ([substitution](packages/orchestra/src/config/variable.ts#L33-L38), [V2 agent](packages/schema/src/agent.ts#L19-L36), [V2 config application](packages/core/src/config/plugin/agent.ts#L88-L111), [the backend specialist prompt](packages/orchestra/src/agent/prompt/backend.txt)).

Presentation seam also needs attention: Orchestra Agents page selects entries and seeds chat drafts with `.name`; V1 normalization preserves incoming names, while V2 normalization copies `id` into `name`. Configurable display labels therefore need stable-ID routing through UI normalization/draft creation, not only server schema changes ([normalizer](packages/app/src/context/global-sync/utils.ts#L15-L36), [selection](packages/app/src/orchestra/chapters/agents.tsx#L47-L52), [draft creation](packages/app/src/orchestra/chapters/agents.tsx#L182-L192)).

## 4. Atlas: existing substance, missing native admission

**Knowledge path exists:** `maestro.atlas` selects project-bound static catalog/Own snapshot. Host verifies project, repository containment, source ancestry/blob hashes, artifact bytes, graph coverage, budget, and skill-cache correspondence. `skill({ name: "own_…" })` uses same verifier; it is not intrinsically Maestro-only execution, but configuration is Maestro-namespaced. Authorized delegation sends verified skill bodies as synthetic child prompt parts ([source verification](packages/orchestra/src/maestro/atlas-source.ts#L33-L130), [Own admission](packages/orchestra/src/maestro/atlas-source.ts#L136-L187), [skill route](packages/orchestra/src/tool/skill.ts#L35-L52), [Task handoff](packages/orchestra/src/tool/task.ts#L497-L542)).

**Memory implementation also exists, separately from that handoff:** Atlas composition builds durable Memory, Orientation, Awareness, owner-bound emit/read adapters. `memoryHeader()` yields shared Awareness/Orientation plus that owner's ranked project rules; task/PR/logbook memory requires explicit recall. Writes preserve native template, owner, cap, scanner, and append rules. MCP advertises real Memory read tools plus governed emit; CLI/MCP share composition. Stale “NO PRODUCTION CALLERS” headers in memory files are contradicted by current composition—do not cite those headers as absence evidence ([composition](foundation/atlas/packages/adapter-io/src/compose.ts#L361-L381), [read exports](foundation/atlas/packages/adapter-io/src/compose.ts#L579-L588), [header/recall](foundation/atlas/packages/adapter-io/src/memory-read.ts#L186-L205), [write admission](foundation/atlas/packages/adapter-io/src/memory-emit.ts#L116-L235), [MCP Memory](foundation/atlas/packages/mcp-server/src/server-memory-tools.ts#L25-L121)).

**Current host gap:** inspected Orchestra adapter admits static Own, not Atlas running-turn Memory header. Generated Atlas boundary exports catalog/Own verification, not Memory ports. V2 assembles registry + skill + reference context, then persists Context Epoch before provider dispatch. Add Atlas at that admission boundary, not through duplicate transcript/memory machinery ([boundary exports](packages/atlas-boundary/src/generated/boundary.d.ts#L55-L115), [assembly](packages/core/src/session/runner/llm.ts#L168-L239), [epoch persistence](packages/core/src/session/context-epoch.ts#L40-L88)).

**MCP identity trap:** `atlas-mcp` composes once from process CWD; Atlas resolves actor from `ATLAS_ACTOR`, then local git email. Orchestra's MCP call sends tool name/arguments, not trusted selected-agent identity. One generic MCP process therefore does not automatically provide per-seat headers/writes. Actor is local attribution, not authenticated identity ([Atlas process](foundation/atlas/packages/mcp-server/src/bin.ts#L16-L47), [actor resolution](foundation/atlas/packages/adapter-io/src/compose.ts#L133-L170), [MCP call](packages/orchestra/src/mcp/catalog.ts#L53-L66)).

## 5. Proposed minimal seam changes — not implemented

1. **Adopt one backend profile into existing seat.** For initial V1 target, let host bind plugin-supplied canonical `backend` profile as existing backend seat; use `mode: "all"` for direct selection. Apply host-owned delegated restrictions/return contract when dispatched. Change native-seat early return rather than duplicating backend logic or granting arbitrary plugins `native` authority. Add env/options-derived display labels for non-Maestro seats and render persona from label. Preserve canonical IDs and authorization hashes; route UI selection/drafts by ID while rendering label. If V2 becomes supported target, add separate display-name field through Schema/config/client generation and preserve it in UI normalization.
2. **Expose exact invocation identity.** Add typed stable `agentID` to V1 plugin ToolContext and selected-agent identity to system-transform input at request preparation. Include host-derived Session/project/parent/Location context where Atlas adapter needs it. Add read-only instance Location to V2 public context separately; instance placement is not a substitute for per-turn placement.
3. **Share Atlas through host-owned access/admission.** Lift existing project binding/verifier behind reusable Atlas access seam, independent of Maestro lifecycle; retain compatibility with `maestro.atlas`. Reuse Atlas Memory read/emit ports and stores, with explicit host-derived actor/root input instead of mutating process-global env. V1 can use identity-aware request hook/native tools. V2 minimal path adds session-aware Atlas producer beside `skillGuidance`/`referenceGuidance` in runner; zero-argument Location registry cannot supply owner scope. Keep Context Epoch persistence Session-owned. Define agent-switch retirement/replacement explicitly so former owner's admitted rules are not retained as current rules.
4. **Expose only needed data tools.** V1 already has tool/MCP loading; deliberately admit selected Atlas/skill actions into delegated profile. V2 would need plugin-to-canonical-Tools bridge with scoped cleanup and leaf permission checks. Full V2 Maestro delegation also needs missing Task/host integration; treat that as separate compatibility work, not a hidden plugin feature. CLI extension and new model runtime are unnecessary.

Maintain dependency direction: Schema → Core/Protocol → Server; Client runtime stays Schema/Protocol-only. Public Protocol/HttpApi changes require generated Client regeneration, not handwritten generated code ([AGENTS.md](AGENTS.md#L1-L3)).

## 6. Compatibility traps and missed framing

- **Three different “V2” labels:** legacy SDK `/v2`, fork plugin `/v2`, and current official V2 docs are not interchangeable. Fork agent defaults remain `all`; current V2 docs say `primary`. Fork skill tool takes `name`, not current docs' `id`; frontmatter names remain identity ([agent defaults](packages/schema/src/agent.ts#L33-L36), [skill parsing](packages/core/src/skill.ts#L73-L101), [skill input](packages/core/src/tool/skill.ts#L17-L19)).
- **Discovery ≠ refresh:** V2 `skill.reload` replays source state but leaves loaded-content cache intact; same-path or same-name replacements need explicit cache invalidation/restart testing ([cache](packages/core/src/skill.ts#L107-L127)). V1 duplicate skill names load concurrently; avoid collisions ([V1 load](packages/orchestra/src/skill/index.ts#L279-L287)).
- **Shared does not mean automatically cross-worktree.** Memory log is `<repoPath>/.atlas/memory.jsonl`; isolated checkouts give separate files. Decide canonical project store vs explicit branch reconciliation, while preserving worktree-specific Knowledge freshness. Session epoch snapshots are admitted context evidence, not a second writable Memory authority ([store path](foundation/atlas/packages/adapter-io/src/memory-store.ts#L25-L46)).
- **Polyglot execution ≠ polyglot semantic proof.** Native file/shell tools can work across languages; Atlas AST refinement currently loads TS/TSX grammars only. Ship language/framework skills selected from repository evidence and use installed native test tools; report unsupported semantic coverage rather than claiming complete graphs ([AST dispatch](foundation/atlas/packages/adapter-io/src/ast.ts#L38-L49), [extensions](foundation/atlas/packages/adapter-io/src/ast.ts#L83-L97)).
- **Atlas data service ≠ automatic mining runtime.** `atlas mine` has separate operator-configured model-command proposer. Do not silently activate that from backend plugin. Any needed model reasoning stays in existing Orchestra Session execution; data reads/writes reuse Atlas gates ([mine proposer](foundation/atlas/packages/cli/src/mine-proposer.ts#L266), [model command](foundation/atlas/packages/adapter-io/src/model-config.ts#L94-L119)).
- **Role prose ≠ execution control.** Current “Forbidden: merge” prompt coexists with broad `bash: allow`. Native flag, display label, skill prose, and catalog visibility are not interchangeable with operation authorization. Direct use, ordinary Task, authorized Maestro dispatch, and explicitly governed approval are distinct operating modes—not every backend invocation needs approval.

## 7. Meaningful verification plan

Proposed tests exercise host boundaries; positive fixture plus deliberately broken counterpart for each contract:

1. Load actual packaged V1/V2 entrypoints with distributed skill assets; list agent/skills, call tool, unload/reload. Invalid export/missing asset must be distinguishable from successful activation. Existing starting points: [V1 plugin-agent regression](packages/orchestra/test/agent/plugin-agent-regression.test.ts#L40-L51), [V2 loader tests](packages/core/test/config/plugin.test.ts#L19-L149).
2. Run same backend profile directly without Maestro, through ordinary Task, and through authorized Maestro dispatch. Capture actual native provider request, child identity, permissions, and return card. Wrong routed seat, stale context, or mismatched task intent must reject before provider work.
3. Rename all non-Maestro labels through environment, including spaces/Unicode; stable agent IDs, task routing, Memory owner, and receipts stay identical. Maestro stays fixed. Test two agents sharing display label to expose name-as-identity bugs; exercise public ToolContext, system hook, and Agents-page draft selection.
4. Use real Atlas stores: owner project rules differ; shared Awareness/Orientation match; task/PR/logbook require explicit recall. Native Memory emit/recall round-trip survives restart. Tampered Own blobs, wrong project/root, scanner unavailable, over-cap, and wrong owner exercise actual refusal paths ([existing Own fixtures](packages/orchestra/test/maestro/atlas-source.test.ts#L70-L123)).
5. Capture outgoing context across tool continuation, steer/queue promotion, exact prompt retry, agent switch, compaction, and source unavailability. Confirm epoch replacement/updates and actor isolation; no duplicate Memory writes from replay. Existing [System Context tests](packages/core/test/system-context/) and [Session runner tests](packages/core/test/session-runner.test.ts) provide relevant harnesses.
6. Exercise real MCP stdio and CLI against same Atlas root, then separate worktrees/projects. Check normalized names, per-invocation attribution, cancellation, and exact store binding. A single startup `ATLAS_ACTOR` must not pass as multi-agent identity support.
7. Real small TS, Python, Go, Rust, JVM, and .NET backend fixtures: select correct skills/test commands, assert missing toolchain diagnostics, and distinguish unsupported semantic indexing from successful execution. Fail test by removing source registration or swapping actor/root—not by mocking expected answer.

Run future checks from package directories. Research performed no implementation or runtime-test claims.
