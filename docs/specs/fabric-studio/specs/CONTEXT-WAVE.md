# Contexto local real — demanda do próximo recorte backend

**Estado:** preparação de aceitação; contratos provisórios do lead, ainda sem freeze para implementação. Não é C07, login, capítulo UI nem entrega integral. O parent contém o preflight em qualificação; só será integrado após seu gate final. Este recorte cria apenas controles de routing/admissão, sem nomes, composições, consultas, tokens ou payload Fabric em disco.

## Contrato proposto para esta suite

`FabricContexts.make({ operators, root, maxContexts? })` consome Database e Project reais; produz `list(query)`, `preparing(query)`, `create({})`, `resolve(ref)` e `remove(ref)`. Wire canônico em Schema/FabricContext: Info `{context: Ref, location: Location.Info}`, Page `{items: Ref[], after?}`, Query `{after?, limit?}`, Create vazio fechado e Failure com códigos fechados. Domínio fica em modules/fabric; Core tem somente SQL gerado, sem import runtime de produto. Pure parse/contracts/declaration não importam o serviço ou o host.

- Root é configuração confiável do host. Serviço captura seu realpath e Project real após provisionar a raiz privada (0700); aquisição não cria contexto ou workload. Paths de contexto são exclusivamente `root/<id emitido>`, sem workspaceID explícito e sem exigir Git. Resolver Project.global não autoriza combinar contextos.
- O serviço exige Database.storageID não vazio; falta dele é unavailable, nunca namespace inventado. Cada row prende storageID, principal do frame real, root canônico, ID/generation/estado e o placement publicado. Esses controles privados nunca aparecem em DTO/recibo público.
- Ações de bootstrap têm alvo de controle `{projectID: projeto observado da raiz, location: {directory: raiz}, resource?: ...}`. `list/preparing/create` exigem ações `fabric.context.list/list/create` nesse placement. `resolve` exige `fabric.context.read` na raiz e no placement concreto observado, resource `{kind:'fabric.context', id}`, antes de projetar. `remove` exige `fabric.context.delete` na raiz e owner/store/root/ref atuais, mas não abrir a pasta danificada: revoga só o controle local, para permitir cancelar preparo ou excluir uma referência cuja pasta sumiu. Esta autoridade de controle não autoriza operação Microsoft. A fábrica Core e seus frames privados são reais; não aceitar principal/grant vindos do JSON.
- Cada leitura revalida owner/store/root/ref generation/estado e placement atual. Owner errado ou ID desconhecido produz denied indistinguível; referência desatualizada/tombstone de owner atual produz expired. Falha/alteração de filesystem é unavailable. Nunca recriar diretório/contexto em GET/list/resolve. List retorna só refs ativas do owner atual/store/root em ordem lexicográfica de ID, default 16, máximo 32, `after` exclusivo; retorna cursor apenas se houver outra página.
- Create e remove exigem idempotencyKey do frame. Reusar CapabilityRequest para admitir a reserva SQL-only e guardar recibo redigido **somente Ref `{id,generation}`**, sem filesystem/network no callback SQL. Metadados próprios do ledger continuam privados no ledger; seu outcome não duplica owner/store/root/nonce. Reserva `preparing` não aparece no list; quota conta preparing+active por owner/store/root, default e máximo 64, override positivo seguro só pelo host.
- Criação reserva ID/generation 1 e nonce de preparo sob autoridade atual; só então prepara a pasta fora da transação. Marker privado `.orchestra-fabric-context` tem o ID e nonce exatos da reserva; não é grant. Criar o marker usa exclusividade e mode 0600, sem sobrescrever arquivo. Leitura valida tamanho máximo de 1 KiB antes de alocar conteúdo, rejeita symlink e valida o objeto fechado `{id, nonce}`. Diretório preexistente só pode ser retomado se diretório real, sem symlink, e marker exato da reserva. Unmarked/incompatível é unavailable, não adoção ou limpeza automática. Erros não ecoam conteúdo do marker, nonce ou mensagens brutas de I/O/SQL.
- Publicar exige nova transação que revalida frame/owner/reserva/estado e placement real capturado fora dela. Dois criadores com a mesma chave usam o mesmo ID/pasta; concorrência nunca publica duas rows. Replay após reconstruir serviço usa a intenção durável com autoridade atual, não memória singleflight. Retry de intenção cujo contexto já foi excluído falha expired; não ressuscita. Nenhum comando Fabric é reexecutado por esse retry local.
- Remove é tombstone local, não apaga diretórios ou dados remotos. Transação incrementa generation uma vez, invalida ref antiga e libera quota de ativo/preparo; replay exato do mesmo remove retorna o mesmo tombstone. Nova chave tentando excluir ref já inválida não fabrica novo sucesso. Capacidade do ledger existente também limita o número de admissões; nenhuma política de purga é introduzida por conveniência.
- Reservas não podem ficar inacessíveis quando o cliente perde uma resposta/chave ou o preparo encontra uma pasta incompatível. `preparing(query)` usa a mesma autorização `fabric.context.list`, pagina somente refs preparando do owner/store/root e não retorna Location. Owner pode cancelar explicitamente pelo `remove(ref)`; isso libera quota sem apagar diretório e impede o criador interrompido de publicar o ID cancelado. Retry continua explícito; listar ou cancelar não conclui o preparo nem inicia efeito remoto. Nenhum nonce, request key ou grant é projetado por essa recuperação.

| FCT02 | Frame Core válido permite; ausência de frame, factory alheio, autoridade revogada e scope insuficiente falham antes de nova reserva/pasta. Testar códigos, não só qualquer erro. |

| FCT04 | Mesmo idempotencyKey concorrente + retry com novo serviço/banco no mesmo arquivo produz um contexto e um marker; idempotencyKey ausente recusa antes do write; chave conflitante do ledger não é replay. |
| FCT05 | Pausar a entrega de um commit SQL real depois da reserva, interromper o primeiro caller e reconstruir serviço; reserva não listada como ativa, retry explícito conclui o mesmo ID, sem FS no callback de admissão. O instrumento delega queries/rows/commit reais e prova que a barreira foi atingida. |
| FCT06 | Remover pasta, trocá-la por arquivo ou symlink divergente, adulterar marker ou placement persistido bloqueia resolve sem reparo, adoção ou escrita fora da raiz. Sentinels externos permanecem iguais. |
| FCT07 | Limite pequeno real conta preparar/ativo; ultrapassar falha sem novo mkdir. List pagina sem duplicar/perder refs; remove invalida generation e libera quota sem apagar pasta; retry remove é estável e create retry não ressuscita. |
| FCT08 | Create/query/refs inválidos ou com campos extra não autorizam owner/path/Location; missing storageID, raíz inválida e quota inválida não ativam serviço. Schema opcional omite undefined, IDs canônicos e closed DTOs reais. |
| FCT09 | Reserva real pausada depois do commit aparece só em preparing sob autoridade atual; outro owner não a lista/cancela. Cancelamento explícito gera tombstone, libera quota e bloqueia publicação tardia do mesmo criador; não cria Location pronta nem apaga dados. |
| FCT10 | Revogar uma autoridade Core emitida depois da reserva real e antes da publicação impede estado ativo; autoridade configurada atual ainda pode descobrir/cancelar o preparo. |
| FCT11 | Preparo encontra pasta não marcada ou marker incompatível: recusa sem alterar sentinels/marker, permanece recuperável/cancelável; marker exato do ID+nonce da reserva é o controle de retomada permitida. |
| FCT12 | Prepares reais atravessam página default/limite/cursor sem serem Locations ativas; queries inválidas são recusadas. O observador de commit distingue a nova reserva das anteriores sem substituir rows/serviços. |
| FCT13 | Após o preparo real e antes da transação de publicação, cancelamento ou revogação bloqueiam a publicação tardia. Barreira delega callback/resultados SQL reais e prova que o marker exato já existe. |
| FCT14 | Duas intenções com chaves distintas chegam à admissão antes de iniciar as transações reais; quota 1 aceita uma e recusa a outra sem segunda pasta. O limite é decidido na transação SQL, não por count anterior ou mutex global de pedidos. |
| FCT15 | Churn real com quota 1 atravessa 64 recibos sem purgar/substituir os anteriores; remove antigo continua replay estável e create excluído continua expired. |

Fixtures usam Database/Project/CapabilityOperator e filesystem reais com roots sintéticos; sem credentials/keychain/network ou runtime instalado. Não criar tabelas manualmente para fingir integração: Database.layerFromPath deve materializar a migration gerada real. Uma barreira de ordenação pode envolver o cliente SQL real, delegando resultados intactos como CCT01; não mockar o serviço Fabric. Testes só em test:ci, nunca nesta máquina.

Antes do freeze: materializar testes, criticar demanda+suite independentemente, comprovar RED nas operações do scaffold (não imports), congelar mínimo compartilhado e definir seams de implementação. Integração HTTP e entrada Solid serão gates separados e depois exercitados juntos; este recorte não satisfaz BSC08/BSE ou S01 sozinho.

**Prova composta do limite do ledger:** a política pertence a Core/CapabilityRequest, não será duplicada em Fabric nem copiada como outro número. Revisão fria obrigatória inspeciona todas as mutações SQL do serviço: somente criar/atualizar controles, nenhuma purga de recibos, e fábrica CapabilityRequest sem override de `maxReceipts`. O gate Core `capability-request.test.ts` exercita quota finita e retry entre handles/principals; deve executar junto à qualificação afetada, além de FCT15 no domínio. Testar mais um limiar N de purga não prova ausência em todo N; a ausência é obrigação de revisão integral da fonte, assim como SQL-only e limites de leitura de arquivos. Isso não dispensa a recusa de capacidade do ledger real nem autoriza Fabric a alterá-la.
