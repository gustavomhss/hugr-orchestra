## Destinos e autoridade

`FabricIdentityDiscovery.make({profile, network?, timeoutMs?})` interno sem package export/DTO/tool. `load()` sem parâmetros busca somente `https://login.microsoftonline.com/organizations/v2.0/.well-known/openid-configuration` e `https://login.microsoftonline.com/organizations/discovery/v2.0/keys`, por GET sem body/auth/cookie/client cert no request nativo. Não aceita URL/kid/tenant/nonce/headers do chamador. Metadata deve declarar issuer público template, authorization/token endpoints organizacionais exatos, jwks_uri exato e RS256 suportado. Nenhum endpoint extra da metadata (userinfo, mtls alias, rbac) é seguido. Mudança de metadata/JWKS é falha, não fallback para common/Graph/URL do token. Public cloud/organizational v2 apenas; claims-mapping appid, soberano e B2C seguem unsupported.

Origem observada por GET público sem credenciais em 2026-11-06 via webfetch externo, não runtime do produto: `organizations` metadata declarou jwks_uri **organizations/discovery/v2.0/keys**, issuer `https://login.microsoftonline.com/{tenantid}/v2.0`, auth/token endpoints esperados e RS256. Não trocar por common por suposição. Referência oficial reaberta: https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens#validate-tokens — multitenant exige issuer/tid/issuer da chave coerentes; access tokens Microsoft são opacos para o client. Não usar IDV como validador de access token.

`network` opcional é configuração **somente do host confiável**, nunca workspace/request: endereço IP literal, porta válida e CA PEM opcional limitada a 64 KiB. Não contém código, URL, headers, chave/certificado cliente ou flags TLS. Permite rota administrada e fixture TLS local; SNI/hostname de certificado/Host e paths continuam Microsoft fixos. O host já pode fornecer chaves a IDV; confiança nessa configuração não nasce de request ou declaração. Default não a fornece e usa DNS/trust nativos, TLS >=1.2, rejectUnauthorized/checkServerIdentity explícitos, agent false, sem cookies/proxy/auth/client TLS extra. CA/rota customizadas pertencem à base de confiança do host; não vender fixture como Microsoft ou trust store padrão. Provas locais não qualificam proxy corporativo/distribuição.

**Correção arquitetural antes da qualificação final:** a proposta de Agent customizado foi substituída por parâmetros nativos explícitos de conexão depois de o controle demonstrar zero chamadas ao hook e recebimento de metadata pública real, sem credenciais. Não aceitar esse resultado como TLS local. O caminho alternativo Bun.fetch foi experimentado, não ficou no candidato final. O diagnóstico intermediário de socket do cliente vazando foi retirado: a fixture recebia EOF do peer e mantinha sua própria metade de escrita aberta. O oracle final Linux cruza `/proc/net/tcp` com `/proc/self/fd`, encontra **um descritor cliente real antes de interromper e nenhum depois**, antes de a fixture liberar sua metade. Scope também limpa sockets TLS ainda em handshake. Isso qualifica cleanup local, não heap/budget de produto. Os testes contam spawns reais pelo contador Omni; o bunfig Fabric não preloada o controle global Core, então não afirmar verdict global inexistente.

## Transporte finito e publicação

Native `node:https` não segue redirect; somente status 200, content-type application/json (charset utf-8 opcional), content-encoding identity/ausente, headers até 16 KiB. Metadata até 64 KiB e keys até 256 KiB, limite medido nos chunks reais mesmo sem Content-Length; conteúdo UTF-8 estrito/JSON válido e response.complete obrigatório. Não imprimir body/URL upstream/erro TLS. Timeout total por request default 10 s, host pode reduzir dentro de 100–10000 ms; interrupção/erro/limite encerra request/resposta/socket, sem retry automático. Esses limites iniciais não são medição de orçamento de produto.

load cria um verificador IDV real somente depois de duas respostas íntegras e chaves públicas finitas válidas. Cada chave remota exige issuer próprio público template ou UUID-v2 exato; chave sem issuer não herda confiança implícita. Observação pública externa das chaves mostrou `cloud_instance_name`: o adapter aceita só o hint `microsoftonline.com` e descarta **somente esse campo**. Todos os demais campos são preservados para IDV recusar private fields/desconhecidos; não remover arbitrariamente o que não entende para conseguir verde. O IDV inalterado limita forma/força/ambiguidades e faz assinatura real. Sem cache persistente/single-flight/refresh por kid nesta fatia; cada load é nova leitura finita e falha não retorna verifier antigo. O futuro host deve decidir cache/rotação/expiração antes de consumo; proof de identidade continua não sendo Authority nem permissão Fabric. Sem token/code/material sensível nos requests.
