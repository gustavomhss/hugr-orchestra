# R02 — OIDC/JWKS com transporte host-owned

**IJW01, freeze solo antes do scaffold.** Consome IDV01/IXM01, não provider exchange/cache/conexão/UI. Configuração nunca vem de token header, manifesto ou argumentos de ferramenta. Sem credenciais/tenant vivo, restart ou agente delegado. Provas de TLS serão locais, com servidor wire real e CA sintética, não atestação de endpoint Microsoft em CI.

## Destinos e autoridade

`FabricIdentityDiscovery.make({profile, agent?, timeoutMs?})` interno sem package export/DTO/tool. `load()` sem parâmetros busca somente `https://login.microsoftonline.com/organizations/v2.0/.well-known/openid-configuration` e `https://login.microsoftonline.com/organizations/discovery/v2.0/keys`, por GET sem body/auth/cookie/client cert no request nativo. Não aceita URL/kid/tenant/nonce/headers do chamador. Metadata deve declarar issuer público template, authorization/token endpoints organizacionais exatos, jwks_uri exato e RS256 suportado. Nenhum endpoint extra da metadata (userinfo, mtls alias, rbac) é seguido. Mudança de metadata/JWKS é falha, não fallback para common/Graph/URL do token. Public cloud/organizational v2 apenas; claims-mapping appid, soberano e B2C seguem unsupported.

Origem observada por GET público sem credenciais em 2026-11-06 via webfetch externo, não runtime do produto: `organizations` metadata declarou jwks_uri **organizations/discovery/v2.0/keys**, issuer `https://login.microsoftonline.com/{tenantid}/v2.0`, auth/token endpoints esperados e RS256. Não trocar por common por suposição. Referência oficial reaberta: https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens#validate-tokens — multitenant exige issuer/tid/issuer da chave coerentes; access tokens Microsoft são opacos para o client. Não usar IDV como validador de access token.

`agent` opcional é capacidade de rede **somente do host confiável**, nunca configuração de workspace/request. Permite uma rede host-owned (por exemplo rota administrada), e nos testes mapeia socket para TLS local conservando hostname/URL de destino; não é mock HTTP. O host já pode fornecer chaves a IDV, então injetar Agent não cria uma nova autoridade para request. Composição padrão omite Agent e usa trust store nativa, TLS >=1.2, rejectUnauthorized/checkServerIdentity explícitos, agent false, sem cookies/proxy/auth/client TLS extra. Um Agent customizado pertence à base de confiança do host e pode substituir conexões; não vender essa execução como prova da Microsoft ou TLS padrão. Nenhuma opção permite `rejectUnauthorized:false`, CA livre, URL alterna ou fetch vindo de request. Provas locais não qualificam proxy corporativo ou o trust store de distribuição.

## Transporte finito e publicação

Native `node:https` não segue redirect; somente status 200, content-type application/json (charset utf-8 opcional), content-encoding identity/ausente, headers até 16 KiB. Metadata até 64 KiB e keys até 256 KiB, limite medido nos chunks reais mesmo sem Content-Length; conteúdo UTF-8 estrito/JSON válido e response.complete obrigatório. Não imprimir body/URL upstream/erro TLS. Timeout total por request default 10 s, host pode reduzir dentro de 100–10000 ms; interrupção/erro/limite encerra request/resposta/socket, sem retry automático. Esses limites iniciais não são medição de orçamento de produto.

load cria um verificador IDV real somente depois de duas respostas íntegras e chaves públicas finitas válidas. Cada chave remota exige issuer próprio público template ou UUID-v2 exato; chave sem issuer não herda confiança implícita. O IDV já limita forma/força/private fields/ambiguidades e faz assinatura real. Sem cache persistente/single-flight/refresh por kid nesta fatia; cada load é nova leitura finita e falha não retorna verifier antigo. O futuro host deve decidir cache/rotação/expiração antes de consumo; proof de identidade continua não sendo Authority nem permissão Fabric. Sem token/code/material sensível nos requests.

## Ownership e provas JWK01–05

Novos discovery/transport/contrato/fixture/testes internos; sem mudar IDV/IXM/PKP/callback/Schema/Core/DDL/Client/dependências. Fixture real TLS/HTTP e certificados gerados por OpenSSL via AppProcess/omni, nunca globalThis ou TLS verification off; controles contam requests/headers e sockets. JWK01 caminho positivo com assinatura real; JWK02 metadata retarget/issuer/alg/endpoints; JWK03 redirect/status/media/encoding/JSON/limites de chunks/partial; JWK04 trust e hostname recusados contra controle positivo; JWK05 deadline/interrupção/cleanup, key issuer obrigatório e ausência de publicação parcial. Timeout e redaction também medidos. Scaffold/RED antes de implementação, CI Linux focado, typecheck e contraprovas/restauração, gates estáticos. Não repetir WPs inalterados por retomada; sem full/epic, merge dev/release ou review independente dispensado.
