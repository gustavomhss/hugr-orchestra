## Execution and proof rules

- LIVE: real provider, using only credentials and samples already available in the QA install.
- MOCK: local HTTP provider, with real transport, Inbox service, Credential and SQLite. Reuse the versioned fixture markers, restricted to the mock. A frontend mock or a `/api/inbox` response mock does not satisfy this definition.
- LOCAL: internal application behavior, with real backend and DB, no provider dependency.
- Record results separately: PASS-LIVE, PASS-MOCK, PASS-LOCAL, FAIL or BLOCKED, with reason. Absence of a grant or of a real event is BLOCKED for that variant, not PASS.
- Do not create tokens, redo consent to obtain new grants, extract cookies, send messages, revoke grants, publish, or restart the work application. Restarts, failures and controlled reconnections use the disposable QA install or the local harness.

## Three pin-specific warnings

- **Jira**: `jira.test.ts` still tests the helper with Bearer. It does not prove the Basic fix on the full path. Jira is also acquired by the `GET /api/inbox` refresh, not by `/api/inbox/account/sync`; missing email and errors can end in an undistinguished empty result.
- **Edits/no-reopen conflict**: the stated no-reopen rule conflicts with current behavior for some sources. Teams reopens on text edits; Linear on material changes; GitHub on notification revision; Calendar on material changes. QA-25 preserves the required rule as the criterion and exposes this divergence without converting current behavior into an automatic approval.
- **Live evidence available**: backlog records Jira/Linear delivery, GitHub without eligible notifications, empty Outlook mailbox, Teams blocked for lack of a corporate account. The Slack grant from the old QA root must not be presumed available. Those records are historical; this session's execution needs its own evidence.
