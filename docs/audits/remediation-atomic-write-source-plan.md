Use `open(temporary, "wx", 0o600)` from the existing Node filesystem API; `FileHandle.writeFile` and `close` are actual Bun compatibility APIs at runtime. Do not claim that inspecting Node's implementation proves Bun's handle behavior. Explicit acquisition/closure is the intended resource boundary, to be tested on the real runner.

If write and close both fail, retain both errors; attempt close and own-temporary cleanup on every acquired-handle failure. A small supporting function is justified only to name this resource boundary and keep the exported function's successful path clear. The public signature stays unchanged.

Return a source-only proposal for Root and independent review before applying it. Then run serial package typecheck and the exact unchanged four-case BOTH gate. A remaining sharing violation is a failed candidate, not permission to weaken the acceptance. Any further retry or ordering policy requires another explicit source contract. ## Second candidate: bounded Windows rename contention

The explicit-close candidate `b250d10485` failed qualification in run `43360087813`: Linux4 pass; Windows1 pass/3 fail at the same rename after the explicit close. Do not describe handle closure as the completed fix. The observed errors still do not identify which OS handle was involved. Windows replacement requires compatible sharing permissions ([Microsoft's file replacement documentation](https://learn.microsoft.com/windows/win32/fileio/moving-and-replacing-files)); that explains why contention needs a policy, not the exact cause of these failures.

Authorize a second source-only proposal retaining the explicit close and adding a bounded retry around rename alone. POSIX still attempts once. On Windows, only EPERM/EACCES/EBUSY may retry, with a16ms maximum wait between attempts, a1000ms monotonic deadline from the first rename attempt and a64-attempt ceiling. Sleep only the smaller of16ms and positive remaining budget. Capture the deadline once, reevaluate after each failure and never start another attempt after expiry. Other errors fail immediately. Return the actual final filesystem error at refusal; no invented success or swallowed permanent failure.

Reuse the same already-written temporary and exact content; never repeat serialization/write or unlink the destination. Final rejection follows the existing own-temporary cleanup path. No per-file global queue or unrelated writer serialization is introduced. These are cooperative retry bounds, not a promise of preemption while the runtime or filesystem blocks. All four test bytes, read/write counts, waits and criteria remain frozen. Root and independent source review precede commit/type/hosted execution. A failure of this candidate requires a new decision; no further retry widening is implicit.
