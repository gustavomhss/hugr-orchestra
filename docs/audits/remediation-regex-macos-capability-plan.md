# E10: macOS capability qualification

The verified hardened source/compiled process gate currently maps Linux and Windows only. The CLI also ships Darwin targets. Before a Core native-regex provider claims macOS support, qualify the same mechanism on actual hosted macOS runners.

The only proposed fixture change is two explicit Darwin cases in the existing `compileTarget` helper: Darwin+x64 returns `bun-darwin-x64`, and Darwin+arm64 returns `bun-darwin-arm64`. Update its setup error to mention macOS. Leave the four existing Linux/Windows branches byte-for-byte unchanged. Preserve the five cases, helper constant scripts, input sizes, canaries, minimal environment, marker/heartbeat bounds, kill request and full Scope/OS PID absence deadlines. Do not change CLI build fields, product code, the spawner, allowlists or any existing assertions. Source and compiled helper behavior must both pass; a build or startup failure is setup/capability failure, never an interpreter CPU RED.

After full Root and independent review, serial Core typecheck and a pushed checkpoint, run the existing official five-case file once with `--os macos` and once with `--os macos-intel`. The ARM selector asserts the runner architecture; the Intel selector currently records it without an assertion. Root must independently require the recorded actual `process.arch` to equal `x64` for Intel and `arm64` for ARM before qualifying either result. A nominal runner label alone is insufficient. Run no local test or build. Each URL releases its uploader slot; resume the same remote job after monitoring errors.

Capture actual Bun/OS/arch and compiled manifest inputs, helper identities, canary results, CPU markers, heartbeat gaps, full child/reader/Scope settlement and independent OS PID absence. Retain failures and setup distinctions. This does not run the actual release CLI, qualify its complete bundle, prove an interpreter timeout or establish Electron support. Native wire/factory/interpreter integration still needs its separate frozen contract.
