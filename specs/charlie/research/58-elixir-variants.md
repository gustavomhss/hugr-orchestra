## Same supplied task: packet F

- Reference assignment extends R42's order example: existing `POST /orders/:id/submit` accepts only `{expected_version: integer >= 0}`. Order has UUID `id`/`tenant_id`, `draft|submitted`, integer `lock_version`, stored recipient. Same-tenant editor may submit draft at expected version; transition increments version. Success: 200 `{id, status: "submitted"}`; anonymous 401, denied actor/tenant 403, missing 404, stale/repeat 409, invalid/unknown input 422. Existing lookup and error-envelope contracts are supplied.
- Existing boundaries are supplied per reference branch: Ecto extends outer `Ecto.Multi`; Ash extends caller-owned `Repo.transact` function. Both require order mutation and receipt-job admission on one Postgres Repo/connection/process; supplied placement uses fixed repo and schema. Failure rolls both back; job admission failure maps to existing 503 envelope. A valid matching existing job may satisfy deduped admission; a returned job without persisted ID cannot. Resource notification handoff, if configured, already belongs to outer commit boundary.
- Existing `receipts` queue, `max_attempts: 5`, insertion uniqueness 60 seconds on `order_id`, existing sender with stable `receipt:<order-id>:v1` idempotency key. Worker gets only order ID; reloads tenant/recipient from stored row and uses supplied service principal authorized to deliver admitted orders. Sender classifications, terminal failures, execution deadline and idempotency guarantees are supplied. HTTP 200 means transition plus durable admission, not receipt delivered.

|---|---|---|---|
| Validate + authorize + transition | Controller → context → supplied access rule + guarded changeset | Same controller → named resource action with arguments, policies and stored-state atomic filter | Treat `accept`/`cast` as authorization, or mutate Ash resource directly through Repo. |
| State and job commit together | `Multi.update(:order, ...)` then native `Oban.insert` | Caller-owned `Repo.transact` invokes Ash action and native `Oban.insert` on same Repo; return normalized two-tuple | Assume transactional action covers later enqueue, or any rollback-capable action fits `Multi.run`. |

## Card 1 — Phoenix controller/context/Ecto changeset

- **Selection (unexecuted):** trigger: assigned F endpoint in component explicitly using plain Ecto context/schema. Non-trigger: Ash-owned resource merely depends on Ecto; UI-only Phoenix task.
- **Supplied facts:** F, existing controller/context/schema and actor lookup, allowed request fields, stale-error convention, authoritative version source, allowed files and initialized ConnCase/DataCase.
- **Steps:** (1) Decode string-keyed params and enforce supplied unknown-field rule; obtain actor from established server boundary. (2) Invoke access rule in reusable domain entrypoint, not only controller. (3) Compare expected version with loaded version, construct server-owned transition and apply supplied `optimistic_lock(:lock_version)` guard; pass into F's Multi. (4) Normalize outcomes and render only contracted JSON fields.
- **Tools/output:** Ecto query/changeset/Repo APIs, existing Phoenix JSON/fallback modules, editor and assigned Mix checks. Output: controller adapter, context function, guarded changeset and scoped tests; optional helpers remain local decisions. [P], [PC], [E]
- **Transfer traps:** `cast` is neither authorization nor automatic unknown-key rejection. Do not overwrite trusted lock state by blindly casting client's version. In-memory status checks alone miss races; default stale writes can raise `Ecto.StaleEntryError`, so preserve explicit stale handling instead of expecting every failure to be a changeset tuple.
- **Local decisions / blockers:** Charlie chooses helper/function layout, query projection, changeset composition and fixture values. Missing policy/status mapping or absent schema support for required concurrency contract blocks affected behavior; no stack redesign.
- **Assigned behavior checks (unexecuted):** actual route covers success, malformed/unknown params, 401/403/404/409/422, exact response keys and unchanged rows/jobs on denial. Independent-connection race belongs to Card 6, not an in-memory changeset test.

## Card 2 — Ash resource/action behind same Phoenix API

- **Selection (unexecuted):** trigger: F assigned to existing Ash/AshPostgres resource/domain. Non-trigger: plain-Ecto target with unrelated Ash dependency; request to pick or migrate frameworks.
- **Supplied facts:** F plus resource/domain identity, named `:submit` update action, actor/policy rules, multitenancy strategy, primary read behavior, same-Repo outer transaction and existing notification handoff when relevant.
- **Steps:** (1) Retain F's HTTP decoder/unknown-key rejection; declare `accept []` plus typed `expected_version` argument. Implement server-owned status change, stored `draft`/version filter and atomic version increment with `require_atomic? true`. (2) Implement supplied policy predicates through resource's `Ash.Policy.Authorizer`. Build `Ash.Changeset.for_update(order, :submit, args, actor: actor, tenant: tenant, authorize?: true)` before execution so changes/hooks see identity. (3) In supplied outer `Repo.transact` function, call non-bang action/code interface, insert receipt through Oban, validate admission result and return `{:ok, %{order: order, receipt: job, notifications: notifications}}`. Propagate every error; normalize Ash's three-tuple success when `return_notifications?: true`. Hand notifications to existing dispatcher only after outer commit. [A], [AU], [AA], [AP], [AC], [AN]
- **Outer-boundary trap:** Ash may explicitly roll back enclosing transaction. `rollback_on_error?: false` is not a general escape hatch: documented data-layer errors still roll back. Blindly wrapping action in `Multi.run` can violate Multi's expected named failure shape. F's Ash branch uses function transaction to handle returned errors and explicit rollback; a target requiring Multi needs its supplied supported integration boundary, not an invented bypass. [AC], [ACH], [ET]
- **Tools/output:** resource DSL, `Ash.Changeset`/`Ash.update`, selected code interface, existing JSON/error adapter and scoped ExUnit checks. Output: action/resource implementation plus transport/transaction adapters; no HTTP endpoint is generated by Ash core merely by declaring action.
- **Transfer traps:** `Ash.Changeset` is not `Ecto.Changeset`; direct Repo mutation bypasses action/policy semantics. `accept []` restricts attribute input, not actors. Default `authorize?: true` permits everything if resource has no authorizers; `require_actor?` still permits explicit `actor: nil`. Preserve HTTP authentication and supplied policy predicates. Setting actor only at final execution is too late for construction-time hooks. [AA]
- **Local decisions / blockers:** Charlie writes atomic expressions, named changes/validations, queries, result adapters and fixtures. Do not disable `require_atomic?` to hide an incompatible callback. Missing tenant/actor contract, data-layer capability, required Multi integration semantics or outer notification ownership blocks affected integration.
- **Assigned behavior checks (unexecuted):** same F route/status/body matrix as Card 1 plus direct action denial, actor available during construction, stale filter → 409, and outer rollback removing order change/job. Policy tests use actual authorizer and Postgres path, not permissive ETS replacement.

## Card 3 — Ecto transaction/Multi versus Ash action boundary

- **Selection (unexecuted):** trigger: assigned all-or-nothing DB mutation/job admission or supplied-diagnosis transaction repair. Non-trigger: pure calculation/read without transaction requirement; cross-database consistency redesign.
- **Supplied facts:** F's boundary, current Ecto call/version, participating repos/processes, action transaction settings, error mapping and any explicitly chosen savepoint behavior.
- **Steps:** extend existing Multi in dependency order, keep operation names unique, and make `Multi.run` callbacks return `{:ok, value}` or `{:error, reason}`. Interpret failure as `{:error, step, reason, changes_so_far}`; earlier returned values were rolled back. Plain static flows can use ordinary control flow in `Repo.transact(fn -> ... end)` when that is existing boundary. [E], [M]
- **Exact transfer trap:** after callback writes successfully and returns `{:error, :blocked}`, `Repo.transaction(fun)` normally commits and returns `{:ok, {:error, :blocked}}`; `Repo.transact(fun)` rolls back and returns `{:error, :blocked}`. Legacy function API needs `Repo.rollback(reason)` or exception for rollback. Inside `Multi.run`, return error instead of manually calling `Repo.rollback`; Multi implementation documents unexpected-rollback failure. [E], [ET]
- **Effect/ownership traps:** nesting Repo transactions does not create independent commits/savepoints. Transaction belongs to process; spawned Task has another connection in production. DB rollback cannot undo HTTP/email/file writes inside `Multi.run`. For F, enqueue DB job inside transaction and send later. Ash construction-time changes are normally pre-transaction; `before_action`/`after_action` are inside enabled action transaction. `after_transaction` handles success or failure and is not proof enclosing caller transaction committed. [E], [A], [AP]
- **Ash variant:** create/update/destroy have transactional defaults; read/generic actions require `transaction? true`. Defaults and single-statement atomicity do not make a later operation part of same transaction; actual transaction use depends on action/data-layer capabilities. F explicitly retains enclosing boundary. [A], [AU]
- **Tools/output:** native Repo/Multi APIs, `Multi.to_list/1` for operation-shape inspection, Ash lifecycle references and supplied real-DB harness. Output: composed transaction and explicit boundary/error adapters; operation list alone does not establish rollback.
- **Local decisions / blockers:** operation labels, query composition and result normalization remain Charlie's. Different Repo/connection placement, unexplained external effect requirement or unsupported savepoint semantics require owner clarification.
- **Assigned behavior checks (unexecuted):** positive control observes changed order and inserted job inside transaction, then late `Multi.run` returns error (Ecto) or outer function returns error (Ash); subsequent read must show original order and no newly inserted job. Invalid prebuilt changeset or `Multi.error` fails before prior steps execute, so cannot substitute for this rollback check. Also force enclosing rollback after successful F command and preserve nested failure propagation. [M], [ET]

## Card 4 — Oban admission, execution and retry

- **Selection (unexecuted):** trigger: F's existing durable job path or assigned worker change. Non-trigger: finite caller-owned computation needing immediate result; adopting a queue because Oban appears in lockfile.
- **Supplied facts:** F, named Oban instance/engine/repo/prefix, queue/retry/uniqueness contract, JSON payload fields, sender outcomes/idempotency, execution identity and timeout.
- **Steps:** (1) Declare `use Oban.Worker, queue: :receipts, max_attempts: 5, unique: [period: 60, keys: [:order_id]]`; build `ReceiptWorker.new(%{order_id: order.id})`. Ecto branch uses native `Oban.insert(multi, :receipt, callback)`; Ash function branch uses `Oban.insert(changeset)` after action success inside outer transaction. Use named-instance overload when supplied. (2) Handle insertion conflict/result before acknowledging admission. (3) Match `%Oban.Job{args: %{"order_id" => id}}`, reload authoritative row, propagate supplied execution actor/tenant, format receipt and await sender result. (4) Return `{:error, reason}` for retryable failure, `{:cancel, reason}` for supplied terminal failure, `:ok`/`{:ok, value}` for success. Success value is ignored; exhausted failures become discarded. Implement supplied execution deadline via `timeout/1` in milliseconds; default is infinity and timeout failure may retry. [O], [W]
- **Tools/output:** native Oban API/worker callbacks, existing sender, scoped Oban.Testing/ExUnit harness. Output: transaction enqueue step and worker implementation; persistent rows are application jobs, not new agent memory.
- **Transfer traps:** raw `Repo.insert`/`Multi.insert` bypasses Oban insertion features; Basic engine `insert_all` does not provide bulk uniqueness. Uniqueness controls insertion, not concurrency or exactly-once execution; OSS documents races. `{:ok, job}` can mean conflict/reuse; inspect `conflict?` and persisted ID. Worker failure after remote acceptance can repeat effect, so stable sender idempotency must survive every retry. Returning success after launching an unawaited Task falsely completes job. [O], [U], [W]
- **Local decisions / blockers:** Charlie chooses payload formatter, reload projection, helper layout and outcome adapter. Missing stable idempotency semantics, execution authorization or transient/terminal classification blocks promised delivery behavior; Charlie does not invent service authority or retry policy.
- **Assigned behavior checks (unexecuted):** F rollback/admission assertions; `perform_job` exercises string-key args, expected payload, error/cancel result and identical key on replay. Manual `drain_queue` plus persisted state/attempt/scheduled-time assertions can check executor transitions. `perform_job` alone does not prove scheduler retries; live staging/recovery requires separately supplied engine-integration acceptance. [OT], [OW], [O]

## Card 5 — Task/Supervisor result and cancellation ownership

- **Selection (unexecuted):** trigger: assigned bounded concurrent receipt rendering or server-side fan-out under existing supervisor. Non-trigger: F's durable receipt admission/retry; detached fire-and-forget replacement for required result; LiveView UI lifecycle.
- **Supplied facts:** caller is request/job/existing GenServer; lifetime/failure-isolation contract, immutable rendering inputs, failure result, execution and cleanup budgets, cancellation signal, supervisor identity and concurrency bound. Same rendering output is required for direct-function and Task paths.
- **Steps:** keep pure direct-call variant in caller process; Task variant copies minimal inputs and returns same value before sender/job success. `Task.Supervisor.async` remains linked to caller. For supplied failure isolation, use `async_nolink` with `Task.yield(task, timeout) || Task.shutdown(task, cleanup_budget)` and handle success, exit and nil; cleanup can extend elapsed time beyond yield timeout. Existing GenServer owner handles `{ref, result}` and `:DOWN`, demonitoring/flushing after reply, rather than blocking long `await`. [T], [TS]
- **Cancellation step:** route supplied cancellation event to explicit owned-task shutdown. If unlinked work must stop after abrupt owner death, implement supplied owner-monitor/lifetime contract; cleanup code in already-dead caller cannot supply that guarantee. [T], [TS]
- **Tools/output:** Task/Supervisor APIs, existing lifecycle owner and ExUnit message/monitor fixtures. Output: bounded invocation plus result/error/timeout cleanup in assigned module; no custom persistent coordinator.
- **Transfer traps:** `Task.await` timeout exits caller, not `{:error, :timeout}`. Linked task normally dies with abnormal caller exit, but normal exit/trapping exits require explicit care; HTTP disconnect is not itself proof task was cancelled. `yield` timeout leaves task running. Nonlinked task is not cancelled by caller's link, and temporary supervised task is not retried/durable. Task cancellation cannot retract remote effect. A production transaction connection does not transfer with captured Repo module. [T], [TS], [E]
- **Local decisions / blockers:** Charlie chooses Task API matching supplied ownership, MFA/helper, copied data subset, result shaping and bounded fan-out details. Unspecified lifetime or cancellation ownership blocks affected cleanup; no new supervisor topology or transport diagnosis.
- **Assigned behavior checks (unexecuted):** direct/Task rendering equivalence; crash isolation matches chosen linkage; controlled task stays alive after yield timeout, then monitor confirms shutdown; normal/abnormal owner exit and assigned cancellation paths release work. Job returns success only after required task result. Avoid sleep-only assertions.

## Extraction recommendation and useful delta from R42

- **Shared scope guidance:** packet facts, assigned behavior, effect boundary, implementation-local judgment, blockers and honest unexecuted evidence. Do not duplicate this per framework or require caller to prewrite functions/queries/fixtures.
- **Language/runtime reference:** Elixir tuples, links/monitors, result ownership, timeouts and process-local Repo state (Card 5 plus Card 3 process rule).
- **Framework references:** Phoenix HTTP/context and Ash action/policy/atomicity (Cards 1–2); Ecto transaction return-shape table (Card 3); Oban engine/version semantics (Card 4).
- **Narrow task recipes:** guarded transition + atomic enqueue (F; Cards 1 or 2 + 3 + 4), caller-owned bounded work (5), real-DB acceptance/ownership (6). F + Ecto selects 1/3/4/6; F + Ash selects 2/3/4/6 while consuming shared Phoenix transport guidance; pure receipt rendering selects 5 only when concurrency is assigned, with no Sandbox recipe unless DB access is assigned.
- **New leverage:** same wire/transaction/job contract survives framework variation; exact error-tuple rollback trap, rollback-capable Ash action versus Multi callback, actor timing, outer commit versus hook timing, insertion dedupe versus remote idempotency, timeout versus cancellation, and test connection ownership become executable instructions/check proposals. R42's codegen/migration recipe remains separate assigned schema-change scope. These labels describe composition; they implement neither native loader routing nor permissions.
