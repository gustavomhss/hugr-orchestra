# R23 — OpenClaw tools, plugins, skills, execution policy

## Decision

Adopt **progressive, exact contracts; host-owned execution; complete skill bundles; deterministic read/reduce operations**. The backend specialist stays independent OpenCode/Orchestra plugin; Maestro integration optional; native Atlas owns grounding identity. Highest-value efficiency candidate: fetch bounded structured data once, join/filter locally, return useful evidence plus completeness. Smaller prompt alone does not mean cheaper execution.

## Provenance and reach

- **R** = official `openclaw/openclaw` release `v2026.9.8`, commit `fc23bc864e4553c2d215e479eeec47b67a0bf943`. GitHub annotated tag `b1c1c6d3af1f68bc82efbb6c92fb224c36df8683` dereferenced to supplied commit. **M** = supplied main pin `06da0de86c0a27dc1e92995f9d0a2428880ce90c`, verified commit API. [Pins]

- Scope: tool discovery/registration, invocation policy, subprocess outcomes, transport parity, skill resources, execution economy. Memory internals and overall session recovery excluded. Selected-file comparison, not whole-release audit.

## Exact surface distinctions

| Surface | Actual contract and guard |
|---|---|
| Native manifest | `openclaw.plugin.json`; `loadPluginManifest` accepts JSON5, bounded to 256 KiB; requires nonblank `id` and object `configSchema`; reserved `node-mcp` rejected. Tool registration additionally requires `contracts.tools`. This is config/discovery metadata, not executable tool implementation. [S1] |
| Declarative tool | `defineToolPlugin({id,name,description,activation?,configSchema?,tools})`; each tool has `name,label?,description,parameters,optional?` and **either** `execute(params,config,context)` with optional `outputSchema`, **or** `factory({api,config,toolContext})`. Factory returns concrete tool(s)/null/undefined; concrete signature is `execute(toolCallId,params,signal?,onUpdate?)`. Output schema belongs on concrete factory result. Omitted config schema becomes strict empty object; activation defaults `{onStartup:true}`. [S2] |
| Search | `tool_search({query?:string\|null,limit?:integer>=1\|null,queries?:Array<{query:string,limit?:integer>=1}>\|null})`. Runtime parser enforces conditional shape; blank scalar alone returns empty candidates, missing scalar/batch fails. Scalar joins nonempty batch first; repeated queries remain independent. Batch-only top-level nonnull limit rejected. Limits clamp to configured maximum; total effective requested candidates ≤50, queries ≤16, each batch query ≤512 characters, serialized query list ≤512 UTF-8 bytes. Batch response ≤4,000 characters with group/global `truncated`. [S3][S24] |
| Describe/call | `tool_describe({id:string})`; `tool_call({id:string,args?:Record<string,unknown>})`. Runtime requires nonblank selector, permits exact ID or unambiguous name. Flattened/alias compatibility parser preserves target `id`/`name`; conflicting selectors reject. Call returns `{tool,result}`; display carries only tool identity/source, structured details retain full envelope. [S3][S4] |
| Code Mode | JavaScript `exec({title:string,code:string,restartSafe?:boolean})`, title nonblank ≤120 characters; `wait({runId:string})`. Runtime-only `command` alias means JavaScript, not shell. `wait` accepts outer waiting-cell identity, never nested process `sessionId`. `restartSafe` is restricted replay control, not user assertion of idempotence. [S5] |
| Shell/process | Shell `exec` requires string `command`; optional `title` ≤120, `workdir`, string-valued `env`, numeric `yieldMs`/`timeoutSeconds`, boolean `background`/`pty`/`elevated`, host enum `auto\|sandbox\|gateway\|node`, string `ask`/`node`. Wire schema leaves several numeric/ask constraints to runtime. `process.action` enum: `list\|poll\|log\|write\|send-keys\|submit\|paste\|kill\|clear\|remove`; runtime requires `sessionId` except list. `process.timeout` is milliseconds, capped at 30,000; exec lifetime is seconds. [S6] |

Compact TypeScript signatures are hints, not substitute schemas. First-party catalog input validates **after** argument repair/hooks/finalization; full output schema compiles before execution, final `details` validates before catalog acceptance. Input-dependent output annotation is `"x-openclaw-input-discriminator":{version:1,inputProperty,mapping:{stringValue:branchIndex}}` over ordinary `anyOf`. Invalid annotation/unselected invalid branch prevents execution; incompatible post-hook output can fail **after effects**. Remote/client schemas stay delegated to their owning boundary. [S4][D2]

## Six concrete source traces

### T1 — Manifest availability → selective runtime load → current factory

1. Fixture plugin `xai` declares `contracts.tools:["x_search"]` and auth/config signals. `src/plugins/tools.ts:resolvePluginToolLoadState` reads manifest snapshot; `resolvePluginToolPluginIds` checks enablement, plugin/tool denial, optional grants, then `hasManifestToolAvailability`. Missing signals → empty selection before loader/factory. Named-account config can make another plugin tool eligible. [S1][S7]
2. Selected owners load via `loadPluginRegistryHandle({activate:false,toolDiscovery:true,onlyPluginIds})`. Existing compatible owner reused; `resolvePluginToolsFromRegistry` still invokes current-context factories per assembly. `createToolHookRegistrars.registerTool` rejects undeclared names; returned names checked again. Missing client caps, null factory, malformed tool, duplicate name, denied actual factory output → omitted with appropriate diagnostics. [S7][S8]
3. Optional tool needs tool/plugin/group/wildcard grant; ordinary nonoptional defaults can load without explicit grant. Runtime grants bind exact **plugin ID + tool name**, not display label or glob. Factory returning zero tools does not justify switching to unrelated registry. Retained callbacks fail when owner retires. [S7]
4. **Cost:** metadata-only discovery can avoid imports; selected catalog assembly is already runtime work. Default startup activation can load plugin earlier. `defineToolPlugin` itself does not promise lazy-per-invocation imports; authors must keep declaration module cheap. Native plugins run trusted in-process code, not isolated skill sandboxes. [D1]
5. **Observed test assertions:** `src/plugins/tools.optional.test.ts` mocks loader entrypoints but keeps owner resolution real. Missing auth asserts loader/factory uncalled; named-account fixture asserts selected owner and one factory call; supplied-owner/retirement fixtures check correct schemas, output, and stale rejection. Establishes resolver behavior, not cold-start timing or arbitrary module import safety. [T1]

### T2 — Policy filtering → rewritten invocation → final-effect fence

1. `resolveEffectiveToolPolicy` selects agent profile over global profile; `alsoAllow` extends profile stage. `buildDefaultToolPolicyPipelineSteps` applies profile → provider-profile → global → global-provider → agent → agent-provider → group → sender. Callers add sandbox, inherited/subagent, owner/runtime restrictions. Each filter narrows surviving tools; later allow cannot resurrect earlier removal. Plugin groups expand against actual owners. [S9]
2. `createToolPolicyMatcher` checks deny first. Important distinction: ordinary empty `allow:[]` means no allow restriction; `createRuntimeToolMatcher([])` denies all. Compatibility: allowing `write` also permits `apply_patch`; denying `write` alone does not deny `apply_patch`. Visibility is not final authorization. [S10]
3. Concrete fixture: trusted `strict_instruction` expects `{instruction:string}`, closed object. Hook rewriting `"valid"` to `42` reaches `wrapToolWithBeforeToolCallHook` → finalizer → `validateToolExecutionParams` → rejection before executor. Hook repair to string can succeed; policy veto precedes schema validation. [S11][T2]
4. `runBeforeToolCallHook` orders loop admission, core/voice checks, trusted policies/approval, normal hooks/approval, final skill-workshop approval. Veto returns `details:{status:"blocked",deniedReason,reason}`. Hook exception becomes failure with exact reason `Tool call blocked because before_tool_call hook failed`; no target invocation. Cancellation and runtime/source authority rechecked after awaits immediately before implementation. Typed interception uses `api.on("before_tool_call",…)`; legacy `registerHook` with typed lifecycle name warns and is not dispatched. [S11][S11b][S8]
5. **Unavailable/partial:** missing approval route returns unavailable failure, not permission; post-call result hooks cannot undo effects. Hook/preparation code itself can do work before target denial; fail-closed target boundary is not proof of zero plugin side effects. Version-2 factory context exposes `assertInvocationCurrent` for plugin's own final write/request boundary. [D1][S8]
6. **Observed tests:** M `tool-search-runtime.test.ts` uses fake tools/hooks to assert repaired execution, invalid rewrite zero executor calls, hostile MCP/client schema nontraversal. R `agent-tools.before-tool-call.approval-policy.test.ts` mocks Gateway: approval subject names selected tool owner, not approving hook; missing route preserves setup guidance. Neither demonstrates real operator interaction. [T2][T2b]

### T3 — Progressive catalog → composed call → output-contract failure

1. Policy-approved tool enters `tool-search-catalog.ts:toCatalogEntry` as `${source}:${owner}:${tool.name}`; `label` stays presentation. `direct-only` stays outside catalog. Trusted core coding primitives can remain directly visible and searchable; MCP lookalikes cannot gain that privilege. Catalog absence throws `Tool Search catalog is unavailable for this run.` [S12]
2. For fixture `records`, search/describe reveals input `{operation:string}` and output union: `list→{records:string[]}`, `remove→{removed:boolean}`. Search ranking is deterministic lexical BM25, English stemming/intent expansion, ID tie-break; exact unambiguous lookup with limit 1 skips lexical-index construction. MCP/client compact input remains `unknown`; untrusted parameter schemas are not indexed. [S4][D3]
3. Code Mode cell requests `records({operation:"list"})`, then `consume_records`. Hook rewrites operation to `remove`. `ToolSearchRuntime.executeEntry` compiles complete output schema, executes finalized input, validates both executed and caller-advertised result variants. Incompatible result → `output_contract`; consumer never runs. Cell may catch error and finish `completed` with `{code:"output_contract",effectStatus:"unknown"}`. Completed cell ≠ successful underlying operation; no rollback implied. [S4][T3]
4. `runScheduledToolSearchCall` shares admission per catalog reference across cells. Parallel prefix may run together; sequential call excludes siblings until execution/acceptance settles. Queued tool removal/replacement/mode change rejects before dispatch; incompatible reentrant calls reject instead of deadlocking. Cancellation of observer must not free slot while producer still works. This is local tool concurrency control, not cluster scheduling. [S13]
5. **Partial/unavailable:** search group `truncated:true` differs from zero matches. Nested bridge replies are intact or explicit resource errors; bounded final display may be successful-but-truncated, optionally reference retained result. `results.save/load` can avoid refetch within owner lifetime; not durable storage. Missing selected executor fails rather than widening to direct schemas. [S5][D2]
6. **Observed tests:** R `tool-search-runtime.output-variants.test.ts` spies executor and continuation: incompatible rewrite executes target once, continuation zero; invalid schema branch executes zero. R `tool-search-scheduling.test.ts` uses deferred fixture tools to observe FIFO events, cancellation, replacement, acceptance hold, reentrancy. M runtime test instruments schema getters during exact searches; proves skipped traversal, not measured speed/token savings. [T3][T3b][T2]

### T4 — Shell launch → background handle → bounded result collection

1. Source fixture starts child that emits `FOLLOWUP_COMPLETE` only after parent releases file gate. `createExecTool` prepares workdir/environment, resolves host, security/ask floors, approvals, then `runExecProcess`. Explicit sandbox without runtime rejects; `security=deny` rejects. Ordinary host defaults are `full/off`; presence of tool policy does not imply shell sandboxing or approval. [S6][S14][D4]
2. Gateway approval supplies `revalidateBeforeExecution`/`assertCurrent` to process launch. `background:true` or elapsed `yieldMs` returns `details:{status:"running",sessionId,pid?,startedAt,cwd,tail,followUp}`. Denied/pending approval returns before spawn; `approval-pending` means not started. Remote node path explicitly has no local process-session continuation. [S14]
3. `process poll({sessionId,timeout})` resolves same scoped process and reports running or final exit metadata; `log` pages retained output, default tail 200 lines. Retention loss and poll omission are reported separately; omitted bytes cannot be recreated by wider display limit. Missing/out-of-scope handle becomes `status:"failed"` with `No session found for …`. Factory without `scopeKey` is unscoped: host must bind real scope. [S15]
4. If process tool unavailable, background options ignored and exec waits synchronously with warning. Timeout continues after background return; turn abort suppresses updates and kills foreground child, but already-backgrounded process retains process owner. One-shot caller cleanup owns its scope. `kill` success means termination requested, not confirmed child exit. [S14][S15]
5. **Outcome trap:** `isToolResultError` explicitly treats `status:"completed"` with nonzero exitCode as nonfatal unless other failure markers exist. MCP test preserves exit 23 as nonfatal. Domain success, process exit, cancellation, display completeness need separate interpretation. [S16][T5]
6. **Observed tests:** R `bash-tools.exec-background-followup.test.ts` uses real local child and file gate: handle/followUp then poll same ID and expected output; process-unavailable fixture completes foreground. `bash-tools.exec-launch-policy.integration.test.ts` wraps actual spawn/PTY boundaries, checks launch counter plus marker file before/after revocation; whole describe skips Windows. Does not prove remote-node behavior or all OS process cleanup. [T4][T4b]

### T5 — CLI inspection/probe and MCP invocation: shared pieces, unequal semantics

1. `src/cli/mcp-cli.ts:registerMcpCli` → `status` calls `buildMcpStatusEntries`: configured/enabled/valid transport and auth facts, no connection. `probe` creates session MCP runtime, calls `getCatalog`, projects provider-safe names, inspects diagnostics/missing server, finally disposes. `doctor --probe` caps concurrent probes at four. These operations may start subprocesses/connect/authenticate/list; they do not prove target tool succeeds. `add` normally probes before saving, while `set` saves config. [S17]
2. `agent-bundle-mcp-materialize.ts:buildBundleMcpToolsFromCatalog` creates sorted safe names; inventory-only projections throw on execution. Executable projections pass effective policy then provider adapter. Coding/messaging profiles can expose `bundle-mcp`; minimal/explicit denial hides it. Tools default **sequential** unless server declares `supportsParallelToolCalls:true`: `Promise.all` does not override catalog exclusion. Tool/resources/prompts remain distinct. `connectWithMcpStartupBackoff` reports unavailable/retry time, doubles cooldown up to 10 minutes, preserves cancellation and avoids reconnect spam; partial catalog diagnostics must survive aggregation. [S25][S26][T5b]
3. Inbound standalone plugin bridge: `acquirePluginToolsForMcp` acquires registry, selects global/profile/agent policies, resolves factories; `createPluginToolsMcpHandlers` wraps or rewraps pre-call hooks with **`approvalMode:"report"`**. Calling denied absent name → MCP `isError:true`, unknown-tool text. Approval-required hook → no executor, no interactive Gateway request, cancelled approval resolution, `Tool error: Approval required`. [S18][T5]
4. Transport contract diverges: handler lists `name,description,inputSchema`, then returns converted `content` plus conditional `isError`; ordinary `details` and `outputSchema` are not exported as MCP structured result/contract. Shared hook wrapper is not proof of identical catalog input/output validation. `openclaw mcp serve` is separate channel-conversation bridge, not universal export of every plugin tool. [S18][S17][D5]
5. **Observed tests:** R `plugin-tools-serve.test.ts` uses mocked acquisitions/Gateway and real hook wrappers; asserts denied executor untouched, report-only approval, unique invocation IDs, argument cleanup. One case uses real MCP SDK client/server over in-memory transport to check image conversion. `agent-bundle-mcp-tools.request-boundary.test.ts` fake runtime verifies profile-filtered request names, deterministic sorting, resource/prompt metadata projection; not remote transport/auth test. [T5][T5b]

### T6 — Skill catalog → exact resource bytes → reproducible bundle

1. File skill roots have explicit precedence: workspace → project `.agents/skills` → personal default-state `.agents/skills` → managed → workshop → bundled → extra/plugin roots. `filterSkillEntries` applies session/agent selection plus `shouldIncludeSkill` prerequisites. Eligible skill supplies instructions, not authorization; plugin skills require enabled plugin. Relative resources belong to selected skill base directory; remote-node `node://` entries stay node-owned. [D6][S19]
2. `prepareSkillResourceDelivery` selects admitted/explicit resources, captures library revision selection, reads complete supporting files. Managed revision uses `readSkillLibraryManifestTree` to check each size/hash and whole revision; ordinary files are reread for turn delivery because catalog version does not version support files. `code-mode-skills.ts:resolveCodeModeSkills` ties exposed skill names/locations to rendered admitted catalog; `readCodeModeSkill` uses captured content, supplied reader, or selected path. [S20]
3. Concrete bundle: `SKILL.md` + executable `scripts/test.sh`. `prepareSkillBundle` sorts portable paths and hashes `JSON.stringify(["openclaw.skill-library.tree.v1",manifest])`, each entry `{path,sha256,sizeBytes,executable}`. Changing helper bytes/path/executable bit changes revision; input enumeration order does not. Limits: 256 files, 1 MiB/file, 8 MiB/bundle, 16 path components; materialized selection also ≤8 MiB total. [S21]
4. Managed imports reject nested links/hardlinks, nonportable paths, case/file-directory collisions. File-backed resource capture can dereference only included regular-file aliases within root; excluded-tree/outside targets fail. `materializeSkillResources` rechecks revision/aggregate bound, writes private exact copies, rewrites instruction/support paths, owns cleanup. Bundle identity does not pin external binaries/packages/network data: reproducible artifact ≠ reproducible computation. [S20][S21]
5. **Unavailable/partial:** disappearing implicitly discovered root can be skipped with warning; explicitly requested missing skill, unreadable nested directory, changed pinned revision, traversal overflow, missing remote reader fail. No silently partial selected bundle. Agent Plugins/Claude/Cursor bundles map only supported features; e.g. Claude `hooks/hooks.json` detected but not executed. Skill `command-dispatch:tool` still resolves policy through `resolveSkillDispatchTools`; bypassing model is not bypassing host. [S20][S22][D7]
6. **Observed tests:** R `library/bundle.test.ts` asserts fixed revision golden, order invariance, helper mutations, invalid paths/limits and filesystem races; link/permission cases skip Windows. `runtime/resources.test.ts` uses real files plus selected spies: helper changes alter delivered revision despite same snapshot; reordered delivery gives same paths/prompt; stale cleanup cannot delete next materialization; missing explicit vs discovered roots differ. No hermetic dependency/execution proof. [T6][T6b]

## Release versus pinned main

- **M lookup efficiency:** `tool-search-runtime.ts` uses `getTextLexicalIndex` from new `tool-search-index.ts`: content-hashed lexical documents share positional index across rebuilt catalogs; positions resolve against caller's current filtered entries. R uses per-catalog index and entry term caches. M still builds/hashes document list for ordinary search; cache hit is not zero work. Exact limit-1 path still bypasses schema traversal. [M1]
- **M schema/discovery:** runtime removes R's explicit JSON-string cache key from validator call; do not infer changed cache semantics without validator owner analysis. `tool-search.ts` adds actionable direct-only-name rejection; client-compaction helper removed from that facade. Inspected policy pipeline, before-call policy/wrapper, scheduling and MCP-tools facade have identical Git blob IDs between pins. That comparison covers named files only. [M4][M2]
- **M resource provenance:** `runtime/resources.ts` retains host-owned file-origin metadata through copies, matches explicit selection by **path + host**, distinguishes same path on Gateway/workspace, rewrites virtual read paths, and uses typed delivery-limit error. R's simpler path match cannot support same inference. `library/bundle.ts` keeps tree revision encoding while relocating helpers/errors. Adopt host-bound resource origin. [M3]

## Economy: useful deterministic work, honest accounting

- **Strong aggregation:** the backend specialist inspection collects authorized Atlas unit receipts, tool availability and bounded evidence pages; one deterministic reducer deduplicates by immutable IDs, joins by unit/project/revision, sorts stably, counts status buckets and returns exceptions plus evidence refs. Completeness includes per-source status/cursor and revision; failed source never becomes empty facts. Ordinary coding primitives remain direct where discovery overhead loses.
- **Progressive disclosure:** compact stable IDs + bounded descriptions/input/output hints → exact schema only when needed → selected invocation. OpenClaw Code Mode quick index caps 8,000 characters and favors known outputs; structured Tool Search directory caps 18,000. These are character budgets, not token measurements. Small catalogs and uncertain output shapes may cost more model turns. [S5][D3]
- **Real costs remain:** batched search performs each ranking; `Promise.all` saves waiting/round trips, not underlying calls. Tool factories, MCP startup/listing, schema compilation, result JSON copies, bundle hashing/materialization and all network/tool effects still run. Bounded **display** can follow expensive/unbounded producer work; put page/byte/item/concurrency/time bounds at producer boundary too.
- **Structured output matters:** one read plus local join can replace repeated model-mediated item inspection; compact output schema enables safe same-cell composition. Unknown/partial schemas require describe or raw-first inspection. Preserve separate successful data, failures, capture loss and display truncation; never compute exact totals from incomplete pages without qualification.
- **Do not misclassify other runtimes as reducers:** R `llm-task` invokes `api.runtime.llm.complete`, then JSON parse/schema validation: extra model compute, not deterministic aggregation. R Lobster runner dynamically imports `@clawdbot/lobster/core` in-process, caches runtime promise, applies aborting timeout and output limits; it is not merely shell batching, and rejecting timeout does not prove work stopped. The backend specialist can obtain deterministic reductions through existing host CodeMode/typed operations. [S23][S27]
- **Acceptance measurements to collect later:** serialized provider bytes/tokenizer-specific counts, model turns, discovery/describes, actual leaf calls and outbound requests, producer bytes/pages, elapsed/CPU, retries, side-effect count. Compare same successful/denied/partial workload with direct and progressive surfaces; no numeric savings established here.

## Host fit at H

- `packages/plugin/src/tool.ts` offers Zod args, `execute`, session/message/agent identity, `directory/worktree`, `abort`, `ask`, string or `{title,output,metadata,attachments}` result. `packages/plugin/src/index.ts:Hooks` exposes tool declaration/definition and before/after hooks. These do not constitute typed access to every host tool or trustworthy output contracts.
- `packages/core/src/tool/registry.ts:materialize/settleWith` already supplies effective definitions, captured registration-identity rejection, leaf settlement and output bounding. Its architecture keeps permission enforcement in leaves, not registry. Preserve that single boundary; plugin boot/MCP canonical integration remains explicit host work, not something the backend specialist can obtain by calling a raw executor.
- `packages/codemode/src/tool.ts` already supports validating Effect Schemas **and render-only JSON Schema**. `tool-runtime.ts:prepare/make` supplies budgeted discovery, search, tool-call limits and callbacks. Reuse this interpreter; JSON Schema description alone does not validate. A backend specialist adapter must use validating codecs or existing host settlement, never assume imported MCP schemas enforce themselves.
- `packages/atlas-boundary/src/generated/boundary.d.ts` exposes project/catalog/snapshot/sourceRevision identity and `verifyHostContext→READY|HOLD`. `packages/opencode/src/maestro/atlas-source.ts` adds source/skill rechecks. This static verification bridge is not proof live native Atlas `own(scope)` adapter exists. `specs/hugr-maestro/atlas-foundation-seam-register.md` names native Own candidate and missing actor/snapshot bindings; do not replace Atlas with cloned skill registry or infer live authority from static receipt.
- Existing `maestro/ability-registry.ts` separates descriptor availability from executor; `ability-descriptors.ts` grants Atlas ability to `maestro/jimmy`. The backend specialist label change cannot acquire another seat's grant. The backend specialist's independent native Atlas binding must carry its real host actor; optional Maestro bridge contributes its own authorized plan/actor context.

**Small contract justified only for cross-host-tool composition:** a scoped plugin-facing view over existing host materialization: immutable operation IDs/generation, exact input/output codecs or explicit unknown, and `invoke` carrying host-bound context/signal. Delegate to existing settlement and leaf permissions; expose no raw execute function. Current plugin `ToolContext` lacks that view. Backend-specialist-owned operations can share their implementation immediately; broad host-tool composition waits for this seam. This adds neither parallel registry nor scheduler.

Suggested backend specialist result distinction: `outcome = succeeded | denied | unavailable | failed | cancelled | running`; independent `completeness = complete | partial`; `effects = not-started | possible | confirmed`; optional typed `data`, source failures/cursors, evidence refs and host operation handle. Use explicit codec/discriminated variants. Presentation label never determines any field or routing. Partial data can be useful without falsely certifying complete inspection.
