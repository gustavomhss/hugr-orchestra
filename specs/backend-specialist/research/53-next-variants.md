## Same assigned backend action, different boundary

Illustrative supplied fixture adapted from R39, not proposed app feature: authenticated profile rename. Trim `displayName`; require 1–60 UTF-16 code units; discard unknown fields; normalized `admin` is reserved. Derive target user from verified principal, ignoring forged `userId`. Supplied repository returns `Date`; prescribed DTO is `{ userId, displayName, updatedAt: UTC-ISO-string }`.
HTTP packet: `PATCH /api/profile`, JSON body; success 200 + DTO; invalid body/name 400 `{ code: "INVALID" }`; missing session 401 `{ code: "UNAUTHENTICATED" }`; reserved name 409 `{ code: "RESERVED" }`. Rejected calls leave profile unchanged. Separately supplied action packet: `renameProfile(input)` returns `{ data }`, `{ validationErrors }`, or `{ serverError: prescribedCode }`. Native Next does not invent these envelopes; next-safe-action supplies its own pipeline only when already selected, as in R39.
Concrete positive: actor `u1`, `{ displayName: "  Ada  ", userId: "u2" }` writes `Ada` only for `u1`, returns matching DTO through selected wrapper. Negatives: number, blank, 61-character name, missing session and `admin`; inspect stored row as well as public error. Invalid service output must fail prescribed output boundary; post-write serialization failure cannot undo committed data.

## C1 — App Router HTTP handler

**Trigger / non-trigger:** assigned App `route.ts` endpoint with HTTP method/status/header/body contract. Excludes action-only contract, internal helper task, Pages API and UI work.
**Provided / targets / stack:** shared packet + `/api/profile` contract, media-type/CSRF/CORS policy, auth/service interfaces and error precedence; `src/app/api/profile/route.ts`, supplied schema/service and HTTP fixture; exact Next pin, selected Node or Edge via C5.
**Sequence → output:** (1) Export prescribed method. (2) Authenticate through supplied verifier; await App request APIs where used. (3) Decode body once; map malformed JSON separately from schema errors; validate params and normalized fields. (4) Authorize target, execute supplied service/transaction. (5) Project DTO, invalidate only committed changes per C6, return explicit status/content type/headers. Output: mounted HTTP implementation plus scoped behavior fixtures.
**Native tools:** Web `Request`/`Response`, `NextRequest`, `NextResponse.json` when appropriate, `next/headers`; `RouteContext<'/api/items/[id]'>` after supported `next typegen`; packet-local typecheck and mounted `fetch` fixture.
**Transport detail:** Next auto-handles missing HEAD from GET and OPTIONS with `Allow`; other unexported supported methods receive empty-body 405. Prescribed JSON 405/headers require explicit supported-method handlers; automatic OPTIONS is not CORS policy. [RH]
**Local judgment / blocker:** choose parsing/schema/helper composition and bounded reader as contract requires. Upstream blocker: public error precedence missing/conflicting, target route collision, or required policy integration outside supplied scope—not caller failing to prewrite every helper.
**Assigned checks — the backend specialist later, Q1:** common rename cases, malformed JSON/content type, exact failure body/status, method handling, awaited dynamic params and session cookies through real mounted handler. Direct function tests alone miss routing/request context.

## C2 — Remotely callable Server Action

**Trigger / non-trigger:** supplied App Router action export and caller integration contract. Excludes externally stable REST/webhook API, Pages-only target, ordinary internal server helper and read-only data-fetch RPC invented for convenience.
**Provided / targets / stack:** shared packet + exported name, argument layout (object, FormData, or previous-state + payload), action result union, auth policy, unexpected-error policy and revalidation intent; `src/app/profile/actions.ts`, C4 service, existing action transport fixture; exact Next/React and optional already-selected next-safe-action pin.
**Sequence → output:** (1) Preserve async action export and argument order. (2) Resolve current session on every invocation; verify resource authorization through action/DAL chain. (3) Validate untrusted args, including bound IDs/previous state; whitelist FormData fields rather than mass-assigning entries. (4) Execute domain mutation. (5) Invalidate per C6 after commit, return prescribed result or perform prescribed redirect. Output: callable action retaining supplied signature, envelope and ownership policy.
**Native tools:** `"use server"`, `FormData.get/getAll`, awaited `cookies`/`headers`, `next/cache`, `redirect`; compiler-generated action transport and supplied compiled integration fixture. Schema library remains packet-selected.
**Auth/error boundary:** actions are remotely callable; layout checks, hidden fields, encrypted closures and unguessable IDs are not authorization. Origin/Host checks supplement auth; 16.3.8 source permits missing Origin, so “same-origin only” is not credential verification. Expected errors use supplied result; unexpected fetch-action throws become 500 + rejected Flight result, not custom REST error JSON. Body-limit `ApiError(413)` also reaches that generic fetch-action catch in examined source; do not promise HTTP 413 from action body-limit configuration. [SEC][ACTION]
**Serialization/redirect:** React supports Date/BigInt/Map/Set beyond JSON, but arbitrary class instances, ordinary functions and `Response` are unsuitable action DTOs. JSON cannot natively encode BigInt; prescribed ISO DTO remains ISO in both transports. `redirect` throws control flow: invalidate first, keep outside broad catch. In **16.3.8**, fetch-action redirect is HTTP **200** + `x-action-redirect`; progressive form submission is **303** + `Location`. Do not assert universal action 303. [REACT][ACTION]
**Local judgment / blocker:** choose validation, minimal DTO and safe mapper locally. Blocker: missing result/signature policy, conflicting required REST contract or unsupported payload/driver runtime. Missing existing transport fixture blocks transport evidence, not local implementation; caller supplies integration without requiring the backend specialist to redesign UI.
**Assigned checks — the backend specialist later, Q2:** fixture cases via actual action reference; valid-origin unauthenticated direct call, forged owner/bound ID, FormData File/duplicate handling under supplied policy, serialization failure, body-limit transport failure and declared action-state argument order. If redirect assigned, exercise hydrated and progressive paths; domain-error result is distinct from transport failure.

## C6 — App data-cache read/invalidation overlay

**Trigger / non-trigger:** supplied app-data read reuse, stale-data correction with diagnosis, or post-mutation freshness policy. Excludes agent/harness memory, build cache, assuming all GETs cache, or caching mutation execution/results.
**Provided / targets / stack:** named read/write consumers, tenant/user cache scope, required freshness (SWR versus read-your-writes), tags/paths, existing cache mode/backend/adapter and failure/retry semantics; `src/server/profile-read.ts`, assigned C1/C2 writer and cache fixture; exact Next pin.
**Sequence → output:** (1) Locate supplied cache owner and named consumers. (2) Authenticate/authorize outside cross-request cache; pass permitted scope identifiers as key inputs. (3) Implement prescribed read-cache API and lifetime, then attach matching invalidation tags. (4) Mutate/commit, then invalidate from supported boundary. (5) Preserve supplied failure/retry semantics if commit succeeded but invalidation failed. Output: scoped read helper + writer invalidation, with explicit cache/key/tag/consumer map.
**Cache ownership:** React `cache`/render fetch memoization is request/render-scoped, not durable data cache or Route Handler deduplication. `fetch(..., { cache: 'force-cache', next: { tags } })` owns Next data entries; `no-store` controls that fetch, not every surrounding output/CDN cache. Existing `unstable_cache` persists function results across requests/deploys: args/function plus `keyParts` identify entries; tags are invalidation labels, **not tenant keys**. [DATA]
**Wrong transfer:** uncached mutation response does not guarantee fresh underlying reads; explicit cached fetch/helper may still serve old data. Data Cache, prerendered route output, client Router Cache and HTTP/CDN caches have distinct owners. Response `Cache-Control` is not invalidation of tagged app data; action client-dispatch ordering is not global mutation serialization or a database lock. [DATA][ACTION]
**Existing Cache Components mode:** use async helper with `"use cache"`, `cacheLife`, `cacheTag`; request cookies/headers read outside, including through nested helpers. Arguments/captured values enter key; default runtime storage is in-memory and instance-dependent, not automatic shared durable cache. Cache keys include build/deployment identity. Preserve chosen mode/backend instead of enabling flags or replacing `unstable_cache` as side task. [CACHE]
**Invalidation, pinned 16.3.8:** action `updateTag(tag)` expires immediately; next read blocks for fresh data. Handler/action `revalidateTag(tag, 'max')` allows stale response and refreshes on later access. Handler needing immediate expiry uses `revalidateTag(tag, { expire: 0 })`; it still does not push updated client state. `revalidatePath` targets path, not all other consumers of shared tags; handler marks next visit, action can refresh current route. `refresh()` is action-only router refresh, not data-tag invalidation. [TAG][PATH][ACTION]
**Local judgment / blocker:** choose helper placement, key encoding and exact supported invalidation API from supplied freshness. Blocker: cache scope/consumers/freshness unspecified, Edge-incompatible mode, or required invalidation outside assigned ownership. Never put context-limited `updateTag` inside shared mutation helper also called by HTTP handler.
**Assigned checks — the backend specialist later, Q6:** warm real cache and prove second read reuses entry; mutate then check immediate freshness versus controlled SWR revalidation. Include two tenants with same resource-local ID, authorization change after warm cache, rejected mutation leaving data/cache intact, unrelated tag unaffected, handler next-visit behavior and supplied action response refresh. Use production-mode/adapter fixture; development HMR behavior does not prove deployed cache semantics.
