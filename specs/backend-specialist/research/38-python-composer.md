## The backend specialist contract

The backend specialist implements that packet; missing/mismatched input returns a blocker.
The backend specialist does not search catalogs, diagnose project shape, select architecture, expand scope or manage permissions. Host owns tool exposure, paths, process environment and permission enforcement. Producer `next_steps` are informational strings, never new assignments.
Reuse selected code-generation entrypoints and runtime modules; generic scanner, promotion, benchmark and agent machinery stay outside integration payload. `CORE-BOUNDARY.md:11-29` describes that split; current `engine/index/manifest.py:43-75,100-121` delegates scanning to `hugr_core.scanner`, while `mcp_tools/tree/data.py:158-178` delegates domain dispatch.

## Consumer integration gaps

- `B/tools.ts` currently exposes `hugr-search`, `hugr-describe`, `hugr-list` alongside execution. Backend-specialist-facing host must expose only packet-selected execution operations; researcher resolves catalog information beforehand. No search fallback on producer suggestions.
- Current bridge has no named-slice/copy-in executor. Add only approved fixed-call adapters needed by selected packets (e.g. audit slice + explicit primitive copy), preserving host path/effect policy; do not expose unrestricted domain bundle/list dispatch to the backend specialist.
- `client.callTool` throws on MCP `isError`, not structured producer `ok:false` or slice `status:"error"`; bridge titles can say “Composed”/“Scaffolded” while body reports failure. Integration needs envelope-aware failure handling. [`B/client.ts:87-93`; `B/tools.ts:6-9,42,97`]
- Bridge disables reconnect retry for compose/scaffold; client supports abort, timeout and process cleanup. Default call inactivity timeout is 30 seconds; hard deadline is 5 minutes. Cancellation cannot be treated as rollback of already-written files. [`B/client.ts:9-10,60-86`; `B/tools.ts:40,95`]
- Plugin activation is opt-in and disabled by `OPENCODE_PURE`; client starts installed `hugr-composer` lazily, forwards bounded environment plus worktree root. This research did not establish installed package contents/compatibility. [`B/index.ts:6-17`; `B/client.ts:114-188`]

## Complementary primary tools — distinct implementation work

### 1. datamodel-code-generator — schema → Python DTO source

- Upstream latest release observed: **0.83.0**, published 2026-09-24; tag commit `f59ac9fd0175eb3d2f5bf08ea89ca04b8f3f7ce8`. **MIT**, generator Python `>=3.10`. [D1–D3]
- Assigned OpenAPI 3/JSON Schema plus resolved refs → Pydantic v2 `BaseModel` or preselected `msgspec.Struct` modules. Handles nested models, refs, unions/enums; richer contract input than Composer's field-string shorthand. Pydantic/msgspec are chosen runtime targets, not extra architecture choices for the backend specialist. [D1]
- Example fixed invocation, **not executed**: `datamodel-codegen --input schemas/api.yaml --input-file-type openapi --output-model-type pydantic_v2.BaseModel --target-python-version 3.12 --disable-timestamp --output app/schemas/generated.py`. Pin generator, model runtime and formatter versions together; owner supplies aliases/coercion/extra-field policy and local reference closure. [D1,D4]
- Writes generated artifacts, not service logic/ORM/migrations. Preserve hand validators/mappers outside generated files. `--check` compares existing output without modification; `--diff-against` compares generation from old/new schemas without output writes. Publication machinery replaces artifacts, not source-aware merge of user edits. [D4,D5]
- Assigned checks: generation drift check; import/type/lint; accepted/rejected payloads for required-versus-nullable, bounds, aliases, enum/union discrimination; schema/OpenAPI equivalence to agreed contract. For msgspec target, assigned FastAPI encode/decode/error mapping remains hand wiring. Generation alone does not establish runtime validation semantics.

### 2. sqlacodegen — supplied database schema → SQLAlchemy model source

- Upstream latest release observed: **4.0.4**, published 2026-06-19; tag commit `1b321d1bc5a16a54ebf1f68a3a07fd9c21f86cde`. **MIT**, Python `>=3.10`, SQLAlchemy `>=2.0.29`. [S1–S3]
- Assigned schema snapshot/connection, table/schema selection, dialect and naming options → declarative SQLAlchemy, dataclass, SQLModel or `Table` code. Distinct value: reproduce existing keys/types/relationships rather than invent DB schema from Composer shorthand. Reflection is deterministic assigned input processing, not the backend specialist project diagnosis/catalog search. [S1,S4]
- CLI shape: `sqlacodegen <assigned-snapshot-url> --generator declarative --schemas <assigned-schema> --tables <assigned-tables> --outfile <assigned-model-path>`. Owner provisions snapshot/access; the backend specialist receives exact invocation. CLI connects through `create_engine` and reflects metadata: a DDL text file alone is not this CLI's input. [S4]
- Default output stdout; `--outfile` opens with `"w"`, overwriting. CLI has no preview/merge switch; capture to assigned staging path. Missing PK or association tables can produce `Table` instead of class; relationship inference depends on actual constraints; SQLModel many-to-many generation is documented unsupported. [S1,S4]
- Assigned checks: emitted table/dependency closure versus supplied schema; PK/FK/unique/nullability/default/enum/numeric precision mapping; import and mapper configuration; controlled round-trip against approved dialect fixture; repeat-generation diff. Async session lifecycle, API DTOs/routes, domain methods, migrations and policies remain hand implementation.
